## 0. 结论速览

**一句话：你看到的不是"mock 数据源被当真接入"，而是『账户行 × 全局直联状态列』的语义错配 + V1 遗留的中信模拟账户档案。**

- 数据**查询侧**（流水/余额）的真实门控是正确的：任务只认 REAL 适配器（`realAdapterCodes` 从装配推导），中信 REAL 未装配 → 不会有任何中信假数据投影。
- 出问题的是**状态/元数据展示侧**：银行账户页把「CMB 是否真连」这个**全局状态**渲染到**每一个账户行**上——包括 V1 迁移就种进 `bank_account` 表的 2 个中信账户（带模拟余额）。CMB 一旦真连，中信账户行也跟着变绿"真实银行直联已连接"。
- 附带缺陷：连接状态**没有 per-provider 维度**（全局只有一个 CMB 开关）、`connection_profile` 表的 status 字段被直接透传展示、前端状态色兜底蓝色——凡是"非红"的状态看起来都像"已连接/正常"。

**v1.1 追加的核心认知**：招行侧"直联"天然是**账户级**的——密钥开通后，银行按**可经办账户清单（DCLISACC）**圈定范围；余额/流水查询接口都以**银行账号（accnbr）为主键**逐个请求、单账户独立成败。因此"CMB 已连接"在招行语义下等价于"CMB 下这 N 个账户真实可查"，FINFLOW 展示与判定都必须落到 `bank_account` 行。

按排期，中信 9/18 才进入联通窗口（今天 9/3），**任何"中信已连接"的展示都是错误的**。

## 1.5 招行接口的账户级证据（v1.1 新增，支撑 per-account 判定）

> 来源：`docs/cmb-clouddc/markdown/` 接口文档镜像 + `FINFLOW-招行免前置对接开发要点.md`

| 接口 | 用途 | 账户维度证据 | 与"账户直连"的关系 |
|---|---|---|---|
| `DCLISACC` 查询可经办的账户列表 | 返回当前密钥用户**可查询/可经办**的账户集合 | 请求 `{buscod,busmod}`；响应 `ntqaclstz[]` 每项 = `accnbr`(账号,string35) + `bbknbr`(分行号) + `ccynbr`(币种) + `accnam`(户名) | **银行侧权威"哪些账户真开通了"**。对接要点 L141 明确定位="账户同步"。上线自检第一步是 `DCLISMOD`（可经办业务模式） |
| `NTQADINF` 批量查询余额 | 按账户查余额 | 请求 `ntqadinfx[]` 每项 `{accnbr,bbknbr?,ccynbr?}`，≤30 账户/次；**单账户错不影响其他返回**（要点 L121-123） | 每次真实余额查询 = 天然**账户级可达性探针**（某 accnbr 返回 SUC0000 即证明该账户真实可查） |
| `trsQryByBreakPoint` 账户交易信息查询 | 按账户拉流水 | 请求 X1 单账户（`cardNbr` 户口号）；多币种时 `acctNbr` 做行内续传 | 9/3 18:00 已用该接口跑通真实 STATEMENT（4 笔），证明账户级链路可用 |
| `DCLISMOD` 可经办业务模式查询 | 返回可用的业务模式 | — | 配合 DCLISACC 使用（账务查询 `BUSCOD=N01010` 时 DCLISACC 忽略 busmod） |

**结论**：FINFLOW 的 `bank_account.account_number` 就是招行侧的 `accnbr`。一个账户行能否标"真实直连"，证据链应为：
`REAL 适配器装配（provider 前提）` → `account_number ∈ 银行 DCLISACC 清单（开通范围）` → `最近真实同步 SUCCEEDED（实测可达）`。

## 2. 根因归类（三个缺陷）

### 缺陷 A：连接状态没有 per-provider 维度
全局只有 `cmbProperties.isRealEnabled()` 一个布尔。系统无法表达"CITIC 未接入 / CMB 已接入"这种多银行并存状态。`ConnectionOverview/Configuration/DataQueryCapability` 三个响应共用同一判定。

### 缺陷 B：账户行 × 全局状态错配（"直联状态"列是假列）
`BankAccountPage` 的状态列不读账户的 `bankCode`/`accountNumber`，而是渲染全局 connected。中信账户行因此显示"已连接"。这是用户看到"中信连接成功"的直接原因。**v1.1：即使修成 per-provider 也不够——CITIC 若 9/18 接入，其名下多个账户仍需逐一证明可达。**

### 缺陷 C：模拟时代档案残留 + DB 状态透传
- `V1` 中信账户种子（含模拟余额）至今留在 `bank_account`，账户 API 原样返回 `availableBalance`（`BankAccountService.toResponse` L66-69）。
- `connection_profile.status` 由外部写入、无校验源，`toSummary` 透传 → 只要某行 status 不是红字词汇，就显示成"正常"。

## 3. 目标语义（真实联通才显示，v1.1 账户级）

**两级模型：provider 是前提，account 是判定单位。**

```
┌─ provider 层（连接概览/banner）：这个银行接入没有？
│   REAL 适配器 bean 装配（bankdata.adapter.<bank>.real-enabled=true 且 registry 有 REAL 模式）
│
└─ account 层（账户表直联状态列）：这个账户真能查到数吗？← 核心展示单位
    account.directStatus = f( 装配通过
                             , account_number ∈ 银行侧可经办清单(DCLISACC 缓存)
                             , 最近真实同步 SUCCEEDED(bank_data_sync_task 按 bank_account_id)
                             )
```

| 展示物 | v1.0 规则 | v1.1 规则（账户级） |
|---|---|---|
| 账户行直联状态 | 按账户 bankCode 取 provider 状态 | **每行独立 `directStatus`**（后端合成，服务端为唯一事实源），不共享、不继承其它行 |
| `directStatus` 取值 | — | `DIRECT_CONNECTED`（装配+银行清单命中+有真实成功同步）/ `ONBOARDED`（装配+清单命中但暂无真实同步）/ `NOT_CONNECTED`（未装配或不在清单） |
| 连接列表行状态 | 每行独立 REAL / NOT_CONNECTED | 不变（provider 语义），但 status 以装配+心跳合成，不再透传 DB 字段 |
| 全局 banner | 至少一个 provider REAL 才绿 | 动态文案："已接入：招商 CMB（3/5 账户可查）"——**账户数也来自账户级统计** |
| 模拟余额 | 未接入 provider 的账户不展示余额 | 同左；且只有 `DIRECT_CONNECTED` 账户的余额才标记"实时"，其余显式标注"历史档案/待同步" |

## 4. 分阶段路线图（v1.1 账户级）

### P0 取证（部署侧 1 步，确认线上存量）
```sql
-- RDS 执行，回传结果即可
SELECT id, bank_code, account_name, account_number, status, available_balance, company_id FROM bank_account ORDER BY id;
SELECT id, connection_code, display_name, provider_type, enabled, status, company_id FROM connection_profile ORDER BY id;
```
目的：确认生产 `bank_account` 是否含 V1 中信种子（id=1/2）及其 company 归属、**每行 account_number 是否真实（CMB 建档账户 id=4 的账号是什么）**；connection_profile 是否被运行时写入过中信档案。**这决定 P2/P3 清理范围与 DCLISACC 对账方式。**

### P1 后端 provider 状态 + 账户判定引擎（核心改造）
- **Provider 层**：从 `BankDataAdapterRegistry` 推导每 provider 的 REAL 装配状态，替换 `ConnectionOperationsService` 单 `cmbProperties` 判定；`ConnectionOverview/Configuration/Summary` 增加 per-provider 状态与动态 message。
- **Account 层（v1.1 新增）**：`BankAccountService.listAccounts()` 输出每行新增 `directStatus` + `directEvidence`（最近成功同步时间/证据摘要），合成逻辑收敛到新组件 `AccountDirectStatusService`（输入 = registry REAL 装配 + 账户 bankCode/accountNumber + sync task 心跳 + DCLISACC 清单缓存）。
- 涉及文件：`ConnectionOperationsService.java`、`BankAccountService.java`（或 Response DTO）、新增 `account/AccountDirectStatusService.java`、`bankdata/.../BankDataAdapterRegistry.java`（只读装配查询）。

### P1.5 银行侧可经办清单核对（DCLISACC 探针，v1.1 新增，**见 D4**）
- 新增 CMB 适配器方法 `queryOperableAccounts()`（funcode=DCLISACC，buscod=N01010）→ 解析 `ntqaclstz[]` 的 accnbr 集合。
- 缓存策略：TTL（如 6h）+ 手动刷新（账户建档/连接页加载时触发）；失败降级为"跳过清单核对，仅凭装配+心跳"，不阻断主流程。
- 对账用途：`bank_account` 里 bankCode=CMB 的行的 account_number 与清单 diff → 产出"本地建档但银行侧不可经办"预警（这是**账户级真实性**的最强证据）。
- 涉及文件：`adapter/cmb/` 新增 `CmbOperableAccountsQuery`/解析扩展 `CmbResponseParser`；`AccountDirectStatusService` 消费。

### P2 展示语义修复（前端）
- `BankAccountPage`：直联状态列**消费后端每行 `directStatus`**（不再用全局 connected）；`DIRECT_CONNECTED` 绿、`ONBOARDED` 金、`NOT_CONNECTED` 灰/红。
- 删除写死"（招行 CMB）"文案，消费服务端动态 message（含可查账户数）。
- `statusColor` 扩展三态语义（健康绿 / 中间态金 / 未接入红灰），去掉"非红即蓝"兜底误导。
- 涉及文件：`frontend/src/modules/bank-access/pages.tsx`、`shared/format.ts`、`shared/components.tsx`、`bank-access/types.ts`。

### P3 数据清理与回归护栏
- V1 中信种子账户处置（**见 D1**）：禁用/归档/保留但显式"未接入"。
- 集成测试新增：仅 CMB REAL 时——CITIC 连接行 = NOT_CONNECTED；中信账户行 `directStatus=NOT_CONNECTED`；CMB 账户行仅在 stub 清单命中且有心跳时 `DIRECT_CONNECTED`；`release-contract` CI 若 pin 旧 message 同步更新。
- 验收：全量测试绿 + CI release-contract 绿。
