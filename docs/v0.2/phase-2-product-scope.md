# FINFLOW v0.2 第二阶段产品范围：银行数据接入底座

## 1. 文档定位

本文是 FINFLOW v0.2 第二阶段的产品范围、交付基线和验收口径，供产品、研发、QA、财务、安全及后续银行联调用。本文与 `docs/product-requirements.md` 第 15 节及 `docs/v0.2/bank-data-delivery-backlog.md` 配套使用；若实现细节与本文冲突，以经评审的接口契约和最新产品决策为准。

本阶段的目标是先交付可验证、可追溯、企业隔离的银行数据接入底座。当前仓库没有正式中信 SDK/API 文档、JAR、字段字典、沙箱地址、测试证书或真实回执协议，因此 MOCK 验收不能被表述为真实中信银行已接入。

## 2. 目标与成功口径

### 2.1 阶段目标

1. 建立统一 Bank Adapter 契约，使银行专有协议不扩散到自动入账、资金管理和前端。
2. 打通“适配器 -> 原始请求/响应及同步日志落库 -> 统一模型 -> 业务表/查询投影 -> FINFLOW API -> 前端”的可追溯链路。
3. 同一套任务状态机同时支持定时和手动同步，具备幂等、并发控制、重试、失败定位和审计能力。
4. 通过 MOCK 覆盖余额、流水、回单、对账单、代发五类只读数据及日期窗口、分页、重复、乱序和状态映射场景；支付记录不属于当前范围。
5. 为未来银行 SDK/API、证书和授权沙箱联调留下清晰的准入条件和差距清单。

### 2.2 成功口径

v0.2 在 MOCK 环境完成本文件的 P0 验收，能够证明内部数据链路、权限边界、异常恢复和审计有效。真实银行接入的成功口径另行定义，至少需要银行物料、授权沙箱和联调证据；不能以“页面有数据”或“模拟调用成功”作为真实接入证据。

### 2.3 本轮固定产品决策

- 一期真实银行调用次数为 **0**：v0.2 仅允许 MOCK 或未启用连接，任何真实银行 SDK/API、真实网络请求、真实证书和真实业务数据均不得进入一期验收范围。
- 固定数据链路为：`Bank Adapter -> 原始请求/响应及同步日志落库 -> 统一模型 -> 业务表/查询投影 -> FINFLOW API -> 前端`。任何绕过原始层直接写入统一模型、业务表或前端的实现均不符合本阶段要求。
- 原始数据当前默认按接收时间保留 30 天；到期后的物理删除、归档、延长留存和争议数据豁免规则仍待决策。
- 手动和定时同步必须复用同一任务状态机、任务编号、内部请求号、幂等键、权限、并发控制、重试、监控和审计规则，不得形成两套行为不一致的同步通道。
- 同步责任人、告警接收人、升级路径、静默时间和处置 SLA 尚未确定；在决策完成前不得假设默认责任人或宣称生产告警闭环已完成。
- 未执行并留存测试证据的能力不得标记为“已完成”；设计存在、代码存在或 MOCK 数据可展示，只能标记为“待验证”或“MOCK 已验证”。

## 3. 范围与非范围

### 3.1 本阶段范围

| 范围 | 交付内容 |
| --- | --- |
| Adapter 底座 | 内部 SPI、连接引用、请求上下文、结果状态、分页/游标、幂等号、错误分类和 MOCK Adapter |
| 原始层 | 原始请求、原始响应、接收结果、同步日志先落库；原始数据默认保留 30 天 |
| 同步编排 | 定时和手动触发、任务状态机、并发互斥、可控重试、失败处置和审计 |
| 统一模型 | 五类银行只读数据的内部模型、字段校验、映射版本、来源引用和状态映射 |
| 数据交付 | 业务表或查询投影、重复/乱序处理、部分成功、可追溯关联 |
| 查询 API | FINFLOW 自有只读 API 和前端查询边界，支持企业隔离、账户权限、分页和过滤 |
| 运维与合规 | 同步监控、日志安全摘要、原始数据清理审计、差异对账和测试证据 |

### 3.2 明确不在本阶段

- 不实现或宣称已实现真实中信 SDK/API 接入。
- 不接入真实银行网络、真实生产数据、真实证书、密钥、白名单或真实回执通道。
- 不以配置开关把当前占位适配器变成真实银行调用；未通过银行准入时，真实模式必须保持未启用/快速失败。
- 不重构一期自动入账或银行接入的既有业务流程；主动支付/调拨不属于当前产品。
- 不由银行数据查询修改 FINFLOW 账户余额、转账状态、支付状态、自动入账复核状态或凭证状态。
- 不从银行流水自动创建支付/调拨申请，不以银行查询结果替代支付审批或执行。
- 不让前端直接访问 SDK、银行原始报文、日志全文、密钥或银行专有字段。
- 不在本阶段提供真实银行支付提交、真实回执确认、真实对账结论或真实金蝶制证。
- 不在原始数据 30 天策略之外擅自决定物理删除、长期归档或延长留存；清理/归档最终规则需决策。

## 4. 领域边界与端到端链路

### 4.1 三域边界

| 领域 | 本阶段关系 | 禁止跨域行为 |
| --- | --- | --- |
| 银行接入 | 负责 Adapter、连接引用、同步任务、原始层、日志、监控和五类只读查询投影 | 不拥有主动支付，不直接改变自动入账复核或凭证状态 |
| 自动入账 | 接收经过统一模型和业务校验的流水，继续执行人工复核、模拟制证、对账和追溯 | 银行同步不得跳过人工复核，不得生成支付/调拨申请 |
| 资金管理/支付与调拨 | 继续管理付款或调拨申请、审批、执行和既有资金状态 | 银行查询不得替代申请审批，不得写回资金余额或支付最终状态 |

五类银行只读数据均先进入银行接入域的数据管道。流水若满足一期自动入账的来源和校验规则，可形成自动入账域的待复核输入；余额、回单、对账单和代发只形成查询或对账投影，不能因此改变其他域状态。支付记录及主动支付不在当前产品范围。

### 4.2 数据链路及强制顺序

```text
Bank Adapter / MOCK Adapter
        |
        v
原始请求、原始响应、同步日志落库（先完成）
        |
        v
统一模型、字段校验、状态映射、组合去重
        |
        +--> 自动入账流水业务表（仅进入待复核）
        +--> 五类银行数据业务表/查询投影
        |
        v
FINFLOW 只读 API（企业上下文和 RBAC 由服务端强制执行）
        |
        v
前端查询、任务监控、对账和追溯
```

强制规则：

1. 外部调用返回后，必须先保存原始请求/响应及同步日志，再开始标准化、校验和业务写入；原始层落库失败时不得继续向业务层写入。
2. 原始层、统一模型和业务表/投影分层保存，通过任务编号、内部请求编号、来源记录 ID 和原始消息引用关联。
3. 统一模型成功不等于人工复核通过、凭证生成成功、支付成功或真实银行对账成功。
4. 前端只能调用 FINFLOW API；API 不返回银行 SDK 响应、原始报文全文、同步日志敏感内容或未经治理的银行专有字段。

## 5. 用户角色与权限

权限按“企业上下文 + 账户授权范围 + 操作权限”三层判断。服务端从当前会话取得企业 ID，客户端传入的企业 ID 不能作为授权依据；所有详情、列表、搜索、统计和导出都要复用同一隔离规则。

| 角色 | 默认能力 | 明确禁止 |
| --- | --- | --- |
| 系统管理员 | 管理连接引用、同步计划、手动触发、失败重试、监控、五类查询、审计查看；可按最小权限查看脱敏原始内容 | 查看明文密钥；绕过状态机修改业务事实；直接审批或篡改银行最终状态 |
| 运营/连接管理员（如启用） | 管理授权连接范围、触发和处置同步任务、查看监控和安全日志摘要 | 修改自动入账复核、支付审批和账户余额；读取不必要的原始敏感字段 |
| 财务专员 | 查看授权账户的五类数据和自动入账流水；按授权拥有同步触发或重试时必须单独授予 `bank-sync:trigger`/`bank-sync:retry` | 查看其他企业或账户；修改原始数据；把查询结果当作付款成功 |
| 财务经理 | 查看授权账户、查询和对账；按授权复核自动入账输入；同步操作需显式授予 | 通过银行查询修改支付/调拨状态；将标准化或受理状态解释为最终成功 |
| 审计/合规 | 只读查看审计、任务安全摘要和经脱敏/授权的原始内容 | 触发同步、重试、修改映射或删除原始/审计记录 |
| 业务查看者 | 只读查看被授权的标准化查询结果 | 触发同步、查看原始报文/同步日志全文、修改任何业务状态 |
| 后端服务账号 | 内部调用 Adapter、标准化和落库服务；权限限定到服务接口和企业上下文 | 被前端直接调用；使用未注入或未经批准的真实凭据 |

最小权限拆分至少包括：`bank-data:query`、`bank-sync:trigger`、`bank-sync:retry`、`bank-task:manage`、`bank-raw:view`、`bank-audit:view`、`bank-reconcile:operate`。查询权限不继承触发、重试、原始内容查看或回执处置权限。

## 6. 业务对象与状态

### 6.1 核心对象

| 对象 | 必备关联 | 说明 |
| --- | --- | --- |
| 连接引用 | 企业、连接 ID、来源类型、启用状态 | v0.2 默认 MOCK/未启用；真实凭据仅引用部署密钥，不落业务库 |
| 同步任务 | 企业、连接、账户、数据类型、窗口/游标、触发方式、请求号 | 定时和手动共用状态机与幂等规则 |
| 原始消息 | 企业、任务、请求号、银行请求号、数据类型、接收时间、结果和存储版本 | 请求/响应与安全日志的事实留痕，默认保留 30 天 |
| 统一记录 | 企业、来源、来源记录 ID、账户、映射版本、原始消息引用、业务时间 | 五类数据的内部稳定模型 |
| 查询投影/业务记录 | 企业、统一记录引用、状态、可检索字段 | 供 FINFLOW API 和前端查询；不得覆盖原始事实 |
| 对账记录 | 企业、任务/窗口、记录集合、匹配规则、差异原因、处理状态 | 只能表达本阶段可验证的数据差异，不推断真实银行最终结论 |
| 审计事件 | 企业、操作者/系统任务、操作、目标、前后摘要、结果、请求号 | 追加写入，不能由业务页面修改或删除 |

### 6.2 状态约束

同步任务至少支持：`CREATED`、`RUNNING`、`RAW_SAVED`、`NORMALIZING`、`COMPLETED`、`PARTIAL_COMPLETED`、`FAILED`、`TIMED_OUT`、`MANUAL_ACTION_REQUIRED`、`CANCELLED`。

外部调用返回“已受理”、超时、未知结果或乱序回执时，任务不得直接进入最终成功。必须进入待回执/人工处理路径，或根据已确认的幂等查询结果进入明确终态。

五类记录的外部状态统一映射为内部状态，并保存原始状态值和映射版本。未识别状态进入 `UNKNOWN`/人工处理，不得静默映射为成功、已回单或已对账。

## 7. P2 Epic / Story 及验收标准

优先级说明：P0 为本阶段必须交付并阻断发布的能力，P1 为应交付能力，P2 为有余力时交付或在银行物料到位后补齐的增强项。每条 Story 的“MOCK”只表示可在内部模拟器中验收，不代表银行联调完成。

### P2-E1 Adapter 契约与 MOCK 适配器

#### P2-E1-S01 定义统一 Bank Adapter SPI（P0）

- 用户故事：作为后端工程师，我希望用统一内部契约封装五类只读查询和分页结果，使银行专有协议与业务域隔离。
- 角色/权限：仅后端服务账号调用；前端用户不能直接调用 Adapter。
- 依赖：企业上下文、连接引用、原始层契约。
- 验收标准：
  1. 输入包含企业上下文、连接引用、账户、数据类型、日期窗口/游标、内部请求号和幂等键。
  2. 输出包含结果状态、原始消息引用、银行请求号（如有）、分页信息、重试建议和安全错误摘要。
  3. 五类数据与异步回执在契约层明确区分；银行字段不直接成为前端 DTO。
  4. 未安装真实 SDK 或未通过准入时，真实 Adapter 不可用并快速失败，不能回退为真实成功。
- MOCK：SPI、成功/空结果/失败/超时、错误分类和幂等契约。
- 需银行物料：正式字段、错误码、签名、证书、分页/限流和回执语义。

#### P2-E1-S02 可控 MOCK 数据源（P0）

- 用户故事：作为 QA，我希望按场景稳定注入五类数据和外部异常，以回归全链路。
- 依赖：P2-E1-S01、P2-E2、P2-E7。
- 验收标准：
  1. 可生成余额、流水、回单、对账单、代发的成功、空数据、分页、字段缺失、业务失败、超时、重复和乱序场景。
  2. 相同输入和幂等键得到可重复结果，所有结果显式带 `MOCK` 来源标识。
  3. 模拟器不读取真实凭据、不访问银行网络、不修改 FINFLOW 余额，不创建支付/调拨申请。
- MOCK：全部。
- 需银行物料：无；但 MOCK 通过不能作为真实银行验收证据。

### P2-E2 原始请求/响应与同步日志先落库（P0）

#### P2-E2-S01 原始层先行写入

- 用户故事：作为审计/排障人员，我希望标准化失败时仍可依据原始结果和同步日志定位问题。
- 依赖：P2-E1-S01、企业隔离、脱敏策略。
- 验收标准：
  1. 原始请求/响应和安全日志在标准化、校验和业务写入前持久化；原始写入失败时业务写入不发生。
  2. 原始记录关联企业、连接、账户、任务、内部请求号、银行请求号、数据类型、接收时间、结果和存储版本。
  3. 原始记录不可被业务页面编辑或覆盖，标准化修正以新版本/新引用留痕。
  4. 令牌、密码、私钥、签名原文、证书材料和不必要的完整账号不得进入原始层、日志、审计或 API。
- MOCK：原始优先级、解析失败追溯、脱敏抽检和事务边界。
- 需银行物料：真实报文结构、敏感字段清单和银行请求号核对。

#### P2-E2-S02 原始数据 30 天保留（P0）

- 用户故事：作为合规负责人，我希望原始请求/响应按接收时间默认保留 30 天，并能证明到期处理发生。
- 依赖：P2-E2-S01；待决策 D-01。
- 验收标准：
  1. 原始数据默认保留 30 天，普通业务用户不能修改期限。
  2. 到期处理具备预览、执行、失败重试、范围、数量和结果统计；不得误删统一模型、业务记录或审计事件。
  3. 清理/归档任务写入不可删除的审计事件；争议或事故标记可暂停清理，并记录授权、原因和期限。
  4. 在物理删除、加密归档和延长留存未决时，不宣称已满足长期合规要求。
- MOCK：时间推进、到期清理、豁免和审计恢复。
- 需银行物料：无；最终留存方式需业务/合规决策。

### P2-E3 定时与手动同步编排（P0）

#### P2-E3-S01 手动触发同步

- 用户故事：作为有 `bank-sync:trigger` 权限的运营人员，我希望按连接、账户、数据类型和日期窗口手动同步，并查看任务结果。
- 依赖：P2-E1、P2-E2、P2-E4、RBAC。
- 验收标准：
  1. 请求先创建唯一任务号和内部请求号，再调用 Adapter；重复请求返回既有任务或明确冲突结果。
  2. 服务端白名单校验企业、连接、账户、类型、窗口和游标；客户端企业 ID 不参与授权。
  3. 同一企业、连接、账户、类型、窗口/游标和幂等键的并发请求最多一个有效执行。
  4. 完成、部分完成、失败、超时和待人工处理均可查询，受理或超时不得显示为已同步。
- MOCK：全部。
- 需银行物料：真实数据、增量规则、网络策略、限流和真实错误。

#### P2-E3-S02 定时任务编排（P0）

- 用户故事：作为系统管理员，我希望为已启用的 MOCK/连接配置定时同步，并能暂停和恢复。
- 依赖：P2-E3-S01、银行接入模块、监控审计。
- 验收标准：
  1. 每次运行记录计划时间、实际时间、触发方式、窗口/游标、请求号、重试次数和最终状态。
  2. 多实例部署不会重复执行同一计划任务；锁和幂等结果可追踪。
  3. 可重试错误与不可重试错误分类明确，重试不得重复产生业务事实。
  4. 未通过真实银行准入时，定时任务只能运行 MOCK 或保持未启用；单独打开配置不能启用真实调用。
- MOCK：调度、锁、暂停/恢复、重试和告警模拟。
- 需银行物料：真实定时拉取、银行限流、维护窗口和生产网络白名单。

#### P2-E3-S03 任务状态与人工处置（P0）

- 用户故事：作为运营人员，我希望知道任务卡在哪个阶段，并对失败或未知结果执行受控重试或人工处理。
- 依赖：P2-E2、P2-E3-S01、P2-E6。
- 验收标准：
  1. 仅服务端允许状态转换；刷新、重复点击和篡改请求不能伪造完成。
  2. 每次转换记录前后状态、操作者/系统任务、时间、请求号、错误摘要和影响范围。
  3. 未知结果不得自动重发可能产生副作用的外部请求；应先回执查询、对账或人工处置。
- MOCK：全部状态转换、未知结果和人工处置。
- 需银行物料：真实回执查询、补单策略和银行最终确认规则。

### P2-E4 日期窗口、分页与增量边界（P0）

#### P2-E4-S01 日期窗口校验

- 用户故事：作为运营人员，我希望按明确时间窗口同步，避免漏数或重复拉取。
- 验收标准：
  1. 窗口使用明确时区和边界语义，起止时间、最大跨度和未来时间均有服务端校验。
  2. 相邻窗口的边界记录可重复拉取但不会产生重复业务事实；任务记录实际请求窗口和标准化窗口。
  3. 超出银行或系统允许跨度时分段创建可追踪子任务，任一分段失败能定位。
- 依赖：P2-E1、P2-E3、P2-E5。
- MOCK：时区、边界、分段和重复窗口。
- 需银行物料：银行账期、时区、最大窗口和增量游标语义。

#### P2-E4-S02 分页、游标与断点恢复

- 用户故事：作为系统，我希望分页拉取在失败重试后从可验证断点恢复，不漏记录或重复制证。
- 验收标准：
  1. 记录页码/游标、页大小、总量（如有）、上一页引用、最后成功断点和结束标志。
  2. 空页、重复游标、页码跳转、最后一页和中途超时均有明确处理；重复页不会产生重复业务记录。
  3. 断点恢复与全量重跑使用同一去重规则，原始响应每页均可追溯。
- 依赖：P2-E2、P2-E3、P2-E6。
- MOCK：全部。
- 需银行物料：真实分页协议、游标有效期、限流和断点语义。

### P2-E5 统一模型、标准化与业务写入（P0）

#### P2-E5-S01 五类统一模型及状态映射

- 用户故事：作为业务域工程师，我希望五类数据进入稳定的内部模型，银行专有字段留在受控边界内。
- 验收标准：
  1. 余额、流水、回单、对账单和代发记录至少包含企业、来源系统、来源记录 ID、账户引用、映射版本、原始消息引用、来源时间和标准化时间。
  2. 流水统一表达时间、方向、金额、币种、对手、摘要和外部流水号；金额使用精确货币类型。
  3. 原始状态值和内部状态、映射版本、未知状态原因均可追溯；未知状态进入人工处理，不默认为成功。
  4. 标准化成功不改变支付/调拨、自动入账复核或凭证状态。
- 依赖：P2-E1、P2-E2、一期自动入账模型和字段字典。
- MOCK：模型、映射版本、正常/缺字段/未知状态。
- 需银行物料：正式字段语义、状态枚举、金额方向、外部编号和时效口径。

#### P2-E5-S02 校验及分批落库

- 用户故事：作为财务专员，我希望每条无效记录都有原因，有效记录不因其他记录失败而丢失。
- 验收标准：
  1. 校验必填字段、金额、精度、币种、方向、时间、账户归属、外部编号和长度。
  2. 具备最小识别信息的失败记录保留原始引用和字段级原因；无法识别的输入计入任务失败统计。
  3. 任务允许部分成功；每条业务记录都能追溯到原始消息和任务。
  4. 流水进入自动入账域时只能进入待复核，不得自动跳过人工复核或生成支付/调拨申请。
- 依赖：P2-E5-S01、P2-E2、一期自动入账第 13 节。
- MOCK：全部校验、部分成功和追溯。
- 需银行物料：银行特殊字段和业务规则确认。

#### P2-E5-S03 组合去重及并发唯一性（P0）

- 用户故事：作为系统，我希望定时、手动、重试、重复页和乱序回执不会形成同一银行事实的多条业务记录。
- 验收标准：
  1. 优先使用银行流水号；缺少稳定编号时使用“企业 + 银行账户 + 交易时间 + 金额”组合，并保存命中规则、候选记录和判定依据。
  2. 服务端业务判断与数据库企业范围唯一约束共同兜底；并发导入最多一条标准化记录和一条业务事实。
  3. 命中重复时返回既有记录引用和 `DUPLICATE` 结果，不重复入账、不重复制证。
  4. 弱判定要记录冲突风险并转人工复核；不同企业即使流水号相同也必须隔离。
- 依赖：P2-E2、P2-E5-S01、企业隔离。
- MOCK：重复导入、跨企业同号、并发、弱判定和乱序。
- 需银行物料：各数据类型稳定主键和字段缺失情况。

### P2-E6 五类查询与前端交付（P0）

#### P2-E6-S01 FINFLOW 只读查询 API

- 用户故事：作为授权用户，我希望通过 FINFLOW API 查询五类银行只读数据，而不直接接触银行接口。
- 角色/权限：`bank-data:query`；同步触发、任务重试、原始查看和回执处置为独立权限。
- 验收标准：
  1. 提供余额、流水、回单、对账单、代发的只读查询；数据来源为标准化业务表或投影。
  2. 支持适用的企业/账户、日期、方向、金额、状态、来源、业务编号和关键字过滤；分页、排序和窗口有上限。
  3. 未接入真实银行时，响应明确标记 `MOCK`、`UNAVAILABLE` 或 `EMPTY`，不能伪造真实银行结果。
  4. 查询不能修改余额、支付/调拨状态、自动入账状态或模拟凭证；跨企业资源访问服务端拒绝且不泄露对象存在性。
- 依赖：P2-E5、RBAC、企业隔离、P2-E7。
- MOCK：五类查询契约、数据、空结果、错误状态和权限。
- 需银行物料：真实五类数据字段、时效和一致性语义。

#### P2-E6-S02 前端查询与追溯

- 用户故事：作为财务人员，我希望在前端查看列表、详情、状态和追溯链路，并从流水关联到自动入账待复核记录。
- 验收标准：
  1. 前端只调用 FINFLOW API，不嵌入 SDK 凭据或银行端点。
  2. 列表支持稳定分页和组合筛选，详情展示来源、任务、原始消息引用、标准化状态、业务状态和更新时间。
  3. 前端明确区分 MOCK、受理中、处理中、未知、成功、失败和人工处理，不把模拟成功显示为真实付款或真实制证。
  4. 无权限模块、按钮和详情均由后端再次保护；直接调用接口也不能越权。
- 依赖：P2-E6-S01、P2-E7、一期自动入账页面。
- MOCK：全部 UI 和追溯交互。
- 需银行物料：真实字段展示的脱敏与业务文案确认。

### P2-E7 异常、乱序回执、对账与审计（P0/P1）

#### P2-E7-S01 重复、乱序和未知状态处理（P0）

- 用户故事：作为系统，我希望外部返回乱序、重复或未知状态时保持事实不被覆盖，并能人工定位。
- 验收标准：
  1. 以内部事件时间、外部状态时间（如有）和版本/序列信息判断新旧；缺少可靠顺序依据时保留事件并转人工处理。
  2. 旧事件不能覆盖已确认的新状态；重复事件幂等；未知事件不映射为成功。
  3. 每次状态映射保留原值、映射版本、来源消息、接收时间和处理结果。
- 依赖：P2-E2、P2-E5-S01、P2-E5-S03。
- MOCK：全部。
- 需银行物料：银行状态时间、序列、回执和最终状态语义。

#### P2-E7-S02 对账与差异追踪（P1）

- 用户故事：作为财务经理，我希望对同步窗口内的原始事实、统一记录、业务投影和模拟回执进行对账，定位缺失、重复和状态差异。
- 验收标准：
  1. 对账范围、时间窗口、匹配规则、参与记录数、匹配数、差异数和执行人/任务可查询。
  2. 差异至少分类为缺失、重复、金额/时间/方向不一致、状态未映射、未知结果和待人工处理，并可追溯原始消息。
  3. 对账结果不自动修改银行事实、余额、支付/调拨状态或自动入账复核结果。
  4. 页面明确“MOCK 数据对账”与“真实银行对账”的边界。
- 依赖：P2-E2、P2-E5、P2-E6、P2-E7-S01。
- MOCK：全部内部链路和差异场景。
- 需银行物料：真实对账文件/接口、银行口径和最终确认规则。

#### P2-E7-S03 监控、日志摘要与审计（P1）

- 用户故事：作为运营和审计人员，我希望按任务、请求号、连接、账户、类型和结果定位问题，并证明敏感操作发生过。
- 验收标准：
  1. 查询显示阶段、耗时、重试次数、状态、影响范围和安全错误摘要，不返回令牌、签名、完整账号、原始响应全文或内部堆栈。
  2. 同步触发、重试、原始内容查看、映射变更、清理/豁免和权限拒绝均产生审计事件。
  3. 日志与原始内容读取遵守企业隔离和最小权限，审计记录追加写入且不可由业务页面删除。
- 依赖：P2-E2、P2-E3、RBAC、监控基础设施。
- MOCK：全部安全和审计验证。
- 需银行物料：真实错误码到安全摘要的映射。

## 11. P2 发布验收出口

只有同时满足以下条件，才可称为“v0.2 MOCK 底座验收通过”：

2. 原始请求/响应及同步日志确认先落库，标准化失败可追溯，30 天保留和清理审计可验证。
3. 日期窗口、分页/断点、重复、并发、乱序和未知状态测试均有结果；没有重复业务事实或错误最终成功。
4. 企业隔离、角色权限、API 只读边界和前端不直连银行的测试通过；跨企业查询和越权操作均被服务端拒绝。
5. 自动入账仅接收符合规则的待复核流水；支付/调拨状态、余额和凭证状态未被银行查询改写。

真实银行接入必须另行通过：银行资料包和映射评审、证书与安全评审、授权沙箱联调、真实错误/分页/回执/对账测试、数据合规评审、生产灰度和银行侧签字。任何一项缺失，连接仍保持未启用或 MOCK，不得以本阶段文档作为真实银行上线凭证。

### 11.2 验收证据与完成标记规则

每条 P0/P1 Story 必须关联可复核的需求编号、测试场景、执行时间、环境、输入摘要、结果和缺陷编号（如有）。验收记录至少应覆盖成功、空结果、部分成功、失败、超时、重复、乱序、未知状态、跨企业越权和重复请求等适用场景。

以下情况只能标记为“未完成”或“待银行物料”，不能标记为已交付：

1. 只有接口设计、代码检查或人工演示，没有可复核的自动化或系统测试证据。
2. 只有 MOCK 结果，没有真实银行 SDK/API、证书、授权沙箱和银行侧联调证据。
3. 只验证了页面显示，没有验证原始层先落库、企业隔离、服务端权限、幂等和跨域不变式。
4. 能力依赖待决策项，但责任人、决策结论或风险豁免尚未留痕。

### 11.3 v0.4 产品范围覆盖说明（2026-08-31）

当前产品范围以 `docs/product-requirements.md` v0.4 为准：银行接入仅提供余额、流水、回单、对账单和代发五类只读查询；银行支付记录查询、主动转账、付款、调拨、支付审批和支付执行均不建设。本文早期“六类查询”、支付回执查询或出站支付提交描述属于历史方案背景，不构成当前交付范围；支付相关需求须另立银行 SDK 适配和独立验收。

### 11.4 轻量统一 Adapter 聚合层基线

本阶段补充并固定以下架构：`FINFLOW 业务模块 -> 统一 API 聚合层 -> 中信/招行/建行/MOCK 等 Bank Adapter -> 各银行接口`。聚合层不是独立复杂平台，而是统一北向契约、路由和南向编排边界。

1. 聚合层统一余额、流水、回单、对账单查询及同步任务 API，负责请求/响应、分页、日期窗口、错误码和状态模型；支持 `SUCCESS`、`FAILED`、`PENDING`、`TIMEOUT`、`UNKNOWN`、`EMPTY`、`DUPLICATE`、`PARTIAL`，未知不得自动成功。
2. `BankDataAdapter` 作为底层扩展插件保留。按银行/连接编码注册和路由，首期至少用 `CITIC_MOCK` 与 `CMB_MOCK` 验证格式转换、分页、异常隔离、状态映射和幂等；真实 Adapter 仍仅保留受控边界。
3. 聚合层输出的统一结果必须带映射版本；原始请求/响应及同步日志继续以独立事务先落库，再转换统一模型、写业务表/投影。任务号、请求号、银行请求号、原始摘要和映射版本形成追溯链。
4. 前端、自动入账、对账只调用 FINFLOW API，不能直接调用 Adapter 或银行 SDK/API。首期不做支付/转账/调拨、自研加密、证书/签名、云直连/专线、生产银行通道和复杂低代码字段编排，真实银行调用保持为 0。
