# FINFLOW v0.2 银行数据接入交付 Backlog

## 1. 版本目标与交付原则

- 版本：FINFLOW v0.2 银行数据接入底座。
- 目标：在银行文档、SDK/API 和授权沙箱条件满足后，提供可恢复、可追溯、企业隔离的银行数据采集与查询能力，并为支付回执接入保留边界。
- 核心链路：

```text
银行 SDK/API
-> 银行适配器
-> 原始结果与同步日志
-> 统一标准化模型
-> 校验与组合去重
-> 自动入账业务表或只读查询投影
-> FINFLOW 只读 API
-> 前端
```

- 设计原则：外部银行字段不扩散到业务域；原始结果、标准化记录和业务记录分层保存；定时与手动同步共用任务、幂等、审计和错误处理；所有资源以服务端企业上下文隔离。
- 业务收益延续一期目标：在规则稳定、业务量可比的完整自然月中，减少人工下载、整理、核对和追溯工作量；v0.2 不以“已调用银行”或“SDK 返回成功”单独作为上线标准。

## 2.1 中信 SDK/接口资料转化基线

当前仓库未发现中信银行正式 SDK/API 文档、JAR/依赖包、字段字典、沙箱地址、测试证书或回执协议。因此，现有实现只能作为 FINFLOW 内部占位契约，不能据此推断中信正式协议或直接宣称已具备真实接入能力。

### 已知占位能力

- `CiticBankSdkClient.queryAvailableBalance(BankAccount)`：查询可用余额的内部占位方法。
- `CiticBankSdkClient.submitPayment(BankAccount, BankTransferCommand)`：提交支付的内部占位方法。
- `MockCiticBankSdkClient`：返回本地模拟余额和 `CITIC-MOCK-*` 参考号，不访问银行网络。
- `ExternalCiticBankSdkAdapter`：非模拟模式当前返回 `501`，不允许被解释为真实银行调用成功。

### 尚未确认的协议事实

银行接入前必须逐项确认：正式调用路径和版本、请求/响应字段及枚举、鉴权/签名/验签、证书与密钥轮换、错误码、分页与游标、时间和账期语义、幂等键、限流与超时、回执通知/查询、重试和对账口径，以及余额、流水、回单、对账单、支付记录和代发的业务含义。

### 银行资料包准入清单

银行接口负责人需提供可审计版本的接口目录、SDK/API 包及依赖说明、字段和错误码字典、安全接入手册、沙箱端点与网络要求、测试账号/账户与证书、样例报文、回执和对账规则、限流/维护窗口说明、生产准入流程及联调联系人。资料缺失的字段只能进入待确认映射，不得由研发猜测后进入真实适配器。

## 4. Backlog 明细

### E1 银行适配器契约与模拟器

#### V02-E1-S01 定义银行适配器 SPI

- 优先级：P0
- Story：作为后端工程师，我希望以统一适配器接口封装鉴权、签名、分页、余额、流水、回单、对账单、支付记录、代发和回执能力，使银行专有实现不会侵入自动入账、支付/调拨或前端。
- 角色与权限：仅后端服务内部调用；任何前端用户不能直接调用适配器。适配器配置管理由系统管理员拥有，真实凭据只允许通过部署平台密钥引用注入。
- 验收标准：
  1. SPI 明确区分拉取类数据、出站支付提交和异步回执查询，输入输出使用 FINFLOW 内部契约。
  2. 每个调用能够携带 `company_id`、连接档案、内部 `request_id`、任务编号、外部幂等号和请求时间范围。
  3. 适配器输出包含原始报文引用、银行侧请求号、分页信息、结果状态和安全错误摘要；银行字段不直接出现在前端 DTO。
  4. 未安装真实 SDK 或未通过沙箱准入时，真实适配器不可用并快速失败，不回退为真实成功。
- 依赖：连接档案/企业上下文；E3 原始层契约；银行接口文档；后续真实适配器依赖银行 SDK/API 和沙箱。
- 模拟器可完成：接口契约、模拟适配器、错误映射、分页、超时、重复/乱序回执和幂等行为。
- 必须等待 SDK/API/沙箱：真实鉴权、签名、证书、错误码、限流和外部回执语义。

#### V02-E1-S02 建立可控银行模拟器

- 优先级：P0
- Story：作为 QA/研发，我希望模拟器能注入确定性结果，以验证同步和回执流程，而不是每次随机返回成功。
- 验收标准：
  1. 可按测试场景返回余额、流水、回单、对账单、支付记录和代发的成功、空数据、部分分页、业务失败、网络超时、重复响应、乱序回执和字段缺失结果。
  2. 相同测试输入和幂等键产生可重复结果；测试场景明确标记为 `MOCK`，不得显示为真实银行事实。
  3. 模拟器不读取真实凭据、不发起外网银行请求、不改写 FINFLOW 账户余额，不创建支付/调拨业务记录。
  4. 失败和超时场景可在自动化测试中复现，并能关联内部请求编号和任务编号。
- 依赖：V02-E1-S01、E2、E6。
- 模拟器可完成：全部。
- 必须等待 SDK/API/沙箱：无；但模拟通过不等于真实银行准入。

#### V02-E1-S03 将中信资料转化为适配器实现清单

- 优先级：P0
- Story：作为适配器负责人，我希望把中信正式资料逐项映射到内部 SPI、字段、错误处理和联调案例，确保真实实现可评审、可回归且不把银行协议扩散到业务域。
- 角色与权限：银行接口负责人提供并确认资料；适配器负责人维护映射和差距清单；安全、财务和 QA 参与评审；未完成评审的映射不得进入真实环境。
- 验收标准：
  1. 对每个计划能力建立“银行接口/字段/枚举/错误码/回执 -> FINFLOW 内部字段或状态”的可追溯映射，标明资料版本、负责人、确认状态和原始依据。
  2. 对鉴权、签名、证书、分页、游标、时间区间、幂等、限流、超时、重试、回执、对账和敏感字段分别记录已知事实、差距、风险及测试案例。
  3. 每个未确认项都有阻断级别和处理人；未确认的银行字段不得被静默映射、写入通用 API 或用于自动入账/支付状态变更。
  4. 适配器实现清单覆盖成功、空结果、字段校验失败、业务拒绝、网络失败、超时、重复响应、乱序回执、分页断点和跨企业隔离，并能关联内部请求编号。
  5. 资料包、映射表、样例报文和联调结论均有版本留痕；研发、QA、财务和安全共同签字后，才能进入银行沙箱验收。
- 依赖：V02-E1-S01、V02-E1-S02；银行正式资料包、测试账号/证书和授权沙箱。
- 模拟器可完成：基于内部契约的映射模板、差距清单、故障矩阵、回归案例和所有不依赖真实银行语义的自动化测试。
- 必须等待 SDK/API/沙箱：中信正式字段和错误码确认、SDK/API 兼容性验证、签名/证书实测、真实分页/限流/回执和银行侧联调结论。

### E2 同步任务：定时与手动

#### V02-E2-S01 手动发起银行数据同步

- 优先级：P0
- Story：作为有授权的运营人员，我希望按企业、连接、账户和时间范围手动触发一次同步，并能查看任务结果。
- 角色与权限：系统管理员或后续明确授权的运营角色拥有 `bank-sync:trigger`；财务专员/财务经理默认只能查看授权范围内任务；业务查看者无触发权限。
- 验收标准：
  1. 手动请求先创建唯一任务编号和内部请求编号，再进入适配器调用；不得绕过原始报文落库。
  2. 请求参数按白名单校验企业、连接、账户、数据类型和日期/游标范围；服务端从会话取得企业上下文，不接受客户端企业 ID 作为授权依据。
  3. 同一企业、连接、账户、数据类型、时间范围/游标和幂等键的并发请求只产生一个有效任务；重复请求返回原任务及当前状态。
  4. 任务完成后可查看成功、部分成功、失败、超时、重试或需人工处理原因，不能把受理或超时显示为数据已同步。
- 依赖：E1、E3、E4、E7、企业与 RBAC 基础。
- 模拟器可完成：触发模拟同步、故障注入、重复提交和查询结果验证。
- 必须等待 SDK/API/沙箱：真实数据拉取、银行增量规则、网络策略和真实调用限流。

#### V02-E2-S02 定时同步任务编排

- 优先级：P0
- Story：作为系统管理员，我希望为启用的连接和账户配置定时同步，使日常拉取不依赖人工操作，并可暂停或恢复。
- 角色与权限：系统管理员配置频率和启停；运营监控角色查看运行结果；财务角色只读查看与其账户授权相关的任务。
- 验收标准：
  1. 每次调度都创建可追溯任务，包含计划时间、实际开始/结束时间、连接、账户、数据类型、游标/账期、请求编号和状态。
  2. 多实例部署不重复执行同一计划任务；任务锁、幂等键和重试次数可查询。
  3. 失败按可重试/不可重试分类；重试不重复写入原始报文、标准化记录或业务事实。
  4. 定时任务默认在 `MOCK` 或未启用状态运行；未通过真实银行准入时，不能仅通过配置开关启用真实调用。
  5. 责任人、告警接收人、升级路径、静默时间和处置 SLA 未决前，系统必须展示“责任配置未完成”，不得默认为生产责任人。
- 依赖：V02-E2-S01、连接运营模块、E7；待决策项 D2。
- 模拟器可完成：调度、锁、暂停/恢复、故障重试、模拟监控。
- 必须等待 SDK/API/沙箱：真实定时拉取、银行限流和生产网络白名单。

#### V02-E2-S03 同步任务状态与人工处置

- 优先级：P0
- Story：作为运营人员，我希望看到任务处于什么阶段，并能对失败或未知结果执行受控重试/标记人工处理。
- 验收标准：
  1. 任务至少支持 `CREATED`、`RUNNING`、`RAW_SAVED`、`NORMALIZING`、`COMPLETED`、`PARTIAL_COMPLETED`、`FAILED`、`TIMED_OUT`、`MANUAL_ACTION_REQUIRED`、`CANCELLED`。
  2. 状态只能按服务端状态机转换；刷新、重复点击或篡改请求不能伪造完成。
  3. 每次转换记录前后状态、操作人/系统任务、时间、请求编号、错误摘要和影响范围。
  4. 未知结果不得自动重发可能产生副作用的外部请求；需先执行回执查询、对账或人工处置策略。
- 依赖：E3、E4、E6、E7；待决策项 D3。
- 模拟器可完成：全部状态转换、未知结果和人工处置测试。
- 必须等待 SDK/API/沙箱：真实未知结果的补单、回执和银行侧最终确认规则。

### E3 原始报文与同步日志

#### V02-E3-S01 原始请求/响应先落库

- 优先级：P0
- Story：作为审计和排障人员，我希望在标准化失败时仍能受控查看原始银行结果和同步日志，确保链路可追溯。
- 角色与权限：原始报文不是普通前端资源；系统管理员或专门审计角色通过最小权限审计接口查看脱敏内容；普通财务用户只看安全摘要和业务结果。
- 验收标准：
  1. 外部调用返回后，原始请求/响应在标准化、校验和业务写入之前持久化；原始层写入失败时不得继续写业务层。
  2. 原始记录至少关联企业 ID、连接/账户、任务编号、内部请求编号、银行侧请求号、接收时间、数据类型、结果、报文摘要和存储版本。
  3. 原始报文不可被业务表覆盖、编辑或删除；标准化映射和业务修正均产生新记录或新版本引用。
  4. 密码、令牌、私钥、签名原文、证书材料和不必要的完整账号不得进入原始报文、日志、审计、导出或浏览器。
- 依赖：E1、企业隔离、密钥管理策略。
- 模拟器可完成：原始先落库、解析失败追溯、脱敏抽检和故障回滚。
- 必须等待 SDK/API/沙箱：银行原始报文格式、字段敏感性清单和真实请求/响应核对。

#### V02-E3-S02 30 天保留与清理审计

- 优先级：P0
- Story：作为合规负责人，我希望原始结果按接收时间保留 30 天，并能证明到期处理发生过。
- 验收标准：
  1. 原始请求/响应默认按接收时间保留 30 天；保留期限由配置控制，但不得由普通业务用户修改。
  2. 到期任务具备预览、执行、失败重试和清理统计；清理按企业和记录范围执行，不能误删标准化记录、业务记录或审计事件。
  3. 每次删除或归档记录清理任务编号、执行人/系统任务、时间、数量、范围、结果和失败原因；清理审计本身不可删除。
  4. 争议、审计或事故标记的记录可暂停清理；暂停和恢复必须有授权、原因和期限。
  5. 物理删除、加密归档或按事件延长留存的最终策略未决前，系统不得擅自宣称满足长期合规留存。
- 依赖：E3-S01；待决策项 D1。
- 模拟器可完成：时间推进、到期清理、豁免、审计和恢复测试。
- 必须等待 SDK/API/沙箱：无，但最终保留策略需业务/合规决策。

#### V02-E3-S03 同步日志查询与安全摘要

- 优先级：P1
- Story：作为运营人员，我希望按请求编号、任务、连接、时间和结果查询同步日志，快速定位失败。
- 验收标准：
  1. 支持按企业、时间、任务、连接、账户、数据类型、结果、错误类型和请求编号筛选，组合条件为 AND，服务端分页和排序有上限。
  2. 结果显示耗时、阶段、状态、重试次数和安全错误摘要；不显示令牌、签名、完整账号、原始响应或内部堆栈。
  3. 日志读取权限与数据企业边界一致；越权查询统一拒绝且不泄露对象存在性。
  4. 日志读取、原始内容查看和失败重试均产生审计事件。
- 依赖：E3-S01、E7、权限模型。
- 模拟器可完成：全部。
- 必须等待 SDK/API/沙箱：真实银行错误摘要映射需待 SDK/API 确认。

### E4 标准化、校验与组合去重

#### V02-E4-S01 建立统一银行数据模型

- 优先级：P0
- Story：作为业务域工程师，我希望余额、流水、回单、对账单、支付回执和代发结果有稳定的内部模型，避免银行字段侵入业务表。
- 验收标准：
  1. 每类标准化记录至少带 `company_id`、`source_system`、`source_record_id`、银行账户引用、`mapping_version`、原始消息引用、来源时间和标准化时间。
  2. 流水统一表达交易时间、方向、金额、币种、对手、摘要和外部流水号；金额使用精确货币类型，不使用浮点计算。
  3. 银行专有字段只保留在原始层或受控扩展字段，不进入通用自动入账、支付/调拨和查询 API 契约。
  4. 标准化成功不等于复核通过、制证成功、付款成功或真实对账成功。
- 依赖：E1、E3；自动入账现有模型；业务字段字典。
- 模拟器可完成：模型、映射版本、正常/缺字段映射。
- 必须等待 SDK/API/沙箱：最终银行字段映射、金额/方向和外部编号语义。

#### V02-E4-S02 标准化与业务校验

- 优先级：P0
- Story：作为财务专员，我希望系统在写入自动入账或查询投影前发现格式、账户和业务问题，并保留每条失败原因。
- 验收标准：
  1. 校验必填字段、金额大于零、货币精度、方向枚举、交易时间、账户归属、外部编号和字段长度。
  2. 校验失败不丢弃原始事实；具备最小识别信息的记录保留为失败标准化记录并记录字段级原因，无法识别的输入计入任务失败统计。
  3. 批次/任务允许部分成功；有效记录不因其他记录失败而回滚，但每条记录结果可定位到原始消息和任务。
  4. 有效流水进入自动入账待复核域或只读投影的规则明确；不得自动跳过人工复核或自动生成支付/调拨申请。
- 依赖：V02-E4-S01、E3、自动入账第 13 节流程。
- 模拟器可完成：全部校验和部分成功场景。
- 必须等待 SDK/API/沙箱：银行特殊字段和业务规则确认。

#### V02-E4-S03 组合去重与唯一约束

- 优先级：P0
- Story：作为系统，我希望定时、手动、重试和重复回执不会产生多条同一银行事实。
- 验收标准：
  1. 去重同时使用银行流水号，以及“企业 + 银行账户 + 交易时间 + 金额”组合；保留命中规则、候选记录和判定依据。
  2. 服务端先做业务判定，数据库以企业范围内唯一约束/索引兜底；并发导入最多创建一条标准化记录和一条业务事实。
  3. 命中重复时返回已有记录引用和 `DUPLICATE` 结果，不重写原始数据、不创建第二个自动入账待复核记录、不重复制证。
  4. 银行缺少稳定流水号时必须记录降级判定、冲突风险和人工复核要求，不得静默使用弱判定。
  5. 不同企业即使流水号相同也必须隔离；同一企业不同账户或不同交易时间/金额的合法流水不能被错误合并。
- 依赖：E3、E4-S01、企业隔离、数据库约束。
- 模拟器可完成：重复导入、并发、跨企业同号、弱判定和回执乱序。
- 必须等待 SDK/API/沙箱：各银行流水号稳定性和字段缺失情况。

### E5 银行数据只读查询 API

#### V02-E5-S01 提供五类只读查询

- 优先级：P0
- Story：作为授权用户，我希望通过统一 FINFLOW API 查询余额、流水、回单、对账单、支付记录和代发，而不直接接触银行 SDK 或原始报文。
- 角色与权限：默认 `bank-data:query` 只读权限；四类企业角色按企业和账户授权查询。原始报文查看、同步触发、任务重试和支付回执处置为独立权限，不由查询权限继承。
- 验收标准：
  1. API 只返回标准化业务表或查询投影；前端不得收到银行 SDK 响应、原始报文、同步日志和银行专有字段。
  2. 资源支持按企业、账户、时间范围、方向、金额区间、状态、来源、业务编号等适用条件筛选，服务端白名单分页和排序。
  3. 余额、流水、回单、对账单、支付记录和代发均为只读；查询不得修改账户余额、自动入账状态、支付/调拨状态或模拟凭证。
  4. 未接入真实银行时返回明确 `UNAVAILABLE`/`SIMULATED`/`EMPTY` 状态和来源标识，不得伪造真实银行结果。
  5. 查询 API 对跨企业 ID、资源 ID、账户 ID、凭证号和筛选参数执行服务端隔离，越权不泄露对象存在性。
- 依赖：E4、企业隔离、RBAC、E7；各查询投影的数据源。
- 模拟器可完成：六类查询契约、模拟数据、权限、空结果和错误状态。
- 必须等待 SDK/API/沙箱：真实六类数据的字段和时效语义。

#### V02-E5-S02 查询与自动入账追溯关联

- 优先级：P1
- Story：作为财务人员，我希望从银行流水查询结果跳转到自动入账追溯链路，判断其是否已标准化、待复核或已模拟制证。
- 验收标准：
  1. 查询结果可通过受控引用跳转到标准化记录、自动入账批次、复核、模拟凭证和对账投影。
  2. 关联是只读追溯，不改变任何状态，不把查询结果自动标记为已导入、已复核或已制证。
  3. 找不到关联时显示“尚未进入自动入账流程”及原因，不显示为失败付款或真实银行异常。
  4. 关联查询依然按企业、账户和角色过滤，原始报文仅在独立权限下受控查看。
- 依赖：E4、自动入账第 13 节；E5-S01。
- 模拟器可完成：全部。
- 必须等待 SDK/API/沙箱：无。

### E6 异步支付回执边界

#### V02-E6-S01 固化出站请求与外部幂等号

- 优先级：P1
- Story：作为支付域工程师，我希望审批完成后的出站请求能与银行回执关联，同时不让银行接入侵入自动入账域。
- 领域边界：支付/调拨仍负责申请、审批、执行和最终业务状态；银行数据接入只负责适配器调用、原始回执、标准化回执和受控回写。自动入账不会创建支付申请。
- 验收标准：
  1. 调用银行前保存出站请求摘要、企业、转账申请、内部请求编号、外部幂等号和操作审计。
  2. 银行 `ACCEPTED`、网络超时、未知结果和等待回执均进入中间状态，如 `SUBMITTED`、`PENDING_CALLBACK` 或 `PENDING_RECONCILIATION`，不得直接变为已付款、已执行或扣减本地余额。
  3. 真实最终回执仅通过标准化回执更新支付尝试、转账申请和交易；更新权限和事务边界由支付域负责。
  4. 自动入账流水、连接查询和回执数据之间只能使用只读外部引用关联，不共享状态机和写权限。
- 依赖：转账申请状态机、E1、E3、E4、E7；待决策项 D3。
- 模拟器可完成：出站摘要、幂等号、接受/拒绝/超时/重复/乱序回执和中间状态。
- 必须等待 SDK/API/沙箱：真实支付提交、银行异步通知、回执查询和最终状态协议。

#### V02-E6-S02 回执重试与未知结果处置

- 优先级：P1
- Story：作为财务经理/运营人员，我希望对超时或未知支付结果执行查询和人工处置，避免重复付款。
- 角色与权限：回执查询由 `bank-callback:query`；人工确认/补单/取消等高风险动作需独立审批权限，v0.2 默认不开放真实补单。
- 验收标准：
  1. 回执查询和支付重试使用不同动作与幂等键；未知结果不得允许直接再次提交原支付。
  2. 重复、乱序、延迟回执按外部幂等号和银行请求号去重，并保留全部到达事件。
  3. 任何人工处置必须记录前后状态、理由、操作者、审批人、请求编号和审计事件。
  4. 模拟环境可以完成流程演练；真实环境在银行沙箱未验证前，所有补单/放款入口禁用。
- 依赖：E6-S01、E3、E7；银行回执协议；待决策项 D3。
- 模拟器可完成：全部流程和风险用例。
- 必须等待 SDK/API/沙箱：真实回执、补单和最终确认规则。

### E7 可观测、对账与端到端验收

#### V02-E7-S01 全链路关联与审计

- 优先级：P0
- Story：作为审计人员，我希望从一个内部请求编号追踪到任务、原始报文、标准化记录、业务对象和审计事件。
- 验收标准：

  2. 链路覆盖创建、开始、原始保存、标准化、去重、业务写入、查询、失败、重试、回执和人工处置。

  4. 审计和业务查询均不能泄露令牌、签名、私钥、完整账号、原始敏感报文或其他企业数据。

- 模拟器可完成：全部链路关联和审计验证。
- 必须等待 SDK/API/沙箱：银行侧请求号/回执号的最终映射确认。

#### V02-E7-S02 对账投影与差异定位

- 优先级：P0
- Story：作为财务人员，我希望比较来源、标准化记录、业务记录、凭证/回执投影的数量和金额，快速定位缺失或重复。
- 验收标准：
  1. 可按企业、账户、批次/任务和时间范围汇总各层笔数、收入/支出金额、成功/失败/重复数。
  2. 缺少原始报文、标准化记录、业务记录、模拟凭证或最终回执时，生成明确差异类型和关联资源。
  3. 对账结果只作为投影和控制信号，不直接修改银行余额、支付状态或自动入账复核结论。
  4. 模拟对账明确标识“模拟”；未接入真实银行时不得声称完成银行余额对账或真实总账对账。
- 依赖：E3、E4、E5、E6；自动入账与支付领域的只读引用。
- 模拟器可完成：全部数据层对账、差异注入和定位。

## 6. 跨域边界与不可做事项

### 6.1 自动入账域

- 接收经标准化、校验和去重的银行流水，进入自动入账待复核、金蝶模拟制证、对账和追溯链路。
- 不发起银行付款、不审批支付、不改本地银行余额、不把银行查询结果自动转为支付申请。
- 不因同步成功跳过财务人工复核；不因模拟凭证成功宣称真实金蝶已入账。

### 6.2 支付/调拨域

- 继续拥有转账/调拨申请、审批、执行和最终业务状态。
- 接收标准化支付回执的受控状态更新，但不接收原始银行响应或银行专有字段。
- 不允许自动入账流水、查询投影或模拟对账直接改变支付/调拨状态。

### 6.3 银行接入域

- 拥有连接档案、同步任务、操作日志、监控、定时/手动触发和只读查询入口。
- 不等同于银行接入层；一期/模拟阶段不得显示真实已连接、真实已同步或真实余额。
- 原始报文只属于受控排障/审计范围，不作为普通连接查询 API 返回。

### 6.4 v0.2 明确不可做

- 不接入真实银行 SDK/API、真实银行文件拉取、真实余额、真实流水、真实回单、真实对账单、真实支付记录或真实代发。
- 不在未完成银行 SDK/API、证书、签名、回执和授权沙箱验收前启用真实适配器。
- 不以模拟器结果、`ACCEPTED`、网络响应 200 或任务成功替代银行最终受理、付款成功、到账或余额变更。
- 不让前端直接访问银行 SDK、原始报文、同步日志、银行专有字段或客户端缓存真实凭据。
- 不允许跨企业读取、写入、重试、导出或推断连接、任务、原始报文、标准化记录、业务记录和回执。
- 不覆盖或物理删除原始事实、标准化记录、业务记录、成功回执和审计事件；修正须新增记录并保留引用。
- 不在查询接口中提供支付、改余额、改流水、生成回单、直接制证、补单或放款动作。
- 不把银行数据接入一期的 30 天原始报文保留直接解释为长期财务档案；到期策略以待决策项 D1 为准。

### D7 已决策并落地（2026-08-31）：syncKey 复用时新请求号的处置

现象：同一企业+账户+连接+Adapter+窗口的同步已完结时，携带新 `X-Request-Id` 的重复请求会直接返回原任务，调用方的新请求号不落库（`requestId` 未记录在任何证据行）。影响：客户端无法用自己的请求号追溯该次调用。

拍板：方案 A（保留幂等语义，不留死数据）。落地行为：
- 复用路径（syncKey 命中与并发撞键两处）当新请求号与原任务请求号不同时，写入一条 `TASK_REUSED` 同步日志：`requestId` 字段为调用方新请求号，消息同时记录原任务号与原请求号。
- `GET /api/bank-data-trace` 按请求号查询时，任务表未命中则回退到企业内的 `TASK_REUSED` 日志解析到原任务——新、旧两个请求号都能串联同一条追溯链；日志查询按企业隔离，跨企业与不存在请求号仍同为 404。
- 运行时证据：`syncKeyReuseKeepsTheCallerRequestIdInTheAuditTrail`（同窗口新请求号返回原任务、双请求号均可追溯、日志含 `TASK_REUSED` 且 requestId 为新请求号），测试基线 `mvn test` 30/30。
