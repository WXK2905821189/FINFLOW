# 字典中心升级方案（2026-09-21）

> 触发：2026-09-21 用户反馈 ——「字典中心大有可为，联动好其他模块，用户使用时就不必都改代码了」。
> 本方案不含实现，只定边界、路线与拍板项。

---

## 0. 一句话结论

字典中心现在的瓶颈**不是功能不够，而是三件事没定**：

1. **边界**：什么该进字典、什么绝不能进（不立规矩就会变成垃圾桶，重演 V30 那次「描述过度承诺」）；
2. **权威**：一个值同时存在于代码 / 字典 / 业务表时，谁说了算；
3. **基建**：取数层（一次写、多层读）、审计（改了要能查）、缓存（别每页打 DB）。

`bank` 已跑通第一个**真消费闭环**（见 §6），可以作为后续所有字典项的样板。

## 2. 先立边界：字典准入四问

任何码表进字典前，必须四问全过：

| # | 问题 | 不过关则 |
|---|---|---|
| Q1 | 这个值会**随业务/运营变化**吗？（改名、增删、排序、上下线） | 不变 → 留在代码常量 |
| Q2 | 它是**我们的口径**，还是**外部系统的协议码**？ | 外部协议码（银行返回 `stscod`/`inttyp`/`loanCode`、金蝶返回码）→ **不进字典**，保留"原文直出 + 兜底不吞" |
| Q3 | 它被**写进业务数据**吗？（表里存了这个 code） | 存了 → 该类型的 `itemCode` 必须**锁定只读**，只能改 label / 排序 / 状态 |
| Q4 | 它是**一张清单**，还是一个**有结构的实体**？（要校验、要版本、要状态流转） | 后者 → 走专用配置表，不进字典（例：凭证规则 V34、AI 提示词 V38、账号偏好 V35） |

> Q2 的原则在 `shared/dict.ts` 文件头已经写明：「银行原生返回代码保持原文直出，不进本字典；未收录的枚举值兜底显示原文，银行新增状态不被吞」。把它提升为**全平台规矩**即可。

## 3. 四种形态（决定页面行为与权限）

| 形态 | 权威源 | 页面行为 | 现有/候选例子 |
|---|---|---|---|
| ① **主数据镜像** | 业务表（字典只读直通） | 只读，改数据去业务页 | `company_entity`（已实现，`DictionaryPage.tsx:79`） |
| ② **配置字典**（字典是唯一源，code 由我们定义） | 字典表 | 全功能增删改；**code 创建后锁定** | `bank`（半②：code 来自银行）；费用类型、金蝶组织映射（候选） |
| ③ **展示映射**（code 来自外部，label 是我们的） | 字典表 | **只能改 label / 排序 / 停用**，code 只读 | 币种中文名、账户状态 A/B/C（候选） |
| ④ **协议码表** | 代码（`shared/dict.ts`） | 不出现在字典中心 | 银行 `stscod`/`inttyp`/`loanCode`/`bankStatusCode` |

**判定唯一关键**：这个 code 是**我们**定的，还是**外部系统**定的？③ 与 ④ 的分界就是"我们需不需要给它一个中文名"——需要（且中文名可能变）→ ③；不需要（原文就是给技术人员看的）→ ④。

## 5. 路线（按"能消灭哪类改代码场景"排序）

### P0 — 可并入当前批次（纯增量，不动表结构、不加迁移）

| # | 项 | 交付物 | 完成标志 | 牵头 |
|---|---|---|---|---|
| P0-1 | **`itemCode` 锁定**：已引用形态（②③）的项，创建后禁止改 code | `DictService.updateItem` 校验 + 前端禁用输入框 | 试图改 `CITIC` → `CITICBANK` 返回 400 且提示「项标识被业务数据引用，不可修改」 | 后端 |
| P0-2 | **字典写审计** 6 事件：`DICT_TYPE_{CREATE,UPDATE,DELETE}` / `DICT_ITEM_{...}` | 复用 `SystemAuditService.record(userId, action, type, objectId, requestId, result, detail)`，detail 记 before/after | 在审计中心能看到「admin 改了 bank 字典：CITIC 中信银行 → 中信银行(总行)」 | 后端 |
| P0-3 | **消费方声明**：字典类型页明确显示"这个字典被谁读" | 前端 `dictConsumers.ts` 登记表（typeCode → 消费模块清单），页面渲染；**不入库**（避免为纯展示加 DDL） | `bank` 类型页显示「消费方：余额查询 / 流水查询 主体树、银行列、筛选下拉、账户档案页」 | 前端 |
| P0-4 | **通用取数层** `useDict(typeCode)` | 从 `useBankNames` 抽出通用版（模块级缓存 + inflight 去重 + `revision` + 订阅），`useBankNames` 改为薄封装 | 第二个字典消费方接入**零拷贝**（不再各写一个 hook） | 前端 |
| P0-5 | **`bank` 字典种子入库** | 新迁移（编号待定，见下）+ `ci.yml` 断言同步 | 全新 H2 / 新环境启动后 `bank` 类型自带 2 条 | 后端 |

> ⚠️ **P0-5 的前置约束（并行会话）**：`V40__ai_voucher_job.sql`、`V41__bank_account_kingdee_mapping.sql` 均**未提交**，`ci.yml` 正被另一会话改 V40 断言。此时新建迁移会**撞号 + 改同一个 yml**。建议：**等 V40/V41 批次落地后再取号（V42）**。在此之前，本次 `bank` 数据只落在**生产库**（2026-09-21 已建，见 §6），新环境靠代码兜底常量显示 —— 不影响使用。

### P1 — 平台化

| # | 项 | 交付物 | 完成标志 | 牵头 |
|---|---|---|---|---|
| P1-1 | **后端字典缓存** | `DictService` 进程内缓存 + 写时失效（单实例；后续多实例加 60s TTL 或 Redis） | 连续 100 次消费调用只打 2 次 SQL；改字典后立即生效（同一请求内可见） | 后端 |
| P1-2 | **币种口径统一到字典（三层一次改）** | 删掉 `kernel.ts` 死代码；前端 + `BankDataExportService` 都改为读字典（后端走缓存） | 屏幕上与 CSV 导出里币种中文名**完全一致**；新增币种零发版 | 全栈 |
| P1-3 | **金蝶组织编码字典化** | 字典类型 `kingdee_org`（`sort_no` = 匹配优先级）+ `KingdeeOrgResolver` 改为读字典（失败退回内置常量） | 新增分公司/主体 → 字典加一条即生效，**不改代码**；顺序语义与现有「分公司先于主公司」一致 | 后端 |
| P1-4 | **`extra_json` 字段 Schema** | 类型级字段定义（键名/显示名/类型/必填），前端**渲染表单**而非 JSON 文本域 | 非技术管理员能维护「税号 / 开户行」而不用手写 JSON | 全栈 |
| P1-5 | **批量导入 / 导出** | 页面支持 CSV 导入（预览 + 冲突报告）与导出 | 20 家银行一次性导入，冲突逐行报错 | 前端 |

### P2 — 治理（有真实需求再做）

- **按类型授权**（HR 只管 HR 字典）：需拆 `system:dict:manage` 为 `system:dict:manage:{typeCode}` 或引入类型级 ACL —— 当字典类型超过 ~8 个且跨部门时才有价值。
- **变更历史与回滚**：P0-2 的审计只记录，回滚需要版本表（成本高，先用审计 + 手工改回）。
- **多语言 label**：当前无海外主体，不做。

## 6. `bank` 首个消费闭环（2026-09-21 已落地）

**已在生产建立**（走应用自身写入路径，享受后端校验与 `created_by` 归属）：

| 项 | 值 |
|---|---|
| 字典类型 | `id=2`，`typeCode=bank`，名称「银行」，状态 ACTIVE |
| 字典项 | `CMB` = 招商银行（sortNo 10）；`CITIC` = 中信银行（sortNo 20） |
| 复验 | `GET /api/system/dicts/bank/items` → 200，2 条，顺序即下拉顺序 |
| 消费方 | `bank-access/useBankNames.ts`：`resolveBankName`（字典优先 → 代码兜底 → 原码）/ `bankAccountLabel`（「银行-尾号」）/ `bankNameOptions`（下拉） |
| 覆盖点 | 6 处：主体树账户节点、网格「银行」列（含导出）、流水/余额详情抽屉、筛选下拉、账户档案页、连通测试标题 |

**上线后的实际收益（准确版）**：

| 场景 | 现在 | 上线后 |
|---|---|---|
| 改银行中文名 | 改 `bankQueryTexts.ts` → 构建 → 发版 | 字典中心改 label，**刷新即生效** |
| 调下拉/列顺序 | 改代码 → 发版 | 改 `sort_no` |
| 某银行暂时下架（不再出现在筛选） | 改代码 → 发版 | 置 `DISABLED`，**历史数据不动** |
| **接入一家新银行** | 写适配器 + 建档案（**仍需代码 + 数据**） | **仍需代码 + 数据**（字典只负责它的显示名） |

> 最后一行是必须说清的一条：字典**不会**让银行凭空可用。取数要适配器（代码）+ 账号档案（数据）。字典消灭的是**改名 / 排序 / 上下线**三类改动。

## 7. 顺带查出的两个既有问题

1. **币种中文名三处定义、内容不一致**（真实漂移，不是理论风险）：
   - `grid/kernel.ts:194`：只有 ISO 5 种（CNY/USD/EUR/HKD/JPY），**且该函数零消费方 = 死代码**；
   - `bankQueryTexts.ts:31`：只有银行码 `10`/`01` + CNY（屏幕渲染实际用这份）；
   - `BankDataExportService.java:56`：只有 `10`（CSV 导出用这份）。
   → 三方都有兜底（未命中显示原码），所以**不会崩**，但同一笔流水在屏幕与导出里可能显示成 `人民币` 与 `10`。建议并入 P1-2 一次性收口。
2. **`updateItem` 允许改 `itemCode`**：`CITIC` 改成别的码后，已存的 `bank_account.bank_code='CITIC'` 就再也匹配不到中文名（静默退化为原码，不报错）。这是 P0-1 要修的根因。

## 附：一句话给非技术同事的解释

> 字典中心 = 界面上那些**下拉选项和中文名的总仓库**。以前要改一个名字得改程序、重新发布；现在有值清单的地方逐步搬进这里，**管理员自己改，改完刷新就生效**。但两类东西永远不放进来：一是银行、金蝶这些**外部系统规定的代码**（它们随时会加新码，放进来会被误改），二是系统自己的**状态流转值**（改了流程就跑不通）。
