# FINFLOW v0.3 模块化架构与迁移方案

> 状态：结构重构基线，保持现有 API、数据库表和业务行为不变；产品收敛于 v0.4 五类银行只读查询。
> 产品范围：工作台、银行接入、流水中心、金蝶入账、对账结账、系统管理。

## 1. 模块边界

| 产品模块 | 后端应用层归属 | 前端归属 | 当前主要能力 |
| --- | --- | --- | --- |
| 工作台 | `workbench` | `modules/workbench` | 采集、复核、入账、差异、结账摘要 |
| 银行接入 | `bankaccess` | `modules/bank-access` | 银行账户、连接、每日采集、补采、任务和状态 |
| 流水中心 | `statementcenter` | `modules/statement-center` | 标准流水、校验异常、重复、人工复核和来源追溯 |
| 金蝶入账 | `kingdee` | `modules/kingdee` | 科目/往来规则、凭证草稿、模拟制证和结果 |
| 对账结账 | `reconciliation` | `modules/reconciliation` | 银行/FINFLOW/金蝶核对、差异和账期结账 |
| 系统管理 | `systemmanagement` | `modules/system-management` | 用户、角色、企业、飞书、审计和系统设置 |

`common`、认证安全、企业范围、RBAC、审计、请求号、分页、异常和数据库配置属于共享基础能力。模块可以依赖共享基础能力，但共享层不得依赖具体业务模块。

主动转账、付款、资金调拨、支付审批、支付执行和银行支付记录查询不属于当前产品。现有 `bank` 包及相关表保留为历史兼容代码，默认关闭、无产品导航、无新功能开发；不得被新模块引用或重新暴露。

## 2. 数据与接口边界

银行接入的数据链路保持单向：

```text
Adapter -> 原始请求/响应与同步日志 -> 统一模型 -> 业务表/查询投影 -> FINFLOW API -> 前端模块
```

前端只调用 FINFLOW API。原始报文、同步日志全文、银行专有字段、凭据和内部堆栈不进入普通页面、浏览器缓存、导出或前端类型定义。

实体、Mapper 和 Flyway 迁移暂时继续集中管理，原因是它们承担跨模块公共数据访问和固定版本顺序。模块应用层只能通过服务或查询接口访问这些持久化对象，后续再按领域逐步迁移。

## 3. 迁移策略

1. 已完成第一步：前端导航、页面标题和菜单持久化状态抽到 `frontend/src/modules/navigation`；原有路由、API 和权限判断保持兼容。
2. 下一步按银行接入、流水中心、金蝶入账、对账结账、系统管理顺序抽取页面组件和后端应用服务；每次只迁移一个领域，保留旧包门面。
3. 页面迁移完成后，再将实体/Mapper 按表归档到模块目录；迁移必须保持表名、列名、索引、企业过滤和 Flyway 顺序不变。
4. 最后清理前端旧组件引用，验证历史 `bank` 接口仍关闭，再执行全量回归。

## 4. 重构验收

- API 路径、请求/响应字段和权限结果不变，旧客户端可继续访问受支持功能。
- 双企业数据、任务、流水、凭证、差异、飞书配置和审计均不交叉可见。
- 原始层先落库，转换/投影失败仍可按 `request_id` 追溯；前端无原始层读取入口。
- 手动/定时银行同步继续共用任务、幂等键、请求号和审计模型。
- 真实银行、金蝶、飞书 SDK/API、证书、生产密钥和外部网络调用保持为 0。
- H2 迁移、后端测试、前端类型检查、生产构建和浏览器关键路径回归全部记录证据。
- 未新增主动转账、付款、资金调拨、支付审批或支付执行入口。

## 5. 当前风险

- 后端核心服务仍有较大的历史类，必须在每次迁移后检查 Spring 注入、MyBatis 扫描和测试夹具。
- 现有权限中仍有历史通用权限名，具体模块权限收敛需单独迁移和验收，不能只改前端文案。
- MySQL 空库、增量、重复启动、备份恢复和多实例调度仍不能用 H2 结果替代。
