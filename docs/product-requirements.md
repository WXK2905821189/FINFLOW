> 版本：v0.5 真实直联阶段版｜更新时间：2026-09-08
> 文档用途：作为产品、研发、测试、实施和资源协调的共同验收依据。
> v0.5 变更摘要：①用户可见模块更新为实际线上导航（工作台 + 银行数据 / 流水与入账 / 系统管理三组）②权限收敛为 33 项编码基线（见 `docs/permission-catalog.md`）③银行采集进入真实直联阶段：CMB CloudDC（SM2/SM4 国密）已上线，CITIC 适配器就绪待白名单 ④新增可配置同步计划、银行流水一键转入、账户多选两级分组、档案管理拖拽归类、原始报文三段式留存/重放/对账核对 ⑤金蝶由模拟网关升级为真实 OpenAPI 对接（演示环境 save→submit→audit 闭环）⑥第 16 章实现状态全面刷新。

## 1. 产品背景

FINFLOW 面向企业财务团队，解决多家银行流水分散、人工下载和整理耗时、校验与入账依赖人工、结账周期长、对账差异难追溯以及协同通知不及时等问题。

本次需求以以下四项目标为唯一业务主线：

1. 实现多银行流水自动采集、数据校验、自动同步和金蝶自动入账，替代流水环节的全量手工操作。
2. 搭建自研财务数据中台，作为原始数据与业务查询之间的中间池，支持未来财务个性化报表和数据分析。
3. 提升结账效率、降低对账差异、强化资金账务合规性。
4. 连接飞书，承载财务任务、异常和审批协同通知。

## 2. 产品定位与范围原则

FINFLOW 是“银行数据采集、财务数据治理、自动入账和协同运营平台”，不是银行支付系统。

### 2.1 本期范围

| 领域 | 本期职责 | 主要结果 |
| --- | --- | --- |
| 银行数据接入 | 通过可插拔 Adapter 采集多银行账户余额、流水及相关财务资料；CMB 走免前置 CloudDC（SM2/SM4 国密）真实直连，CITIC 适配器就绪等待放行 | 统一的采集任务、原始留痕和标准化数据 |
| 财务数据中台 | 原始数据暂存、标准化、去重、质量校验、业务表和查询投影；银行原文 verbatim 留存与清洗规则重放 | 可追溯、可复用、可扩展的财务数据池 |
| 自动入账 | 将符合规则的银行流水转入标准流水并推送至金蝶出纳收付款单，异常进入人工复核 | 入账结果、凭证号、失败原因和追踪链路 |
| 对账与结账 | 银行流水、FINFLOW 业务事实、金蝶凭证进行核对；银行 Z1 合计 vs 平台计数的对账核对 | 差异清单、处理状态和结账汇总 |
| 飞书协同 | 向指定人员或群组发送任务、异常、待复核和对账通知 | 可追踪的协同消息和处理链接 |
| 管理与审计 | 用户、企业、账户、规则、连接、日志和权限管理 | 最小权限、企业隔离和完整审计 |

### 2.2 明确不做

- 不实现主动转账、付款、资金调拨、支付审批、支付执行或银行出款。
- 不在银行数据采集后自动创建付款或调拨指令。
- 不建设银行支付记录查询。后续如有需要，另立银行 SDK 适配需求和独立验收范围。
- 不在本期建设通用 BI、自助低代码报表、总账全量替代、税务申报、发票管理、多币种核算或 SSO/二次认证。

### 2.3 用户可见模块

产品导航按实际线上结构收敛为一个工作台和三个业务模块组（共 18 个业务页面），避免把技术分层和第三方连接拆成过多菜单：

| 导航组 | 用户关注的问题 | 页面 |
| --- | --- | --- |
| 工作台 | 今天哪里需要处理？ | 工作台（待办优先汇总） |
| 银行数据 | 流水是否按计划拿到了？数据可信可溯源吗？ | 账户管理（含档案管理）、余额查询、流水查询、对账核对、同步任务（含同步计划）、运行日志、原始报文 |
| 流水与入账 | 流水如何形成正确凭证？ | 导入流水（含一键转入）、流水批次、人工复核、规则与映射、金蝶制证 |
| 系统管理 | 谁能访问和配置系统？账是否闭环？ | 用户与角色、审计中心、结账管理、对账看板、飞书协同 |

自研数据中台属于后台数据架构，不作为独立一级导航；原始层、标准层、业务层和查询投影层为上述模块提供数据服务。飞书属于“系统管理”下的协同能力，不作为独立业务模块。

## 3. 用户与角色

平台按企业隔离数据。每个用户属于一个企业，所有资源、任务、流水、凭证、日志、飞书配置和报表查询均必须携带企业范围。例外：跨公司银行数据查看（`bankdata:cross-company:view`，授予 ADMIN/FINANCE_MANAGER）允许余额/流水投影可见全部 ACTIVE 公司，行带公司列，用于集团主体查询。

| 角色 | 核心职责 | 典型权限 |
| --- | --- | --- |
| 企业管理员（ADMIN） | 管理本企业用户、账户、规则、连接和飞书配置 | 用户/RBAC、账户、规则、连接配置、日志与全量查询 |
| 财务运营人员（FINANCE_STAFF） | 维护采集任务和处理数据异常 | 触发同步、导入/转入流水、查看流水、处理采集异常 |
| 财务复核人员（FINANCE_MANAGER） | 复核异常和待入账流水 | 流水复核、制证、差异处理；不得复核本人产生的记录 |
| 业务查看者（VIEWER） | 获取授权范围内的财务信息 | 只读查看，不得同步、复核、入账、改规则或改配置 |

### 3.1 权限要求

权限由后端强制执行（`@PreAuthorize` + 路由守卫），前端隐藏菜单不能代替服务端鉴权。**唯一权威清单为 `docs/permission-catalog.md`（现行 33 项）**，命名规范 `<domain>:<resource>:<action>`；新增端点/页面只允许引用目录中的编码，需要新编码时先登记再落代码。

核心编码示例：`bankdata:balance/statement/reconciliation/receipt/payroll:view`（五类投影查看）、`bankdata:sync:trigger`（触发同步）、`bankdata:raw:view`（原始报文，全系统唯一返回完整银行响应体，仅 ADMIN/FINANCE_STAFF）、`bankdata:cross-company:view`（跨公司查看）、`statement:import/review`、`voucher:push`、`closing:manage`、`bank:manage`（含同步计划修改）、`user:manage`、`audit:view`。

权限验收要求：越权请求返回 `401/403`，不泄露资源存在性；跨企业 ID、账户 ID、任务 ID 和流水 ID 均不得读取、修改或推断。同一动作只允许一个编码，别名收敛走 Flyway 迁移，禁止在代码里堆 `hasAnyAuthority` 兜底。

## 4. 登录、注册与账户安全

### 4.1 登录

- 用户使用账号和密码登录，后端验证账号状态、密码和企业归属后签发会话令牌。
- 登录失败统一返回安全提示和请求编号，不暴露“账号不存在/密码错误”等可枚举信息。
- 停用用户不能登录；停用、退出或高风险权限变更应按会话策略撤销既有会话。
- 前端只调用 FINFLOW `/api`，不得在浏览器保存银行密钥、金蝶凭证密钥或飞书应用密钥。
- 登录接口、会话接口和错误响应必须写入脱敏审计。

### 4.2 注册与初始化

- 仅允许受邀用户或企业管理员创建用户；公开注册不得自动获得企业数据权限。
- 首次初始化必须创建企业管理员，并要求首次登录修改初始密码。
- 生产环境禁止使用仓库内默认密码、开发 JWT 密钥和示例连接配置。
- 密码必须单向加密存储，具备复杂度、失败次数限制和管理员停用能力。

## 5. 总体业务链路

固定链路如下：

```text
银行 Adapter（CMB CloudDC 真直连 / CITIC / MOCK）
  -> 原始请求/响应（银行原文 verbatim + 请求要素）与同步日志独立持久化
  -> 统一模型与数据质量校验
  -> 去重、标准化和业务表/查询投影（银行数据模块，只读留存）
  -> 一键转入：银行流水 -> 标准流水（来源 BANKDATA，带银行请求号溯源）
  -> 自动入账规则匹配 / 人工复核
  -> 金蝶出纳收付款单生成/推送
  -> 对账与结账
  -> FINFLOW API
  -> 前端及飞书协同通知
```

前端只消费 FINFLOW API。银行协议、原始报文、内部日志和第三方密钥不得直接暴露给前端或飞书消息。“银行数据”模块是原始凭证留存层（只读、对账、报文溯源），“流水与入账”模块是进入账流程的标准流水，两者通过一键转入打通，断链不允许回归。

## 6. 多银行流水自动采集与每日同步

### 6.1 Adapter 能力

- 每家银行独立实现 Adapter，统一输出账户、余额、流水、回单、对账单等标准化前的内部契约。
- 招商银行走免前置 CloudDC 通道（SM2/SM4 国密），已真实直连上线：余额 Z1 落库、T+1 逐日流水拉取、逐日 requestId 幂等、ctnFlag=Y 续传翻页。
- 中信银行适配器与证据链已就绪，等待银行白名单放行后启用，验证流程与 CMB 相同。
- Adapter 必须支持银行连接标识、企业标识、账户标识、日期窗口、分页/游标、请求号、超时、错误分类和响应摘要。
- 连接配置与密钥引用分离，真实密钥只能由 KMS/密钥管理服务注入，不得进入代码、仓库或前端。
- 未通过银行物料、授权沙箱和安全准入前，真实 Adapter 必须保持未启用或快速失败，不得回退成“成功”。

### 6.2 采集触发

系统默认“按日读取”：每日按企业、账户和 T-1 窗口（昨日全天）读取银行流水。调度由**可配置同步计划**驱动：

- 管理员（`bank:manage`）在同步任务页“同步计划”卡片维护执行时刻（HH:mm 多选，默认种子 02:10 银行低谷期）；后端调度器每分钟心跳，命中计划时刻才发起一轮全账户 T-1 同步。
- 错峰护栏：计划时刻禁止整点/半点（:00/:30），前后端双重校验，避开 CMB 账务查询与支付共享 20 并发的高峰。
- 计划存数据库（`bank_sync_schedule` 表），不依赖环境变量，改时刻无需重启。
- 同步计划对非管理员只读可见，展示时刻 chips 与下次执行倒计时。
- 发生失败、漏采或补数时，授权人员（`bankdata:sync:trigger`）可手动补拉指定日期窗口。手动和定时同步共用同一任务状态机、任务编号、内部请求号、幂等键、权限、并发锁、重试和审计规则；同账户同窗口重复触发幂等复用旧任务，不重复调银行。

任务状态至少包括：`CREATED`、`QUEUED`、`RUNNING`、`PARTIAL_SUCCESS`、`SUCCESS`、`FAILED`、`CANCELLED`、`NEEDS_REVIEW`。

验收标准：

1. 相同企业、账户、数据类型、日期窗口和来源版本生成可判定的幂等键；重复触发不得造成重复业务事实。
2. 同步计划修改即时生效，且只影响后续触发，不产生补跑。
3. 任务详情可查看触发方式、窗口、处理数、重复数、异常数、耗时、请求号和脱敏错误摘要；运行日志页展示真实同步记录（数据源 `/bank-data/sync-logs`）。
4. 分页、断点、重试和乱序数据不丢失、不重复，失败可定位到任务和原始响应。
5. 调度任务不得绕过权限和企业范围；未授权用户不能通过深链或伪造参数触发任务。

## 7. 数据中台与数据治理

### 7.1 分层模型

| 层级 | 内容 | 规则 |
| --- | --- | --- |
| 原始层 | 请求、响应（银行原文 verbatim）、请求要素、接收时间、来源、任务和同步日志 | 先落库；脱敏；默认临时保留 30 天 |
| 标准层 | 银行统一字段（canonical 27 组件承载银行原生字段）、映射版本、状态、金额、方向和来源引用 | 统一格式、可重复处理、保留原始引用 |
| 业务层 | 流水、账户快照、回单、对账单、入账任务和凭证关联 | 企业隔离、组合去重、可追溯 |
| 查询投影层 | 面向列表、对账和未来报表的只读视图（余额/流水/回单/对账单/代发五类） | 只通过 FINFLOW API 提供，支持分页和过滤 |

### 7.2 数据质量规则

- 必填：企业、银行、账户、来源记录 ID、交易时间、金额、币种、收支方向和来源引用。
- 金额使用定点精度，非法金额、空值、非法方向和不支持币种进入异常，不得静默修正。
- 去重优先使用“企业 + 银行 + 账户 + 来源流水号”；缺少稳定流水号时使用经评审的组合键，并标记降级规则。
- 同批、跨批、重复重试和乱序到达均不得生成第二条业务流水或第二次入账机会。
- 原始事实不可由业务页面修改或删除；修正只能通过新版本、冲正或受控更正记录完成。
- 银行原生字段全量承接进标准模型（如招行 NTQADINF 全 20 字段含生命周期 lmtovr/intcod/intrat/mutdat），不把银行专有字段直接扩散到前端。

### 7.3 原始数据留存

当前默认策略：原始请求、响应和同步日志按接收时间临时保留 30 天。30 天后的删除、归档、冷存储、加密备份及争议数据延长留存规则必须由合规、法务、财务和架构共同决策；未决策前不得宣称长期合规。

### 7.4 报文溯源与清洗重放

- 原始报文页提供三段式证据：银行原文 verbatim / 解析视图 / 请求要素（URL + 明文请求体 + 耗时 + HTTP 状态），配合 duration_ms/http_status 形成完整证据链。
- 清洗规则重放：按当前规则重跑银行原文并与存量结果比对，用于字段漂移定位；重放状态必须走与入库同一条归一路径，并还原余额快照与分页合计，否则视为无效重放。
- 对账核对页提供银行 Z1 合计 vs 平台计数的核对视图，差异标红，作为数据完整性的日常检查手段。

## 8. 数据校验、自动入账与金蝶

### 8.1 校验与复核

- 采集完成后先执行格式、字段、账户、金额、方向、日期、重复和业务规则校验。
- 校验结果至少为 `VALID`、`INVALID`、`DUPLICATE`、`PENDING_REVIEW`，每条异常必须有安全的原因码和处理建议。
- 可自动通过的仅限已批准规则；高风险金额、未知对方、规则冲突或关键字段缺失必须人工复核。
- 导入人不能复核本人产生的记录；复核通过、驳回、转人工和重新处理都必须审计。

### 8.2 自动入账

- 只有校验通过且满足入账规则的流水，才可进入待复核或已批准入账队列。
- 未复核、已驳回、重复、非法和来源不可信的流水不得生成凭证。
- 银行数据一键转入：流水查询页行多选 →“转入流水与入账”，按字段映射生成标准流水，来源标记 `BANKDATA` 并带银行请求号溯源；幂等键为同公司同银行流水号，重复转入走 duplicate 统计不产生重复标准流水；已转入行标记“已转入”禁选；权限与导入一致（`statement:import`）。
- FINFLOW 按金蝶标准接口要求组装收付款单数据，落点为出纳模块收付款单（`AR_RECEIVEBILL` / `AP_PAYBILL`），映射企业、账簿、日期、摘要、金额、借贷方向、科目、往来对象、银行账户和来源流水号。
- 往来匹配以已批准规则和主数据为依据；对手方未命中时自动建档（`BD_Supplier`/`BD_Customer`，FNumber 由名称哈希生成保证幂等，重复拒绝视为已存在回查复用），自动审核默认关闭。
- 复核通过后，系统生成收款/付款单并推送金蝶（save→submit→audit）。这里的“付款单”是出纳单据类型，不表示 FINFLOW 发起付款或银行出款。
- 金蝶对接采用官方 SDK 真实网关，三态装配（mock / Unavailable / Real）由条件装配控制：真实凭据未注入时 fail-closed 不装配，不得静默降级为 mock 后仍宣称已入账。
- 金蝶推送必须支持幂等键、请求号、成功、失败、超时和未知结果状态；未知结果不得再次盲目创建单据；回滚路径为 UnAudit→Delete。
- 真实金蝶生产账套接入需完成接口文档评审、测试账套、单据规则、账号权限、网络策略和回执协议验收；演示环境（apiexp）闭环结论仅作为流程验证证据。

### 8.3 关键状态

```text
采集成功 -> 校验中 -> 待复核 -> 复核通过 -> 入账处理中 -> 已入账
                         |             |             |
                         v             v             v
                       已驳回       入账失败       待人工确认
```

每次状态变化记录操作者、时间、企业、对象、前后状态、请求号、原因和关联原始记录。

### 8.4 科目与往来匹配验收

1. 同一流水在规则、账户、交易方向、摘要、对方和金额等条件相同的情况下，匹配结果稳定且可重复。
2. 唯一匹配结果可生成凭证草稿；无匹配、多匹配、规则冲突和主数据缺失不得自动入账。
3. 人工调整必须记录原匹配结果、调整人、调整原因、最终科目/往来和请求号，不能修改原始流水。
4. 规则版本、金蝶接口请求、响应摘要、凭证号和流水号可以双向追溯。

## 9. 对账、结账与合规

- 对账至少支持银行标准流水、FINFLOW 业务流水和金蝶凭证三方核对。
- 对账维度包括企业、银行账户、账期、流水号、日期、金额、方向、凭证号和状态。
- 差异类型至少包括缺流水、重复流水、金额差异、方向差异、日期差异、缺凭证、状态不一致和数据未完成。
- 差异必须进入责任人待办，具备认领、说明、附件/引用、复核、关闭和重新打开能力。
- 结账前必须满足账期内采集任务完成、异常有处置结论、差异有责任人与状态、入账结果可追溯。
- 结账确认后原始流水、标准流水、对账结果和凭证关联不可覆盖；调整通过新增记录完成。
- 对账和结账结果只能表达 FINFLOW 可验证事实，不得把 MOCK 或未确认回执标记为银行最终成功。

## 10. 飞书连接与协同

### 10.1 目标能力

飞书是协同通知和待办触达渠道，不是财务数据主库、银行连接层或入账执行入口。

- 企业管理员配置飞书应用、租户/企业映射、机器人或群组、通知开关和接收角色。
- 采集失败、任务部分成功、流水待复核、金蝶入账失败、对账差异和结账阻断触发飞书通知。
- 通知包含事件类型、企业、任务/批次号、摘要、风险级别、发生时间和 FINFLOW 页面链接；默认不包含完整账号、原始报文、密钥、Token、身份证号或敏感金额明细。
- 消息必须带事件 ID 和请求号，支持幂等发送、失败重试、限流、撤回/失效链接和发送日志查询。
- 飞书消息中的操作链接回到 FINFLOW，经登录和服务端权限校验后才能查看或处理；飞书按钮不得绕过 FINFLOW API。

### 10.2 飞书接入边界

- 当前阶段以 MOCK Webhook/消息网关完成模板、路由、重试、幂等和审计验收；真实飞书应用接入为后续里程碑，当前不阻塞核心业务流。
- 真实飞书应用需要 App ID、App Secret、租户授权、事件订阅、机器人/群组权限、出口网络和安全审核，由实施与安全团队协调提供。
- App Secret、Webhook 签名密钥和访问 Token 只能通过密钥管理服务保存和注入，不得进入代码、数据库明文、前端或日志。
- 飞书不可直接查询银行 Adapter、原始层、同步日志全文或金蝶凭证接口；所有数据访问统一经过 FINFLOW API。

## 11. 页面与 API 需求

### 11.1 信息架构

- 工作台：待办优先布局——待复核数、入账失败数、对账差异数、采集失败数和结账进度；数字来自服务端企业范围汇总，未接入显示 `--`。
- 银行数据：账户管理（档案管理抽屉支持账户拖拽归类到公司主体）、余额查询、流水查询、对账核对、同步任务（含同步计划卡片）、运行日志、原始报文（含重放）。
- 流水与入账：导入流水（JSON 手动导入 + 银行流水一键转入）、流水批次、人工复核、规则与映射、金蝶制证。
- 系统管理：用户与角色、审计中心、结账管理、对账看板、飞书协同。

页面统一采用表格化展示，支持筛选、服务端分页并保持稳定排序。数据中台原始层不在普通用户导航中开放，仅提供受控追溯摘要。

查询与筛选专项要求（2026-09-08 起生效）：

1. 余额/流水查询的账户筛选为**多选**（tag 模式），选项按“公司主体 → 银行”两级分组，支持账号后四位/户名搜索定位；不选账户 = 查询全部可见账户。
2. 跨公司用户（`bankdata:cross-company:view`）的账户列表返回全部 ACTIVE 公司账户，行带公司归属列。
3. 流水查询支持行多选 +“转入流水与入账”，已转入行禁选并显示标记。
4. 筛选即选即查（服务端实时生效），筛选条件之间为 AND 关系；页面打开、刷新、轮询不得触发银行同步。

### 11.1.1 界面交互与查询规范

- 查询页面采用“草稿筛选 → 点击查询 → 服务端分页结果”的模式；账户、日期范围、状态、来源/通道、关键字和任务/请求编号按页面能力组合使用，默认按业务时间倒序、主键倒序稳定排序。
- 银行数据查询只调用 FINFLOW 自有 API，读取服务端企业、账户和角色过滤后的统一业务模型或查询投影。前端不得直连银行 SDK/API、金蝶或飞书，不得读取或缓存原始请求/响应全文、同步日志全文、银行专有字段、凭据、令牌、私钥、完整账号或内部堆栈（`bankdata:raw:view` 页面按权限展示银行原文，属受控例外）。
- 余额、流水、回单、对账单和代发五类查询统一支持服务端分页、明确来源、末次同步时间及任务号/请求号追溯。未启用真实银行直联的通道持续显示“真实银行直联未启用”；模拟或样例结果必须标记“模拟数据”，余额未获取显示 `--`，不得以 `0.00` 或“成功”制造虚假事实。
- 任务执行采用服务端统一的定时/手动任务事实、幂等键和请求号。手动补拉先选择企业内授权账户和日期范围，再确认影响与去重规则，成功仅表示任务创建，不表示数据已更新；重复请求复用已有任务，页面离开不取消后台任务。
- 任务、日志和流水详情使用右侧抽屉，至少包含概览、关联对象、状态时间线/审计和安全追溯摘要；关闭后保留筛选、分页、滚动位置并恢复触发元素焦点。任务号、流水号和请求号支持复制。
- 状态必须同时使用文字、图标和颜色。统一区分加载骨架、未启用/未配置、当前筛选无数据和查询失败；失败保留上次成功结果并提供局部重试。未知或待确认的银行状态不得在前端折叠为成功，异步回执只有在服务端标准化及对账确认后才能展示最终成功。
- 桌面端保持高密度表格；移动端将三级导航与筛选放入抽屉，详情改为单列，操作目标不小于 `44px`，长编号和错误摘要不得溢出或互相遮挡。
- CSV 导出需对齐银行导出件列序（BOM + CRLF + 防注入），前端 blob 下载经统一拦截器放行。

### 11.2 API 约束

- API 统一以企业和用户权限为边界，列表服务端分页、过滤和稳定排序。
- 所有写操作返回业务结果、状态、请求号和可安全展示的错误摘要。
- API 不返回原始报文全文（raw:view 受控例外）、第三方密钥、银行专有未治理字段或内部堆栈。
- API 至少覆盖：登录/当前用户、账户、同步任务、同步计划、流水/标准化数据、转入、校验异常、复核、金蝶制证、对账、原始报文、运行日志、飞书配置和审计查询。
- 前端只能请求 FINFLOW API；不能直连银行地址、金蝶地址、飞书地址或数据库。

## 12. 非功能与合规要求

- 企业隔离：所有业务表、查询投影、缓存、任务、日志、审计和飞书事件均带企业范围；跨公司查看仅限显式授权权限。
- 幂等与一致性：同步、标准化、转入、入账、通知和重试使用稳定幂等键；数据库唯一约束为最终防线。
- 可观测性：任务、阶段、请求号、耗时、结果、失败原因和重试次数可查询，告警不含敏感数据。
- 安全：生产凭据由 KMS/密钥管理服务注入；日志、导出、浏览器存储和错误页均不得泄露敏感信息；CMB 通道全程 SM2/SM4 国密。
- 性能目标：常规列表首屏接口 P95 不高于 2 秒；单任务处理量、并发量和历史报表容量需在部署前按实际业务量压测确认。
- 可恢复性：任务失败可重试或人工接管；数据库需有备份、恢复验证和发布回滚方案（每次换 jar 部署前自动备份线上 jar + web-dist）。
- 审计：登录、权限拒绝、连接变更、同步、原始落库、校验、复核、转入、入账、对账、飞书发送和结账均追加记录，审计记录不可由业务用户修改或删除。

## 17. 银行 Adapter 统一聚合层（当前研发基线）

银行接入采用“FINFLOW 业务模块 -> 统一 API 聚合层 -> 银行 Adapter -> 银行接口”的分层方式。聚合层是轻量的北向统一契约和南向 Adapter 编排层，不建设独立低代码平台，也不承载支付、转账或调拨。

- 聚合层统一提供余额、流水、回单、对账单和同步查询/任务 API，定义统一请求、响应、分页、日期窗口及 `SUCCESS`、`FAILED`、`PENDING`、`TIMEOUT`、`UNKNOWN`、`EMPTY`、`DUPLICATE`、`PARTIAL` 状态。
- 聚合层按银行/账户编码路由（显式 adapterCode → connection profile → 账户 bankCode，全 miss 返回 400），集中完成字段清洗、分页语义转换、错误码和状态映射；银行专有字段不得扩散到自动入账、对账或前端。
- 数据链路固定为：Adapter -> 原始请求/响应及同步日志（先落库，银行原文 verbatim）-> 统一模型 -> 业务表/查询投影 -> FINFLOW API -> 前端。任务号、请求号、银行请求号、原始摘要和映射版本必须可追溯。
- 当前 Adapter 清单：CMB CloudDC（真实直连，SM2/SM4 国密，已上线）、CITIC（真实适配器，待白名单）、MOCK（测试与回归用）。真实调用开关由服务端统一控制，未装配真实凭据时 fail-closed 快速失败，不得回退成“成功”。
- 前端、自动入账和对账模块只依赖 FINFLOW API，不直接调用具体 Adapter、银行 SDK/API 或读取原始报文全文。
