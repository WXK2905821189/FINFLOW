# FINFLOW 最新产品需求文档（PRD）

> 版本：v0.4 产品收敛版｜更新时间：2026-08-31
> 文档用途：作为产品、研发、测试、实施和资源协调的共同验收依据。

## 1. 产品背景

FINFLOW 面向企业财务团队，解决多家银行流水分散、人工下载和整理耗时、校验与入账依赖人工、结账周期长、对账差异难追溯以及协同通知不及时等问题。

本次需求以以下四项目标为唯一业务主线：

1. 实现多银行流水自动采集、数据校验、自动同步和金蝶自动入账，替代流水环节的全量手工操作。
2. 搭建自研财务数据中台，作为原始数据与业务查询之间的中间池，支持未来财务个性化报表和数据分析。
3. 提升结账效率、降低对账差异、强化资金账务合规性。
4. 连接飞书，承载财务任务、异常和审批协同通知。

## 2. 产品定位与范围原则

FINFLOW 是“银行数据采集、财务数据治理、自动入账和协同运营平台”，不是银行支付系统。

### 2.1 本期范围

| 领域 | 本期职责 | 主要结果 |
| --- | --- | --- |
| 银行数据接入 | 通过可插拔 Adapter 采集多银行账户余额、流水及相关财务资料 | 统一的采集任务、原始留痕和标准化数据 |
| 财务数据中台 | 原始数据暂存、标准化、去重、质量校验、业务表和查询投影 | 可追溯、可复用、可扩展的财务数据池 |
| 自动入账 | 将符合规则的银行流水推送至金蝶，异常进入人工复核 | 入账结果、凭证号、失败原因和追踪链路 |
| 对账与结账 | 银行流水、FINFLOW 业务事实、金蝶凭证进行核对 | 差异清单、处理状态和结账汇总 |
| 飞书协同 | 向指定人员或群组发送任务、异常、待复核和对账通知 | 可追踪的协同消息和处理链接 |
| 管理与审计 | 用户、企业、账户、规则、连接、日志和权限管理 | 最小权限、企业隔离和完整审计 |

### 2.2 明确不做

- 不实现主动转账、付款、资金调拨、支付审批、支付执行或银行出款。
- 不在银行数据采集后自动创建付款或调拨指令。
- 当前版本不建设银行支付记录查询。后续如有需要，另立银行 SDK 适配需求和独立验收范围。
- 一期不接入真实银行 SDK/API、生产证书、生产密钥或生产银行数据；真实银行调用次数必须为 0。
- 一期金蝶使用模拟网关或受控测试接口，不能将模拟凭证表述为真实金蝶入账。
- 不在本期建设通用 BI、自助低代码报表、总账全量替代、税务申报、发票管理、多币种核算或 SSO/二次认证。

### 2.3 用户可见模块

产品导航按财务工作流收敛为六个业务模块，避免把技术分层和第三方连接拆成过多菜单：

| 模块 | 用户关注的问题 | 主要功能 |
| --- | --- | --- |
| 工作台 | 今天哪里需要处理？ | 采集情况、待复核、入账失败、对账差异、结账进度 |
| 银行接入 | 流水是否按计划拿到了？ | 银行/账户、每日定时采集、手动补采、任务、状态和失败日志 |
| 流水中心 | 流水是否可信、完整、可复核？ | 标准流水、校验异常、重复识别、人工复核、来源追溯 |
| 金蝶入账 | 流水如何形成正确凭证？ | 科目/往来匹配、待入账、凭证生成、入账结果和失败重试 |
| 对账结账 | 本期账是否闭环？ | 银行/FINFLOW/金蝶对账、差异处理、账期确认和结账记录 |
| 系统管理 | 谁能访问和配置系统？ | 用户、角色、企业、银行连接、飞书协同、审计和系统设置 |

自研数据中台属于后台数据架构，不作为独立一级导航；原始层、标准层、业务层和查询投影层为上述模块提供数据服务。飞书属于“系统管理/集成配置”下的协同能力，不作为独立业务模块。

## 3. 用户与角色

平台按企业隔离数据。每个用户属于一个企业，所有资源、任务、流水、凭证、日志、飞书配置和报表查询均必须携带企业范围。

| 角色 | 核心职责 | 典型权限 |
| --- | --- | --- |
| 企业管理员 | 管理本企业用户、账户、规则、连接和飞书配置 | 用户/RBAC、账户、规则、连接配置、日志与全量查询 |
| 财务运营人员 | 维护采集任务和处理数据异常 | 发起/重试同步、查看流水、处理采集异常、查看对账 |
| 财务复核人员 | 复核异常和待入账流水 | 校验复核、入账确认/驳回、差异处理；不得复核本人产生的记录 |
| 财务负责人 | 对入账、对账和结账结果负责 | 查看全量财务结果、确认结账、查看审计；不直接修改原始数据 |
| 业务查看者 | 获取授权范围内的财务信息 | 只读查看，不得同步、复核、入账、改规则或改配置 |
| 系统运维人员 | 维护运行环境和任务可观测性 | 查看脱敏运行状态和技术日志；默认不查看业务明细和凭证敏感字段 |

### 3.1 权限要求

权限必须由后端强制执行，前端隐藏菜单不能代替服务端鉴权。建议权限标识：

| 权限 | 说明 |
| --- | --- |
| `user:manage` | 用户、角色和启停管理 |
| `account:manage` / `account:view` | 银行账户配置和查看 |
| `connection:manage` / `connection:view` | 银行 Adapter、飞书连接和连接状态 |
| `sync:trigger` / `sync:retry` / `sync:view` | 同步任务触发、重试和查看 |
| `statement:view` / `statement:review` | 流水查看和人工复核 |
| `validation:manage` | 校验规则和映射版本管理 |
| `validation:view` | 查看校验规则和入账映射 |
| `posting:confirm` / `posting:retry` | 金蝶入账确认和失败重试 |
| `reconciliation:manage` / `reconciliation:view` | 对账处理和结果查看 |
| `closing:manage` / `closing:view` | 账期检查、结账确认和只读查看 |
| `report:view` / `report:manage` | 查询投影和个性化报表 |
| `feishu:manage` / `feishu:view` | 飞书应用、群组和通知策略管理 |
| `audit:view` | 脱敏审计查询 |

权限验收要求：越权请求返回 `401/403`，不泄露资源存在性；跨企业 ID、账户 ID、任务 ID 和流水 ID 均不得读取、修改或推断。

## 4. 登录、注册与账户安全

### 4.1 登录

- 用户使用账号和密码登录，后端验证账号状态、密码和企业归属后签发会话令牌。
- 登录失败统一返回安全提示和请求编号，不暴露“账号不存在/密码错误”等可枚举信息。
- 停用用户不能登录；停用、退出或高风险权限变更应按会话策略撤销既有会话。
- 前端只调用 FINFLOW `/api`，不得在浏览器保存银行密钥、金蝶凭证密钥或飞书应用密钥。
- 登录接口、会话接口和错误响应必须写入脱敏审计。

### 4.2 注册与初始化

- 仅允许受邀用户或企业管理员创建用户；公开注册不得自动获得企业数据权限。
- 首次初始化必须创建企业管理员，并要求首次登录修改初始密码。
- 生产环境禁止使用仓库内默认密码、开发 JWT 密钥和示例连接配置。
- 密码必须单向加密存储，具备复杂度、失败次数限制和管理员停用能力。

## 5. 总体业务链路

固定链路如下：

```text
银行 Adapter
  -> 原始请求/响应与同步日志独立持久化
  -> 统一模型与数据质量校验
  -> 去重、标准化和业务表/查询投影
  -> 自动入账规则匹配
  -> 人工复核或异常处理
  -> 金蝶凭证生成/入账
  -> 对账与结账
  -> FINFLOW API
  -> 前端及飞书协同通知
```

前端只消费 FINFLOW API。银行协议、原始报文、内部日志和第三方密钥不得直接暴露给前端或飞书消息。

## 6. 多银行流水自动采集与每日同步

### 6.1 Adapter 能力

- 每家银行独立实现 Adapter，统一输出账户、余额、流水、回单、对账单等标准化前的内部契约。
- Adapter 必须支持银行连接标识、企业标识、账户标识、日期窗口、分页/游标、请求号、超时、错误分类和响应摘要。
- 连接配置与密钥引用分离，真实密钥只能由 KMS/密钥管理服务注入。
- 一期通过 MOCK Adapter 验证多银行差异、分页、重复、乱序、空结果、超时和失败恢复。
- 未通过银行物料、授权沙箱和安全准入前，真实 Adapter 必须保持未启用或快速失败，不得回退成“成功”。

### 6.2 采集触发

系统以“按日读取”为默认运行模式：每日按企业、账户和账期读取银行流水；发生失败、漏采或补数时，授权人员可手动补采指定日期窗口。手动和定时同步必须共用同一任务状态机、任务编号、内部请求号、幂等键、权限、并发锁、重试和审计规则。

任务状态至少包括：`CREATED`、`QUEUED`、`RUNNING`、`PARTIAL_SUCCESS`、`SUCCESS`、`FAILED`、`CANCELLED`、`NEEDS_REVIEW`。

验收标准：

1. 相同企业、账户、数据类型、日期窗口和来源版本生成可判定的幂等键；重复触发不得造成重复业务事实。
2. 任务详情可查看触发方式、窗口、处理数、重复数、异常数、耗时、请求号和脱敏错误摘要。
3. 分页、断点、重试和乱序数据不丢失、不重复，失败可定位到任务和原始响应。
4. 调度任务不得绕过权限和企业范围；未授权用户不能通过深链或伪造参数触发任务。
5. 默认每日任务具备成功、部分成功、失败和未执行状态；漏采日期可以被识别并进入补采队列。

## 7. 数据中台与数据治理

### 7.1 分层模型

| 层级 | 内容 | 规则 |
| --- | --- | --- |
| 原始层 | 请求、响应、接收时间、来源、任务和同步日志 | 先落库；脱敏；默认临时保留 30 天 |
| 标准层 | 银行统一字段、映射版本、状态、金额、方向和来源引用 | 统一格式、可重复处理、保留原始引用 |
| 业务层 | 流水、账户快照、回单、对账单、入账任务和凭证关联 | 企业隔离、组合去重、可追溯 |
| 查询投影层 | 面向列表、结账、对账和未来报表的只读视图 | 只通过 FINFLOW API 提供，支持分页和过滤 |

### 7.2 数据质量规则

- 必填：企业、银行、账户、来源记录 ID、交易时间、金额、币种、收支方向和来源引用。
- 金额使用定点精度，非法金额、空值、非法方向和不支持币种进入异常，不得静默修正。
- 去重优先使用“企业 + 银行 + 账户 + 来源流水号”；缺少稳定流水号时使用经评审的组合键，并标记降级规则。
- 同批、跨批、重复重试和乱序到达均不得生成第二条业务流水或第二次入账机会。
- 原始事实不可由业务页面修改或删除；修正只能通过新版本、冲正或受控更正记录完成。
- 数据模型必须预留未来报表扩展字段、标签、维度和映射版本，不能把银行专有字段直接扩散到前端。

### 7.3 原始数据留存

当前默认策略：原始请求、响应和同步日志按接收时间临时保留 30 天。30 天后的删除、归档、冷存储、加密备份及争议数据延长留存规则必须由合规、法务、财务和架构共同决策；未决策前不得宣称长期合规。

## 8. 数据校验、自动入账与金蝶

### 8.1 校验与复核

- 采集完成后先执行格式、字段、账户、金额、方向、日期、重复和业务规则校验。
- 校验结果至少为 `VALID`、`INVALID`、`DUPLICATE`、`PENDING_REVIEW`，每条异常必须有安全的原因码和处理建议。
- 可自动通过的仅限已批准规则；高风险金额、未知对方、规则冲突或关键字段缺失必须人工复核。
- 导入人不能复核本人产生的记录；复核通过、驳回、转人工和重新处理都必须审计。

### 8.2 自动入账

- 只有校验通过且满足入账规则的流水，才可进入待复核或已批准入账队列。
- 未复核、已驳回、重复、非法和来源不可信的流水不得生成凭证。
- FINFLOW 按金蝶标准接口要求组装凭证数据，映射企业、账簿、日期、摘要、金额、借贷方向、科目、往来对象、银行账户和来源流水号。
- 金蝶出纳模块的科目/往来匹配以已批准的规则和主数据为依据；匹配成功可自动生成待复核凭证草稿，匹配失败、多个候选或主数据缺失必须转人工处理。
- 复核通过后，系统可生成收款凭证或付款凭证并推送金蝶。这里的“付款凭证”是会计凭证类型，不表示 FINFLOW 发起付款或银行出款。
- 金蝶推送必须支持幂等键、请求号、成功、失败、超时和未知结果状态；未知结果不得再次盲目创建凭证。
- 当前使用金蝶模拟网关验证凭证号、状态、失败重试、重复点击和追溯，不代表真实金蝶系统已入账。
- 真实金蝶接口接入需另行提供接口文档、测试账套、凭证规则、账号权限、网络策略和回执协议，并单独验收。

### 8.3 关键状态

```text
采集成功 -> 校验中 -> 待复核 -> 复核通过 -> 入账处理中 -> 已入账
                         |             |             |
                         v             v             v
                       已驳回       入账失败       待人工确认
```

每次状态变化记录操作者、时间、企业、对象、前后状态、请求号、原因和关联原始记录。

### 8.4 科目与往来匹配验收

1. 同一流水在规则、账户、交易方向、摘要、对方和金额等条件相同的情况下，匹配结果稳定且可重复。
2. 唯一匹配结果可生成凭证草稿；无匹配、多匹配、规则冲突和主数据缺失不得自动入账。
3. 人工调整必须记录原匹配结果、调整人、调整原因、最终科目/往来和请求号，不能修改原始流水。
4. 规则版本、金蝶接口请求、响应摘要、凭证号和流水号可以双向追溯。

## 9. 对账、结账与合规

- 对账至少支持银行标准流水、FINFLOW 业务流水和金蝶凭证三方核对。
- 对账维度包括企业、银行账户、账期、流水号、日期、金额、方向、凭证号和状态。
- 差异类型至少包括缺流水、重复流水、金额差异、方向差异、日期差异、缺凭证、状态不一致和数据未完成。
- 差异必须进入责任人待办，具备认领、说明、附件/引用、复核、关闭和重新打开能力。
- 结账前必须满足账期内采集任务完成、异常有处置结论、差异有责任人与状态、入账结果可追溯。
- 结账确认后原始流水、标准流水、对账结果和凭证关联不可覆盖；调整通过新增记录完成。
- 对账和结账结果只能表达 FINFLOW 可验证事实，不得把 MOCK 或未确认回执标记为银行最终成功。

## 10. 飞书连接与协同

### 10.1 目标能力

飞书是协同通知和待办触达渠道，不是财务数据主库、银行连接层或入账执行入口。

- 企业管理员配置飞书应用、租户/企业映射、机器人或群组、通知开关和接收角色。
- 采集失败、任务部分成功、流水待复核、金蝶入账失败、对账差异和结账阻断触发飞书通知。
- 通知包含事件类型、企业、任务/批次号、摘要、风险级别、发生时间和 FINFLOW 页面链接；默认不包含完整账号、原始报文、密钥、Token、身份证号或敏感金额明细。
- 消息必须带事件 ID 和请求号，支持幂等发送、失败重试、限流、撤回/失效链接和发送日志查询。
- 飞书消息中的操作链接回到 FINFLOW，经登录和服务端权限校验后才能查看或处理；飞书按钮不得绕过 FINFLOW API。

### 10.2 飞书接入边界

- 当前阶段可用 MOCK Webhook/消息网关完成模板、路由、重试、幂等和审计验收。
- 真实飞书应用需要 App ID、App Secret、租户授权、事件订阅、机器人/群组权限、出口网络和安全审核，由实施与安全团队协调提供。
- App Secret、Webhook 签名密钥和访问 Token 只能通过密钥管理服务保存和注入，不得进入代码、数据库明文、前端或日志。
- 飞书不可直接查询银行 Adapter、原始层、同步日志全文或金蝶凭证接口；所有数据访问统一经过 FINFLOW API。

## 11. 页面与 API 需求

### 11.1 信息架构

- 工作台：采集成功率、待复核数、入账失败数、对账差异数、结账进度和最近任务。
- 银行接入：银行连接、银行账户、每日采集计划、手动补采、采集任务、连接状态和失败日志。
- 流水中心：标准流水、校验异常、重复数据、人工复核和来源追溯；按主体、账户、币种和账期筛选。
- 金蝶入账：科目/往来规则、待入账流水、凭证草稿、收/付款凭证、入账结果和失败重试。
- 对账结账：银行/FINFLOW/金蝶三方核对、差异处理、账期确认和结账追溯。
- 系统管理：用户、角色、企业、银行连接、飞书配置、审计和系统设置。

页面统一采用表格化展示，支持按主体、银行账户、币种、账期、状态和关键字组合筛选，服务端分页并保持稳定排序。数据中台原始层不在普通用户导航中开放，仅提供受控追溯摘要。

### 11.1.1 界面交互与查询规范

- 工作台采用“待办优先”布局，优先展示待复核、入账失败/异常、对账阻断和采集失败等需要处理的数量，再展示采集、复核、制证和结账进度。所有数字必须来自当前企业的服务端汇总；接口未接入或失败时显示 `--`、未获取或安全失败状态，不使用本地演示金额补齐。
- 银行接入、流水中心、金蝶入账和对账结账按独立业务模块组织；本期不建设主动转账、付款、调拨、支付审批、支付执行或银行支付记录查询。任何后续支付相关需求都必须另立银行 SDK 适配和独立验收范围。
- 查询页面采用“草稿筛选 → 点击查询 → 服务端分页结果”的模式。账户、日期范围、状态、来源/通道、关键字和任务/请求编号按页面能力组合使用；筛选条件之间为服务端 AND 关系，默认按业务时间倒序、主键倒序稳定排序。页面打开、刷新、轮询和打开详情均不得触发银行同步或拉取全量数据。
- 银行数据查询只调用 FINFLOW 自有 API，读取服务端企业、账户和角色过滤后的统一业务模型或查询投影。前端不得直连银行 SDK/API、金蝶或飞书，不得读取或缓存原始请求/响应、同步日志全文、银行专有字段、凭据、令牌、私钥、完整账号或内部堆栈。
- 余额、流水、回单、对账单和代发五类查询统一支持服务端分页、明确来源、末次同步时间及任务号/请求号追溯。未启用真实银行直联时持续显示“真实银行直联未启用”；模拟或样例结果必须标记“模拟数据”，余额未获取显示 `--`，不得以 `0.00` 或“成功”制造虚假事实。
- 任务执行采用服务端统一的定时/手动任务事实、幂等键和请求号。手动补采先选择企业内授权账户和日期范围，再确认影响与去重规则，成功仅表示任务创建，不表示数据已更新；重复请求复用已有任务，页面离开不取消后台任务。
- 任务、日志和流水详情使用右侧抽屉，至少包含概览、关联对象、状态时间线/审计和安全追溯摘要；关闭后保留筛选、分页、滚动位置并恢复触发元素焦点。任务号、流水号和请求号支持复制，日志查询默认最近 24 小时且失败时保留筛选和请求号。
- 状态必须同时使用文字、图标和颜色。统一区分加载骨架、未启用/未配置、当前筛选无数据和查询失败；失败保留上次成功结果并提供局部重试。未知或待确认的银行状态不得在前端折叠为成功，异步回执只有在服务端标准化及对账确认后才能展示最终成功。
- 桌面端保持 `24px` 内容边距和高密度表格；移动端将三级导航与筛选放入抽屉，详情改为单列，关键字段保留时间、状态、金额、关联号和任务/请求号，操作目标不小于 `44px`，长编号和错误摘要不得溢出或互相遮挡。

### 11.2 API 约束

- API 统一以企业和用户权限为边界，列表服务端分页、过滤和稳定排序。
- 所有写操作返回业务结果、状态、请求号和可安全展示的错误摘要。
- API 不返回原始报文全文、第三方密钥、银行专有未治理字段或内部堆栈。
- API 至少覆盖：登录/当前用户、账户、同步任务、流水/标准化数据、校验异常、复核、入账、凭证、对账、飞书配置和审计查询。
- 前端只能请求 FINFLOW API；不能直连银行地址、金蝶地址、飞书地址或数据库。

## 12. 非功能与合规要求

- 企业隔离：所有业务表、查询投影、缓存、任务、日志、审计和飞书事件均带企业范围。
- 幂等与一致性：同步、标准化、入账、通知和重试使用稳定幂等键；数据库唯一约束为最终防线。
- 可观测性：任务、阶段、请求号、耗时、结果、失败原因和重试次数可查询，告警不含敏感数据。
- 安全：生产凭据由 KMS/密钥管理服务注入；日志、导出、浏览器存储和错误页均不得泄露敏感信息。
- 性能目标：常规列表首屏接口 P95 不高于 2 秒；单任务处理量、并发量和历史报表容量需在部署前按实际业务量压测确认。
- 可恢复性：任务失败可重试或人工接管；数据库需有备份、恢复验证和发布回滚方案。
- 审计：登录、权限拒绝、连接变更、同步、原始落库、校验、复核、入账、对账、飞书发送和结账均追加记录，审计记录不可由业务用户修改或删除。

## 13. 版本与验收标准

### 13.1 MVP/模拟验收

在不调用真实银行和真实金蝶的前提下，必须完成：

1. 至少两家 MOCK 银行 Adapter 使用统一契约完成每日定时采集和授权手动补采。
2. 原始请求/响应与同步日志先落库；标准化、校验或业务写入失败时仍可追溯原始引用。
3. 日期窗口、分页、重复、乱序、空结果、超时、部分成功和未知状态均有可复核结果。
4. 双企业、不同角色、深链和伪造 ID 的访问均通过服务端隔离和 RBAC 验收。
5. 流水完成校验、科目/往来匹配、人工复核、收/付款凭证模拟生成、失败重试、对账和全链路追溯；不产生任何支付/转账/调拨对象。
6. 30 天原始数据保留规则可验证，清理/归档动作和审计状态清晰标注；长期策略仍显示待决策。
7. 飞书 MOCK 通知覆盖任务失败、待复核、入账失败、对账差异和结账阻断，验证模板、幂等、重试和脱敏。
8. 前端所有业务请求只指向 FINFLOW API，真实银行调用次数为 0。

### 13.2 生产/真实接口准入验收

真实银行或金蝶上线前必须另行完成：接口/SDK 资料评审、字段映射、证书与密钥管理、网络白名单、授权沙箱、错误码与回执、限流、幂等、备份恢复、渗透/安全扫描、生产灰度和责任人签字。飞书真实应用同样需完成租户授权、安全审核和敏感信息检查。

未有测试证据的能力只能标记为“待验证”；MOCK 通过只能标记为“MOCK 已验证”，不得写成真实银行或真实金蝶已接入。

## 15. 待决策项

- 原始数据 30 天到期后是删除、归档、冷存储还是分级保留，争议数据如何延长。
- 多银行同步频率、默认日期窗口、时区、最大跨度、重试次数和限流策略。
- 每类银行流水的稳定主键、金额/方向/余额口径和去重降级规则。
- 自动入账规则的责任人、金额阈值、复核层级、凭证模板和失败补偿方式。
- 金蝶标准接口版本、科目/往来主数据来源、匹配优先级、收/付款凭证模板和人工调整边界。
- 对账差异的责任归属、关闭条件、结账时间点和逾期升级机制。
- 飞书通知范围、群组与个人接收规则、静默时段、消息保留和失败升级策略。
- 测试阶段是否允许使用真实业务数据；如允许，需明确脱敏、授权、隔离、留存和回收责任。
- 生产服务器规格、数据库规格、可用性目标、备份周期、恢复目标和预算。

## 16. 当前实现状态说明

当前仓库已有登录/RBAC、银行数据 MOCK 底座、自动入账部分流程和前后端页面基础，但文档中的完整多银行每日采集、金蝶标准接口自动入账、科目/往来智能匹配、飞书真实连接和生产级部署仍不能视为已完成。发布判断必须以对应 API、数据库、端到端、安全和运维证据为准。

本 PRD 发布后，后续研发任务应以本文件为准；原有“转账/支付/调拨”需求不再属于 FINFLOW 产品范围，相关旧页面或代码如需下线，应由研发另立技术清理任务，不在本 PRD 中默认为已删除。
