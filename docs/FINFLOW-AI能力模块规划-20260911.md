# FINFLOW AI 能力模块规划

- **日期**：2026-09-11
- **状态**：待拍板（文末 D1~D3 决策点）
- **基线**：master `4dde312`（Spring Boot 3 + JDK17 / React 18 / Flyway V23 / RBAC 33 项 / 公司隔离）

---

## 一、背景与现状

系统是**数据密集型财务平台**：银行流水/余额（canonical 27 组件 + vendor 双轨）、报文证据链（真原文 + 请求要素）、金蝶凭证推送（收付款单）、对账勾稽、结账期间。当前所有"智能"环节都是**纯规则**：

| 环节 | 现状 | 痛点 |
|---|---|---|
| 流水→科目映射 | `AccountingMapping` 关键词匹配（counterpartyKeyword → 借/贷科目） | 新对手方/新摘要无映射时断链，靠人工建规则 |
| 数据查询 | 固定查询页 + CSV 导出 | 临时性分析要导出后自己算 |
| 对账差异 | Z1 vs 平台计数标红 | 差异原因靠人翻报文 |
| 报文排障 | 证据链三段式展示 | 错误码/语义要懂各行规范才能读 |
| 经营洞察 | 无 | 无汇总性结论输出 |

**本系统做 AI 的独特优势**：数据结构化程度极高（36 列 + 血缘）、权限模型完备（RBAC + 公司隔离 + 全量审计）、关键写路径（入账/推凭证）已有人工确认关卡——AI 可以安全地做"建议者"，不需要碰"执行者"。

## 二、目标与设计原则

1. **AI 只建议，不执行**：任何落库动作（科目映射保存、入账、推金蝶）仍走既有权限 + 人工确认；AI 输出一律标记为建议。
2. **权限继承**：AI 查数工具以当前用户身份执行（复用 `CompanyScopeService` + 现有 `bankdata:*` 权限），AI 永不比人看得多。
3. **数据最小化**：送 LLM 前脱敏（账号掩码沿用 `accountMasked`）、限量分页、只送场景所需字段；对手方名称等业务字段按 D3 拍板口径决定是否出域。
4. **全量审计**：新增 `ai_call_log` 表——谁、什么能力、送了什么（哈希+脱敏摘要）、返回什么、耗时/token/费用。
5. **成本优先**：不引入重型框架（不上 Spring AI 全家桶），自建轻量 `LlmGateway`（OpenAI 兼容 HTTP 协议，兼容 DeepSeek/通义/本地 vLLM，换供应商只改配置）；按能力独立开关，默认全关。

## 三、AI 能力清单与优先级

| # | 能力 | 场景 | 价值 | 成本 | 优先级 |
|---|---|---|---|---|---|
| A1 | **智能入账建议** | 流水审核页：映射未命中时，AI 基于摘要+对手方+历史映射推荐借/贷科目，人确认后保存 | 直击断链痛点，越用越准 | 低 | **P1 首发** |
| A2 | **自然语言查数** | "招行 8 月支出合计/最大 5 笔" → 受控工具调用返回表格+结论 | 免导出，老板自助 | 中 | P2 |
| A3 | **报文排障助手** | 报文详情页：喂 evidence 链，解读错误码/失败原因/修复建议 | 排障从"懂行的人"变"人人可查" | 低 | P2 |
| A4 | **异常检测** | 批量扫描：大额、同对手方高频、非常规时间、新对手方首笔 | 风控兜底 | 中 | P3 |
| A5 | **财务简报** | 月度流水/余额/入账率 narrative 简报，一键生成 | 汇报省事 | 低 | P3 |

> 排序依据：A1 有现成规则体系做冷启动（历史 AccountingMapping 就是训练样本）且闭环最短；A2/A3 依赖 P0 地基；A4/A5 锦上添花。

**与制证自研的衔接（重要）**：今日并行调研已确认金蝶 GL_VOUCHER 制证自研可行（`kingdee-voucher-selfdev-feasibility-20260911.md`），制证方案定调为「规则映射表为主 + AI 兜底预填（不直接定案）」——其中 **AI 兜底预填即本规划的 A1**，是同一件事的两半：424 科目表（用户已上传，含核算维度列）+ 财务规则表就是 A1 的上下文与冷启动样本；A1 的建议被人工确认后沉淀回映射规则库，规则命中越多 AI 介入越少。规划合并推进，避免两套"AI 建科目"重复建设。

## 四、技术架构

```
前端（各页面 AI 入口 + 全局悬浮助手 A2）
  │  POST /api/ai/{capability}   ← 新权限 ai:use + 按能力细分
  ▼
AiController → AiCapabilityService（每能力一个，互相独立）
  │ 权限校验 │ 脱敏 │ 限量 │ 开关 │ 组装上下文
  ▼
ToolRegistry（受控工具：查余额/查流水/查映射/查对账/查报文摘要）
  │  工具内部以当前用户身份走 CompanyScopeService + 现有 Service 层
  ▼
LlmGateway（轻量 OpenAI 兼容客户端：chat + tool-calling，超时/重试/降级）
  ▼
LLM 提供方（DeepSeek / 通义 / 本地 vLLM，配置切换）
  │
ai_call_log 审计表（V24）+ 现有 system_audit 双写
```

**关键设计决策**：

| 决策 | 选择 | 理由 |
|---|---|---|
| 查数方式 | **受控工具调用（function calling）**，不做裸 Text-to-SQL | SQL 注入/越权/性能三重风险归零；工具=白名单查询，天然权限继承 |
| LLM 接入 | 自建 `LlmGateway` 接口 + OpenAI 兼容实现，~200 行 | 不上 Spring AI（重、绑定快、本场景用不到 RAG/向量库）；换供应商零代码改动 |
| 建议置信策略 | A1 输出 top-3 候选科目+理由，人工必须点选 | 置信度分数不可靠，让 LLM 给理由而非分数 |
| 前端形态 | 能力内嵌页面（审核页按钮/报文页按钮）优先，全局聊天助手放 P2 之后 | 内嵌 = 上下文自动带对，聊天 = 用户要自己描述清楚 |

## 五、分期路线图

### P0：地基（约 2 天）

- V24：`ai_call_log` 表 + `ai` 权限域（ai:use、ai:config）进 permission-catalog
- `LlmGateway` + OpenAI 兼容客户端 + 配置（`ai.provider.*`，密钥走环境变量，启动校验快速失败）
- 能力开关框架（`ai.capabilities.*.enabled`，默认关）+ 审计切面
- **验收**：切 provider 只改配置；每次调用留全量审计；密钥不出现在代码/日志/前端；关掉开关后所有 AI 端点 403

### P1：智能入账建议 A1（约 3 天）

- 审核页「AI 建议科目」：未命中映射的流水 → LLM 给 top-3 科目候选+理由（上下文=公司现有 AccountingMapping 全集摘要 + 该流水摘要/对手方/金额 + 同对手方历史入账）
- 人确认后可一键"保存为新映射规则"（沉淀回规则库，下次不再问 AI）
- **验收**：建议→确认→入账全链路走通；保存映射后同类流水规则命中（AI 不再介入）；确认率 100%（无任何自动落库路径）；100 条样本建议命中率 ≥70%（人评）

### P2：自然语言查数 A2 + 报文排障 A3（约 4 天）

- A2：5~8 个受控工具（按公司/账户/期间查余额合计、流水分页/聚合、对账结果、映射列表），全局悬浮助手，回答附数据表格+来源任务号
- A3：报文详情页「AI 诊断」，上下文=evidence 链（URL/明文请求/响应/状态/耗时，脱敏后）
- **验收**：集成测试证明越权查询 0 命中（跨公司/跨权限用户各测）；工具调用全程审计；A3 对既有已知错误码样本解读正确

### P3：异常检测 A4 + 简报 A5（约 3 天，按需启动）

- A4：每日增量扫描任务（复用调度框架错峰），异常清单页 + 处理流转
- A5：按月生成简报（数字全部来自 SQL 聚合工具，LLM 只负责叙事），导出
- **验收**：A4 误报率人工评估 <30% 后才推给业务角色；A5 数字与查询页一致（勾稽）

## 六、安全与合规边界

| 风险 | 措施 |
|---|---|
| 数据出域 | 出域内容 = 脱敏账号 + 业务字段；D3 拍板"仅本地模型"则 A2/A3 降级为本地模型可用集 |
| 越权 | 工具执行体=当前用户身份；AI 模块自身不持有任何数据权限 |
| 提示注入 | 银行报文/流水摘要作为**数据**进 prompt（分隔+转义），指令只来自系统模板；LLM 输出永不进入 SQL/文件路径 |
| 滥用与成本失控 | 每用户每能力限频（如 20 次/日）；ai_call_log 记 token 与估算费用；月度预算告警 |
| 密钥 | 环境变量注入（compose env 白名单加透传行），启动时校验 |
