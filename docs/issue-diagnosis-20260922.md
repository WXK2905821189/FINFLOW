# 诊断报告：GL 凭证推送「必录维度未录入或不可用：银行账号」（2026-09-22）

> 起因：W15 上线插桩后用户复推，日志显示维度**确实在报文里**
> （`#2 1002 FDETAILID__FF100002=110922659010201`），但金蝶仍拒。
> 本轮通过 **4 轮真实账套差分实验**定位根因并完成修复（commit `e39ebb5`）。

## 一、结论

**根因：银行账号维度值档案（CN_BANKACNT）必须属于账簿对应组织。**
`KingdeeProperties.glAcctbookNumber` 硬编码 400（雪云账簿），而图虫的流水
由 `KingdeeOrgResolver` 解析到 org 410 —— 图虫的银行账号档案
`110922659010201`（org 410，已审核、未禁用、全账套唯一）在雪云账簿 400
的语境下被金蝶判「**不可用**」。报错文案「未录入**或不可用**」里的
「不可用」就是字面意思。

## 三、破案过程中的两个关键反转

1. **昨天的「成功对照实验」全部无效**：9-22 上午的 16079-16083 用的科目是
   **1001（库存现金，无必录维度）**——往不需要维度的科目塞维度值，金蝶根本不校验。
   唯一有效的历史成功是校准日 16043：1002 + 雪云档案 + org 400（账簿恰好匹配）。
2. **`ExecuteBillQuery` 响应就是行数组**：调试中发现金蝶该接口返回的
   `Result.Result` 直接是数组（部分场景为字符串化 JSON 需二次解析），
   早期脚本把它误当字符串再 parse 导致截断报错。
