## 1. 这次到底改了什么

用户两条原始诉求：

> 1. 原始报文数据需要留存并展示一下，单独给个模块来做这事，方便我确认是否连接到

改之前的状态（诊断结论）：

| 位置 | 银行返回 | 落地 | 丢弃 |
|---|---|---|---|
| 余额 `NTQADINF` | 10 字段 | **1 个**（可用余额） | 上日 / 联机 / 冻结三个口径 + 6 个账户身份字段 |
| 流水 `trsQryByBreakPoint` Z2 | 30 字段 | **7 个** | 含每笔后余额、起息日、冲账标志、信息标志等 23 个 |
| 原始报文 | 已在留存（payload + sha256） | 有表有数据 | **没有任何出口**：无查询接口、无页面 |

改完之后：余额 10 字段全链路落地，流水 30 字段全链路落地，投影层彻底删除改为直出，原始报文有了独立模块。

## 2. 关键决策与它们的代价

### D1 借贷表示法：按 API 存原始

招行接口与网银导出件的借贷口径**不等价**，这是本次最重要的发现：

| 来源 | 表示法 |
|---|---|
| API `trsQryByBreakPoint` | `loanCode(C/D)` + **单个带符号** `transAmount`（D 借方为负） |
| 用户提供的 Excel 导出件 | 「借方金额 / 贷方金额」**两列无符号**（13 行实测互斥，both=0 / neither=0） |

决定：**以 API 为存储基准**。因此同时存两个金额：

- `signed_amount` — 银行原始带符号金额（D 为负、C 为正）
- `amount` — 内部记账用的无符号金额

**为什么两个都要留**：`BankDataSyncExecutor.validate()` 有一条 `amount must be greater than zero` 的硬校验，且 `uk_bank_statement_business` 唯一键包含 `amount`。把 `amount` 改成带符号会让**每一笔借方交易都被判为 INVALID**。所以不复用 `amount`，而是新增列 —— 既拿到银行原始值，又零回归。

### D2 存储形态：现有表加列

`V17`（余额 9 列）、`V18`（流水 25 列），全部 nullable，不回补、不编造历史值。

### 「不用业务投影」：直接删掉投影层

`BankDataProjectionResponse`（id / sourceRecordId / occurredAt / amount / direction / summary）已**整体删除**，余额页与流水页直接返回 `BankDataBalanceResponse` / `BankDataStatementResponse`。信封 `BankDataProjectionPageResponse` 改为泛型 `<T>`。

改造前做过可行性核查：既有测试只断言 `records[*].id`、`records[0].bankRequestNo`、`records[0].taskStatus` 这类**血缘字段**，没有一条断言 amount / direction / summary，所以拆投影是干净的——实测也确认 135 条全绿。

血缘字段（`taskNo` / `taskRequestId` / `taskStatus` / `accountMasked`）以可空尾部字段保留在行 DTO 上，只有投影查询填充，其它端点为 null。

## 4. 本轮踩到的坑（都值得记住）

### 坑 1：聚合层 `canonical*` 会重建条目，把新字段悄悄吃掉

`BankDataAggregationService.canonicalEntries()` / `canonicalBalances()` 用**构造函数重建**每个条目做规范化。我只改了适配器与执行器，字段在这一层被丢得一干二净——`availableBalance`（旧列）存进去了，`onlineBalance` 等新列全是 null。

**症状很有迷惑性**：老字段有值、新字段全空，看起来像迁移没生效，实际是规范化层截断。

修法：两个方法都补上厂商字段，并加注释说明「厂商块不是业务词汇，没有可规范化的东西，重建只会丢数据」。

> 教训：本仓库凡是「构造一个新对象做规范化 / 清洗」的地方，加字段时**必须同步检查**，否则字段会在中间层静默丢失。

### 坑 2：H2 不支持一条 ALTER 加多列（实测）

`ALTER TABLE t ADD COLUMN a ..., ADD COLUMN b ...` 在 MySQL 8 没问题，**H2 2.2.224 直接语法错误**——报错位置指向第一个逗号。

用 `backend/.m2-local/com/h2database/h2/2.2.224/h2-2.2.224.jar` 直连实测确认：

| 语句 | H2 2.2.224 |
|---|---|
| 多列 + COMMENT | ✗ |
| 多列（无 COMMENT） | ✗ |
| 单列 + COMMENT | ✓ |
| `DATE` 列 | ✓ |

V17 / V18 因此改为**每列一条 ALTER**。这不是风格问题，是跨库硬约束（与之前记下的「禁用多表 JOIN-DELETE」同类）。

### 坑 3：测试共用一个 H2 实例，数据会跨上下文泄漏

`application-dev.yml` 是 `jdbc:h2:mem:finance;DB_CLOSE_DELAY=-1`——同一个 JVM 内所有 Spring 测试上下文共享同一个库。`RawMessageQueryIntegrationTest` 全量跑时失败 `expected: <CMB> but was: <MOCK>`：其它测试的 MOCK 适配器报文漏进了它的未过滤列表。

修法：断言前先按本测试自建账户过滤（`.param("accountId", ...)`）。

> 另一个小坑：过滤参数名是 **`accountId`** 不是 `bankAccountId`（Controller 的 `@RequestParam` 名）。第一次修的时候写错了名字，过滤被静默忽略，测试照样红。

### 坑 4：MockMvc 响应默认 ISO-8859-1

断言中文（户名、收付方）必须 `getContentAsString(StandardCharsets.UTF_8)`，否则拿到乱码。

## 7. 追加：中信侧真实字段（同批次补做）

`RealCiticBankDataAdapter` 原本和招行一样只落 7 个字段（`CiticStatementRow` 解析了 14 个但丢掉大半）。现已补上，映射关系如下。

### 流水（DLTRNALL → 共享厂商列）

| 共享列 | 中信字段 | 招行字段 | 说明 |
|---|---|---|---|
| `bank_account_no` | 容器 `accountNo` | Z1 `queryAcctNbr` | |
| `loan_code` | `creditDebitFlag` | `loanCode` | 两边都是 C/D，语义一致 |
| `signed_amount` | **`tranAmount` + flag 重建** | `transAmount` 原值 | 见下方警告 |
| `acct_online_bal` | `balance` | `acctOnlineBal` | 交易后余额 |
| `ctp_acct_nbr` | `oppAccountNo` | `ctpAcctNbr` | |
| `ctp_bank_name` | `oppOpenBankName` | `ctpBankName` | |
| `request_nbr` | `sumTranNo` | `requestNbr` | 均为流水序号类标识 |
| `yur_ref` | `oriNum` | `yurRef` | 均指向另一笔业务 |

> **⚠️ 中信的金额不带符号**：实测 `tranAmount=88.00 + creditDebitFlag=C`、`12.00 + D`，而招行是 `-12.00` 这种带符号单列。所以 `signed_amount` 对中信是**按 flag 重建**的（D 取负），对招行才是原值。这一列的含义是「银行口径的带符号金额」，不是「报文原值」。已在代码注释里写明。

中信不报的字段（起息日 `valueDate`、票据号、冲账标志 `reversalFlag`、信息标志 `infoFlag`、母子公司四列等）一律留 null —— **不编造**。

### 余额（DLBALQRY → 共享余额列）

中信与招行报的是**同样三个口径**，只是名字不同：

| 共享列 | 中信 | 招行 |
|---|---|---|
| `available_balance` | `usableBalance` | `avlblv` |
| `online_balance` | `balance` | `onlblv` |
| `frozen_balance` | `forzenAmt` | `hldblv` |
| `previous_day_balance` | 不报（null） | `accblv` |
| `vendor_currency_code` | `currencyID` | `ccynbr` |
| `bank_account_no` / `bank_account_name` | `accountNo` / `accountName` | `accnbr` / `accnam` |

这条同源性反过来证明了 V17/V18 的列是**语义列**而不是招行私有列 —— 两家银行同一套三口径。

### 命名上的取舍（需要你知道）

列名沿用了招行的字段 ID（`ctp_acct_nbr`、`acct_online_bal`、`loan_code`…）。这有个副作用：拿中信的数和中信的导出件比对时，列名对不上。

**没有改名的理由**：① 招行是主接入行，保留其字段 ID 让「屏幕 vs 招行导出件」能逐列对照，这正是需求 2 的目的；② 改中性名要再走一次迁移 + 动实体/DTO/前端/测试，成本不小。

**兜底**：任何一行都能在「原始报文」模块看到完整报文体，那是字段名的最终权威。若你更希望改成中性名（如 `counterparty_account` / `balance_after`），现在改代价最小（还没上生产），说一声就动。

## 8. P3 导出（本轮追加完成）

系统此前没有任何导出能力，本轮从零建了 CSV 导出器，已与真实字段链路一并交付：

- **端点**：`GET /api/bank-data/{balances|statements}/export`，权限与屏上查询同权（不新增权限面——导出只是同一批授权数据的另一种形状）。筛选参数与查询接口一致，导出跟随当前筛选
- **列序**：流水 36 列严格对齐招行网银导出件（账号/账号名称/币种/…/公司一卡通号），能填的填，接口不返回的留空**不编造**；余额 13 列按四口径+身份字段输出
- **借贷双列**：`signedAmount` 在导出时拆回「借方金额/贷方金额」——D 为负落在借方列取绝对值、贷方列留空，与银行文件互斥口径一致。存储层仍保持银行原值不动
- **Excel 兼容三件套**：UTF-8 BOM（中文不乱码）、CRLF+RFC4180 引号、**公式注入防护**（`=+-@` 开头的文本单元格加前导撇号——摘要/收付方名称是交易对手可控制的内容，是真实的注入面；数字单元格绕过防护保住负号）
- **文件名**：RFC6266/5987 双写（ASCII 兜底 + `filename*=UTF-8''` 中文名），前端从响应头解析后落盘
- **超量护栏**：单次导出上限 + 一行前瞻——超限时整单拒绝而非静默截断（截断的对账文件比报错危险得多）
- **前端**：查询页执行筛选后出现「导出 CSV」按钮；http 拦截器为 blob 响应放行（原先的 ApiEnvelope 解包会把 Blob 误判为错误）

**过程中发现并补上的缺口**：流水的银行币种代码（`currencyNbr`）此前根本没存——余额表 V17 有 `vendor_currency_code`，流水表没有，导出第 3 列「币种」会整列空白。新增 **V19**（`bank_data_statement.vendor_currency_code`，nullable，每列一条 ALTER）补上，CMB 传真实值、CITIC 不报留 null。
