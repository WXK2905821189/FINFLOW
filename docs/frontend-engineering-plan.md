# FINFLOW 前端真实 API 接入实施计划

## 1. 目标、范围与原则

本计划仅覆盖 `frontend/`。目标是将当前演示工作台逐步替换为受服务端认证、会话和 RBAC 约束的实现，并为用户、银行账户、交易和转账建立可验证的接口边界。

当前前端存在固定 `demo-token`、固定管理员身份、本地演示数据和本地“成功”状态。这些内容必须移除，不能作为降级路径或开发环境自动兜底。页面不得把网络失败、接口未实现、银行适配器的 `ACCEPTED` 或本地表单状态描述为已创建、已提交、已执行或已入账。

前端权限仅用于导航、路由和操作入口的可见性；服务端的 `401`/`403` 与资源级授权是最终依据。所有请求均继续使用 Vite 的 `/api` 代理，前端不传递企业 ID，也不在日志或错误提示中输出令牌、完整账号或密码。

## 2. 当前契约盘点

后端统一使用如下响应信封，前端请求层必须先解包并保留 HTTP 状态和响应消息用于错误处理：

```ts
type ApiEnvelope<T> = {
  code: number;       // 成功为 0
  message: string;
  data: T;
  timestamp: string;
};

type PageResponse<T> = {
  page: number;
  size: number;
  total: number;
  records: T[];
};
```

### 2.1 可立即接入的后端接口

| 领域 | 接口 | 请求/响应要点 | 前端使用与限制 |
| --- | --- | --- | --- |
| 认证 | `POST /api/auth/login` | `{ username, password }` -> `{ accessToken, tokenType, expiresInSeconds, user }` | 仅在 `code === 0` 时保存服务端返回的真实令牌和用户快照。登录失败统一显示“账号或密码错误”。 |
| 会话 | `GET /api/auth/me` | Bearer JWT -> `CurrentUserResponse` | 应用启动和每次恢复会话时调用；以返回结果覆盖本地用户和权限。 |
| 注册 | `POST /api/auth/register` | `{ username, email, password }` -> 待激活用户 | 成功后仅显示待激活结果并回到登录，不建立会话。当前后端没有 `name`/确认密码字段，前端可本地校验确认密码，但提交时只发送契约字段。 |
| 用户 | `GET /api/users?page&size` | -> `PageResponse<CurrentUserResponse>` | 仅 `user:manage`；当前只支持分页，不支持搜索或状态/角色筛选。 |
| 用户 | `POST /api/users`、`PUT /api/users/{id}` | `UserUpsertRequest` -> `CurrentUserResponse` | 请求须含 `username`、`email`、`status`、`roleIds`；创建时通常还需 `password`。无 DELETE、启停专用、邀请、最近登录字段。 |
| 角色 | `GET /api/rbac/roles` | -> `SysRole[]` | 需要 `role:manage`；用户管理若需角色下拉，后端须确认管理员同时拥有该权限，否则这是阻塞项。 |
| 银行账户 | `GET /api/bank-accounts` | -> `BankAccountResponse[]`，账号已掩码 | 可用于账户选择和账户列表；前端不得自行恢复完整账号。 |
| 银行账户 | `POST /api/bank-accounts`、`PUT /api/bank-accounts/{id}` | `BankAccountRequest` -> `BankAccountResponse` | 仅 `bank:manage`；字段为银行代码、名称、完整账号、CNY、可用余额、状态。 |
| 银行适配器 | `GET /api/banks` | -> 银行代码数组 | 仅 `bank:view`；用于账户表单的银行代码选择。 |
| 转账（现状） | `POST /api/transfers` | `BankTransferRequest` -> `{ bankCode, bankReference, status, message }` | 仅能表达银行适配器已受理；目前不产生可查询的转账申请、交易或余额变更，且开发环境为模拟适配器。不得接入“发起转账成功”流程。 |

`CurrentUserResponse` 的字段为 `id`、`username`、`email`、`phone`、`status`、`roles`、`permissions`。展示层应使用后端的状态和值；不要继续依赖中文演示枚举。

### 2.2 缺失或不满足产品要求的契约

以下能力没有可用接口，或现有接口不能满足需求。对应页面可先完成框架、权限、加载和明确的“暂不可用/请求失败”状态，但不得创建替代性本地数据：

| 缺口 | 所需后端契约/语义 | 影响的前端功能 |
| --- | --- | --- |
| 会话注销与失效原因 | 可选 `POST /api/auth/logout`；至少需统一的 `401` 错误码/消息约定。 | 退出可先清除客户端会话；`401` 必须清除真实令牌并提示会话失效。 |
| 仪表盘 | 聚合摘要、启用账户、最近 10 笔交易、6 个月趋势、待我审批数量/金额。 | 不得再显示固定余额、趋势柱或演示交易。 |
| 交易 | 服务端分页列表、组合筛选、详情和冲正；字段覆盖交易编号、日期、类型、账户、对方、金额、状态、关联转账、创建人/时间。 | 交易记录、仪表盘最近交易、交易详情/冲正。 |
| 转账申请状态机 | 草稿创建/编辑/提交/取消、详情、分页待办、审批、执行；稳定申请编号、状态和事件时间线。 | 三段式发起、审批、执行、结果页和跨页面刷新。 |
| 转账安全语义 | 提交/执行的幂等键、两位小数校验、计划日期、职责分离、余额/状态/交易的原子结果；执行失败保持已批准。 | 高风险提交防重、可解释错误和成功结果。 |
| 用户管理完整性 | 搜索、状态/角色筛选、最近登录/创建时间、启用/停用、邀请/重发、唯一管理员/未完成任务风险。 | UI 规范中的筛选、启停、邀请和风险确认。 |
| 角色读取权限 | `user:manage` 管理员是否具备角色列表读取能力，或提供面向用户管理的受控角色选项接口。 | 创建/编辑用户的 `roleIds` 映射。 |
| 错误关联 | 字段级校验结构、请求编号、稳定的业务错误码。 | 表单字段错误、可重试错误和故障提示。 |

## 3. 按优先级实施

### P0：认证、会话恢复与权限路由

1. 重建 `services/http.ts`：为真实 JWT 注入 `Authorization: Bearer <token>`，解包 `ApiEnvelope<T>`，将网络、非 2xx、`code !== 0` 归一为可消费错误对象。对并发 `401` 只执行一次会话清理和登录跳转；`403` 不清除会话，也不由拦截器直接弹出与页面重复的提示。
2. 重建认证 store：仅保存真实登录响应中的令牌和用户快照，持久化介质使用 `sessionStorage` 的最小令牌记录，内存保存完整用户。删除 `demoUser`、`demo-token`、演示账号初始值和对 `data/demo.ts` 的认证依赖。令牌永不出现在 UI、错误对象、控制台或 URL。
3. 实现会话恢复：应用启动若存在令牌，进入 `restoring` 状态并请求 `/auth/me`；成功后用最新权限建立 `authenticated` 状态，失败或 `401` 时清除会话并保持匿名。恢复完成前不得短暂渲染受保护菜单、页面数据或权限动作。
4. 重新设计路由守卫：守卫接收所需权限；匿名用户重定向到 `/login?next=...`，只接受站内、受允许路由白名单约束的 `next`；已登录无权限进入 `/403`；权限无法加载或请求出错显示可重试错误页，不能误报为 403。登录成功后优先返回合法 `next`，否则进入第一个可访问页面。
5. 由服务端 `permissions` 生成菜单和操作能力。菜单只显示可访问页面；操作入口按权限隐藏。收到后端 `403` 后保留页面上下文，显示“无权执行此操作”，并刷新 `/auth/me` 以处理权限变更。
6. 登录、注册、403 与退出完整接入：登录提交期间防重，注册成功不自动登录，退出立即清除客户端令牌并转到登录页。补齐忘记密码入口的“服务尚未提供”状态，不能跳转空路由。

**P0 验收标准**

- 任意凭据不能登录，只有服务端返回成功后才进入工作台；应用中不再存在 `demo-token`、固定管理员或假登录延时。
- 带有效真实令牌刷新页面后，先调用 `/auth/me`，再显示权限对应菜单和页面；无效/过期令牌只显示登录页与“登录已失效，请重新登录”。
- 未登录深链接业务路由后登录能返回原合法地址；无权限深链接进入 403，且不请求该页面业务接口。
- 普通角色在 DOM 和路由中均不能访问用户管理；绕过 UI 的 `403` 响应不会被显示成成功。
- `npm run build` 通过，认证和路由单元测试覆盖登录成功/失败、会话恢复、401、403、非法 `next` 和权限菜单。

### P1：统一数据访问层与现有资源页面

1. 在 `types/` 与 `services/api.ts` 建立与后端 DTO 一一对应的 TypeScript 类型、参数对象和领域 API。删除不匹配的 `TransferForm`、中文演示状态和错误的 `DELETE /users` 假接口；所有列表均保留服务器分页的 `page`、`size`、`total`、`records`。
2. 用户管理先按已存在契约交付最小可用版本：服务端分页、加载骨架、无用户/筛选无结果区分、请求失败重试、创建和编辑表单。角色下拉必须等待角色接口授权方案确认；在此之前禁用提交并显示明确依赖说明，不用猜测角色 ID。缺少的搜索、筛选、启停、邀请和审计字段留在后端契约完成后接入。
3. 新增银行账户页或管理区（仅 `bank:manage`），以及被授权用户可见的账户列表。严格使用 `maskedAccountNumber`；创建/编辑完整账号只留在受控表单字段，不将其缓存到页面、通知或日志。账户列表/选择器覆盖加载、空、错误和禁用状态。
4. 将现有转账表单改为 API 契约就绪的受控表单：付款账户来自 `/bank-accounts`，提交字段包含 `payerAccountId` 和 `bankCode`，金额以精确小数表示，校验当前已知字段限制。由于现有接口不能创建受需求约束的申请，该表单在生产工作流中不提供提交成功路径；在缺少 P2 转账契约时展示受控不可用状态，不调用模拟支付接口。
5. 交易记录和仪表盘删除 `data/demo.ts` 的所有读取与固定指标。接口未提供前分别显示稳定的加载占位、缺少数据源的错误状态和重试动作；不得用零值或空列表掩盖请求错误。

**P1 验收标准**

- 前端不存在任何演示交易、演示用户、固定余额、固定申请编号或不存在的 REST 调用。
- 用户与银行页面的列表、表单与反馈全部来自成功 API 响应；网络失败、字段校验、403、空列表分别可辨。
- 页码切换使用服务端 `PageResponse`；创建/更新成功后刷新当前数据且保留合理的页码/筛选上下文。
- 页面所有账号展示都仅使用后端掩码字段；完整账号不出现在通知、确认摘要以外的输入上下文或浏览器存储中。

### P2：仪表盘、交易与安全转账闭环（依赖后端补齐）

1. 与后端先冻结 OpenAPI/DTO：每个新接口注明请求字段、枚举、分页排序、权限、错误码、幂等键、字段校验错误结构与成功后的可刷新资源。前端按已冻结 DTO 生成或手写严格类型，不接受“成功但缺少资源标识或状态”的响应。
2. 接入仪表盘模块级请求。摘要、账户、趋势、最近交易和待审批互不阻塞：各自具备骨架、空态、错误与重试。空数据按产品定义显示 `0.00`，趋势明确显示无足够数据；请求失败则不显示伪造的零值。
3. 接入交易服务端分页、URL 同步筛选、详情抽屉和冲正。筛选以 AND 语义提交，默认最近 30 天；列表刷新不丢失已提交筛选，详情和冲正成功后只以服务端返回记录更新。
4. 接入转账状态机。草稿、确认、提交、待审批、已批准、已驳回、已执行、已取消必须反映服务端状态。提交和执行携带幂等键并禁用重复动作；结果页只显示服务端申请编号与状态。审批/执行操作在权限与职责分离条件不满足时隐藏，但仍正确处理后端 `403`/`409`。
5. 对每个资金动作使用可恢复错误：余额不足定位金额字段；状态冲突提示刷新；执行失败保持服务端返回的已批准状态；不在客户端预扣余额或预写交易。

**P2 验收标准**

- 无数据企业仪表盘可正常显示真实零值和空态；任一模块请求失败不会污染其他模块或被展示为零值。
- 交易列表的分页、组合筛选和详情均来自服务端，筛选和页码可经 URL 恢复。
- 转账成功仅指服务端已创建的转账申请；只有执行成功才显示已执行，并能从服务端查询关联交易和更新后的余额。
- 创建人审批本人申请、审批人执行本人审批申请、重复提交/执行、余额不足和并发状态冲突均具有服务端可验证的失败界面，前端不产生成功提示或本地状态漂移。

### P3：质量、可观测性与交付门禁

1. 引入前端测试工具并建立测试脚本：请求层、认证 store、权限守卫、菜单可见性、错误映射、用户/账户表单，以及金额和账号掩码格式化。
2. 建立端到端联调用例，在后端可提供可重复测试环境后覆盖：登录失败/成功、刷新恢复、角色降级、未授权深链接、用户管理、账户读取、无数据仪表盘、交易筛选及转账创建/审批/执行/重复请求。
3. 保持可访问性和 UI 规范：稳定骨架尺寸、键盘可操作的表单与弹窗、错误不只依赖颜色、1024px 与 375px 下无破坏性溢出。高风险按钮在请求中不可重复触发。
4. 在 CI 门禁中要求类型检查、构建、单元测试和端到端关键用例通过；在接口变更时运行契约测试，并将 API 变更视为需要前后端共同评审的变更。

**P3 验收标准**

- `lint`、类型检查、构建和新增测试均通过；关键认证/RBAC/资金流程有可复现测试证据。
- 真实后端不可用、返回 401/403/409、字段校验失败和空数据时，前端均给出一致且不误导的状态。
- 不存在可从浏览器直接获得管理员权限、虚构资金成功、伪造交易/余额或绕过路由权限的路径。

## 4. 推荐实施顺序与停点

先完成 P0 并以真实 `/auth/login`、`/auth/me` 联调通过，再实施 P1 中用户和银行账户的现有契约。随后暂停转账、交易和仪表盘的业务接入，等待 P2 表中的后端契约、数据模型、审计、幂等和状态机完成并经联调确认。P3 贯穿每个优先级，但不得用仅构建通过替代接口与业务验收。

后端尚未提供的契约应在 OpenAPI 中冻结后再开始对应页面实现。任何“临时模拟响应”“本地成功结果”“固定编号/金额”或以浏览器角色替代服务端授权的方案都不在可接受实施范围内。
