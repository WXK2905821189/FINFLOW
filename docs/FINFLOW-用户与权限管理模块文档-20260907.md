## 1. 模块定位与范围

「用户与角色」是系统管理域的核心模块，页面路径 `/users`，菜单入口位于 **系统管理** 分组下，**仅超级管理员可见**（本系统中超级管理员 = `ADMIN` 角色，sys_role id=1）。

| 范围 | 内容 |
|---|---|
| ✅ 覆盖 | 账号生命周期（创建/编辑/启停用）、角色分配、角色与权限查询、密码重置、登录与会话安全、前后端鉴权链路 |
| ❌ 不覆盖 | 多租户组织架构（company_id 当前固定为 1）、S/SSO 单点登录、细粒度数据行权限（按 company 隔离已有 CompanyScopeService，行级权限不在本期） |

**核心规则（本文档第一原则）：**

1. 「用户与角色」菜单、路由、后端端点三层的唯一通行证 = `user:manage` 权限；该权限**仅授予 ADMIN**。
2. **任何角色（含 ADMIN）都无法查看他人明文密码。** 密码以 BCrypt 单向哈希存储（`sys_user.password_hash`），不可逆——需要提供密码时走「重置密码」流程，这是银企直连系统过银行侧安全评审的合规底线（可逆存储等价于明文存储，招行/审计必挂）。
3. 前端权限控制只做体验（隐藏入口），**真正的闸门永远在后端**：绕过前端直接调 API，无权限一律 401/403。

## 3. 数据模型

### 3.1 表结构（RBAC 五表）

```
sys_user ──< sys_user_role >── sys_role ──< sys_role_permission >── sys_permission
   │
   └──< auth_session（登录会话，支持吊销）
```

| 表 | 关键字段 | 说明 |
|---|---|---|
| `sys_user` | id, username(UNIQUE), **password_hash(BCrypt, VARCHAR(100))**, email(UNIQUE), phone, status, company_id | status ∈ ACTIVE / PENDING / DISABLED；password_hash 永不出现在任何 API 响应中 |
| `sys_role` | id, code(UNIQUE), name, description | 内置 4 角色（见 4.1） |
| `sys_permission` | id, code(UNIQUE), name | 31 项，`<domain>:<resource>:<action>` 命名 |
| `sys_user_role` | user_id, role_id（复合主键） | 一个用户至少一个角色 |
| `sys_role_permission` | role_id, permission_id（复合主键） | 角色→权限多对多 |
| `auth_session` | user_id, token_id, token_version, expires_at, revoked_at | 每次登录插入一条；登出写 revoked_at；tokenVersion 变更可一次作废该用户全部旧 token |

### 3.2 内置角色（V1 种子，不可删除）

| id | code | 名称 | 定位 |
|---|---|---|---|
| 1 | ADMIN | 系统管理员 | **超级管理员**：用户/角色/银行账户管理 + 全部业务查看 |
| 2 | FINANCE_STAFF | 财务专员 | 导入流水、制证、触发同步 |
| 3 | FINANCE_MANAGER | 财务经理 | 复核、监控、结账审批 |
| 4 | VIEWER | 业务查看者 | 只读 |

## 5. 「用户与角色」页面设计（前端待实现部分）

> 现状：后端端点齐全，前端为占位页。本节为实现设计，UI 框架沿用 Ant Design 5 + 现有 21 页规范（`docs/ui-specification.md`）。

### 5.1 可见性三层防线（需求「仅超级管理员可见」的落地）

| 层 | 机制 | 无权限时表现 |
|---|---|---|
| ① 菜单层 | `productNavigation.tsx` 中「系统管理 → 用户与角色」菜单项由 `hasPermission('user:manage')` 控制 | 菜单项不渲染 |
| ② 路由层 | `App.tsx` `<Route element={<PermissionGuard permissions={['user:manage']} />}>` 包裹 `/users` | 重定向 `/403` |
| ③ 后端层 | `UserController`/`RoleController` 每个端点 `@PreAuthorize("hasAuthority('user:manage')")` | 401（未登录）/ 403（无权限，`RestAccessDeniedHandler`） |

### 5.2 页面结构（页签式）

**页签一：账号管理**（对应 `GET /api/users`）

| 列 | 来源 | 说明 |
|---|---|---|
| 用户名 / 邮箱 / 手机号 | CurrentUserResponse | 手机号可空 |
| 角色 | roles[] | Tag 展示，ADMIN 角色行加高亮标识 |
| 状态 | status | ACTIVE=正常 / PENDING=待激活 / DISABLED=停用 |
| 操作 | — | 编辑、重置密码、启用/停用（见 5.4 守护规则） |

- 「新增用户」抽屉：用户名、邮箱、手机号、初始密码、角色（多选，至少 1 个）→ `POST /api/users`
- 初始密码规则：≥8 位；创建成功后**仅提示创建人线下安全渠道告知本人**（页面不提供"查看该密码"回显）

**页签二：角色与权限**（对应 `GET /api/rbac/roles` + `GET /api/rbac/permissions`）

- 左侧角色列表（4 内置角色只读 + 自建角色可编辑）；右侧权限树（按 domain 分组的 31 项复选）
- 角色创建：`POST /api/rbac/roles`；角色权限调整与删除为差距项（见 §9）

### 5.3 「看密码」需求的正确实现 —— 密码不可见 + 重置流程

| 诉求 | 系统行为 | 安全依据 |
|---|---|---|
| ADMIN「可看到不同角色的账号」 | ✅ 支持：账号列表展示全部账号及其角色、状态 | 仅展示非敏感字段，Current​UserResponse 不含 password_hash |
| ADMIN「可看到密码」 | ❌ 不提供任何明文密码查看/导出；提供「重置密码」：管理员输入新密码（或系统生成随机密码）→ BCrypt 落库 → 提示管理员线下告知本人 | BCrypt 单向哈希不可逆；若实现"看密码"则必须可逆存储 = 明文等价，直接违反密码安全基线与银行评审要求 |
| 用户忘记密码 | ADMIN 在账号管理中「重置密码」→ 新密码生效（旧 token 因 tokenVersion 失效可选，见 5.4） | 无自助找回（无邮件服务依赖），管理员代重置是当前部署形态的合理选择 |

### 5.4 危险操作守护规则

| 操作 | 规则 |
|---|---|
| 停用/降级最后一个 ADMIN | **禁止**：后端校验"变更后系统仍存在 ≥1 个 ACTIVE 的 ADMIN 角色账号"，否则 400（防锁死，需 RbacService 补充校验，见 §9 差距项） |
| 删除用户 | 本期不提供物理删除，一律 `DISABLED` 停用（保留审计线索与外键完整性） |
| 管理员重置他人密码 | 写审计（LOGIN_PWD_RESET，见 §8.4）；被重置用户的所有存量会话建议作废 |

## 6. 后端鉴权链路

```
请求 → JwtAuthenticationFilter → SecurityFilterChain（网关层） → @PreAuthorize（方法层） → 业务逻辑
         │ 解析 Bearer token        │ anyRequest().authenticated()     │ hasAuthority('user:manage')
         │ 验签/验过期               │ /api/auth/login 放行              │ 无权限 → 403
         │ auth_session 活性校验      │ 其余全部需认证 → 401
         │ (tokenId+tokenVersion+未吊销+未过期)
```

| 环节 | 实现 | 关键细节 |
|---|---|---|
| 令牌签发 | `JwtService.generateToken` | claims：sub(username)、uid、ver(tokenVersion)、jti(UUID)；HS256 对称签名 |
| 令牌校验 | `JwtAuthenticationFilter` | 验签 → 查 `auth_session`（isActive：未吊销 + 未过期 + tokenVersion 匹配）→ 装载 SecurityContext 与 authorities |
| 网关层 | `SecurityConfig.securityFilterChain` | 无状态（STATELESS）、CSRF 关闭（无 Cookie 会话，纯 Bearer）、仅 login + Swagger 文档放行 |
| 方法层 | `@EnableMethodSecurity` + `@PreAuthorize` | 每个业务端点显式声明权限编码，与 permission-catalog.md 对应 |
| 会话吊销 | `AuthSessionService` | 登出 revoke 单条；改密码/停用可提升 tokenVersion 一次性作废全部旧 token |
| 异常出口 | `RestAuthenticationEntryPoint`(401) / `RestAccessDeniedHandler`(403) | 统一 JSON 响应体，与前端 http 拦截器约定 |

**端点权限表（本模块）**

| 方法 | 路径 | 权限 | 说明 |
|---|---|---|---|
| POST | /api/auth/login | 公开 | 失败统一 401「Account or password is invalid」 |
| POST | /api/auth/logout | 登录即可 | 吊销当前 jti |
| GET | /api/auth/me | 登录即可 | 返回本人信息 + roles + permissions（前端权限数据源） |
| GET | /api/users | user:manage | 分页账号列表（含各账号角色） |
| GET | /api/users/{id} | user:manage | 账号详情 |
| POST | /api/users | user:manage | 创建（初始密码 ≥8 位，至少 1 个角色） |
| PUT | /api/users/{id} | user:manage | 编辑（密码留空不改，填了则 ≥8 位重置） |
| GET | /api/rbac/roles | role:manage | 角色列表 |
| GET | /api/rbac/permissions | role:manage | 权限清单（31 项） |
| POST | /api/rbac/roles | role:manage | 创建角色（含权限集） |

> IDOR 防护：`/api/users/{id}` 的横向遍历同样被 user:manage 拦截（非本人可查自己），路径级与方法级双保险；响应体永不回传 password_hash（`CurrentUserResponse` 字段白名单制）。

## 7. 前端鉴权链路

| 环节 | 实现 | 文件 |
|---|---|---|
| 令牌存储 | `sessionStorage`（Tab 级生命周期，关闭即清，优于 localStorage） | `services/http.ts` |
| 请求携带 | axios 拦截器 `Authorization: Bearer <token>` | `services/http.ts` |
| 会话恢复 | 启动时 `hydrate()`：有 token 则调 `/api/auth/me` 拉最新 user+permissions；401 则清 token 回登录页 | `store/auth.ts` |
| 权限判断 | `hasPermission(code)` 基于 `/me` 返回的 permissions 数组（**前端权限表是后端下发的投影，前端自身不做授权决定**） | `store/auth.ts:44` |
| 路由守卫 | `<PermissionGuard permissions={[...]}>` 命中任一权限渲染 `<Outlet/>`，否则重定向 `/403` | `modules/auth/pages.tsx` |
| 菜单显隐 | `productNavigation.tsx` 按 hasPermission 过滤菜单树 | 同左 |
| 403 页 | 按用户最高可用权限给返回入口（dashboard → statements → login） | `modules/auth/ForbiddenPage.tsx` |

**双层防线原则**：前端守卫被绕过（改路由、直调 API）不构成任何安全事件——后端每端点独立鉴权；前端守卫仅避免"点进去才 403"的糟糕体验。

## 8. 安全设计基线

### 8.1 密码安全
- 存储：BCrypt（`PasswordEncoder`，默认强度 10），随 V1 生效，**迁移到更优算法时仅需替换 Bean，旧哈希自动兼容升级**
- 强度：创建/重置均 ≥8 位；改进项：增加复杂度规则（字母+数字组合）与弱口令黑名单（§9 P1）

### 8.2 令牌与会话
- JWT 有效期默认 2 小时（`app.jwt.expiration`），无刷新令牌——过期重新登录（内网财务系统可接受）
- 双保险吊销：`auth_session` 行级吊销（登出）+ `tokenVersion` 全量作废（改密/停用）
- 生产启动校验：JWT secret ≥32 字符且禁止 `dev-only-` 前缀、DB 凭据强制显式配置，否则拒绝启动（`ProductionSecurityValidator`）

### 8.3 传输与部署
- 生产强制 HTTPS（nginx TLS 终结）；Bearer token 仅经 TLS 传输
- 环境变量注入密钥（ECS docker env），不入代码库、不写日志

### 8.4 审计（已落地）
接入 `SystemAuditService.record(userId, action, type, objectId, requestId, result, detail)`，埋点清单：

| 事件 | action | 结果 |
|---|---|---|
| 登录成功 / 登录失败 | LOGIN_SUCCESS / LOGIN_FAIL | 失败记录尝试用户名（不记密码） |
| 登出 | LOGOUT | — |
| 用户创建/编辑/停用/重置密码 | USER_CREATE / USER_UPDATE / USER_DISABLE / USER_PWD_RESET | detail 记目标账号，**不记密码值** |
| 角色创建/权限调整 | ROLE_CREATE / ROLE_UPDATE | detail 记权限编码集合 |

审计查询复用现有审计中心（`audit:view`，ADMIN/FINANCE_MANAGER/VIEWER 可见）。

### 8.5 防爆破（已落地）
- **用户名锁定**：同一用户名连续失败 5 次锁定 15 分钟（窗口自最后一次失败滑动）；锁定期间返回与密码错误相同的 401 文案（防账号枚举）
- **IP 失败限流**：同一来源 IP 每分钟 50 次**失败**登录 → 429（只统计失败，成功不计入，办公 NAT/网关共享出口不误伤）；IP 取 X-Forwarded-For 首段（nginx 终结后各用户不再共享代理地址）
- 实现：`security/LoginThrottleService`（JVM 内存态，单实例部署可接受；重启清零为既定权衡）
