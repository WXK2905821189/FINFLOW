## 三、根因（代码级，三重证据）

1. `RealCmbBankDataAdapter`（`adapter/cmb/RealCmbBankDataAdapter.java`）L52：`SUCCESS = CmbResponseParser.SUCCESS_CODE`；`CmbResponseParser` L20：`SUCCESS_CODE = "SUC0000"`。适配器 L122/L196 把 `SUC0000` 同时写入 collection 的 `bankStatusCode` 与 `status`。
2. `aggregation/BankDataAggregationService.java` L69：`BankDataStatus status = BankDataStatus.fromVendor(status 或 bankStatusCode)`。
3. `aggregation/BankDataStatus.java` L16-28 `fromVendor()` 映射表：
   ```java
   case "SUCCESS", "OK", "AAAAAAA" -> SUCCESS;   // AAAAAAA 是中信成功码，已覆盖
   ...
   default -> UNKNOWN;                            // "SUC0000" 落入这里
   ```
   → **CMB 成功码 SUC0000 不在词汇表**，被归为 UNKNOWN → `BankDataSyncExecutor` 判定非 SUCCESS → 不执行 normalize/落库。

**为什么单测没抓到**：`RealCmbBankDataAdapterTest` 只测解析层；`CmbGapClosureIntegrationTest` 的 stub 若走 `BankDataCollection` 3 参构造则 status 默认 `"SUCCESS"`（恰好在词汇表内），未覆盖真实银行码 `SUC0000` 穿过聚合层的路径。

## 四、修复建议

1. **主修复**（`BankDataStatus.java`，一行）：`fromVendor` 的 switch 增加 `case "SUC0000" -> SUCCESS;`
2. **单测补充**：
   - `BankDataStatusTest`：`fromVendor("SUC0000") == SUCCESS`（若已有测试类，加一条）
   - 建议 `CmbGapClosureIntegrationTest` 的 stub real 适配器返回 `bankStatusCode="SUC0000"`（而非默认 SUCCESS），走完整聚合 → 落库路径，杜绝此类映射缺口再次漏网
