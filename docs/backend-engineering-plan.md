# FINFLOW 后端工程实施计划

## 1. 目标与边界

本计划针对 `backend/`，目标是把当前 Spring Boot、JWT、RBAC、MyBatis-Plus、Flyway 和银行适配器原型，演进为可在预发布环境进行生产化验证的后端基础。实施过程中不得修改 `frontend/`；接口变更通过文档化契约交付给前端工程师。

本阶段的“生产化验证”指：认证边界、企业隔离、资金领域不变量、持久化、并发控制、审计、迁移、配置和自动化证据达到预发布验收要求。中信真实 SDK、签名证书、回执协议、清算对账和真实资金放行仍须在银行授权沙箱中单独验收；在此之前，生产配置禁止把模拟适配器的成功结果解释为真实支付成功。

当前基线的主要缺口：

- `sys_user`、`bank_account` 和权限查询没有企业上下文；`V1__init_rbac_and_bank_accounts.sql` 还包含演示账户和固定种子数据。
- `BootstrapDataInitializer` 使用源码中的 `admin/Admin@123` 自动创建管理员，生产环境没有一次性引导或强制改密边界。
- `BankController` 直接调用银行适配器，没有转账申请、审批、执行和失败重试状态。
- 没有交易流水、幂等记录、审计记录、请求编号和余额并发控制。
- JWT 虽然会在请求中重新加载用户权限，但没有会话版本/撤销语义；注册账号、停用账号和角色生命周期尚未形成完整认证边界。
- `application.yml` 默认使用 `dev`、固定开发密钥和模拟模式；生产 JDBC URL 仍带有不安全的默认参数；文档端点未按环境收敛。

## 2. 实施原则与依赖顺序

1. 所有资源的企业范围由服务端认证上下文决定，客户端提供的 `companyId`、Header 或查询参数不得改变授权范围。
2. 金额使用 `DECIMAL(19,2)` 和 Java `BigDecimal`，所有状态转换、余额变更和交易写入均由领域服务统一执行。
3. 幂等键用于防止客户端重试造成重复业务对象；数据库唯一约束是最终防线，不能只依赖内存锁或前端按钮禁用。
4. 外部银行调用与本地数据库事务分层：本地状态、出站命令和幂等记录必须可恢复；只有收到明确的成功回执并完成一致性处理，才可进入“已执行”。`ACCEPTED`、超时和未知结果必须进入待对账/人工处置路径。
5. 先完成数据库和认证上下文，再实现转账领域；先完成本地模拟器的可重复测试，再接真实银行 SDK。
6. 每个 P0 里程碑都必须有可重复的自动化测试和迁移/配置证据，未通过不得进入下一阶段或真实资金联调。

## 3. 按优先级的实施计划

### P0-1：企业边界与数据库基线

**目标**：让所有身份和业务资源具备不可绕过的企业归属，并能从现有 V1 数据安全迁移。

**代码落点**：新增 `company` 领域实体、Mapper、`CompanyContext`/解析器和企业范围查询辅助；改造 `SysUserService`、`RbacService`、用户/角色/银行账户查询及所有后续业务服务。不要把企业 ID 放在 JWT 中作为唯一可信来源，JWT 只携带用户身份；每次请求根据用户当前数据库状态解析企业和权限。

**迁移建议**：

- 新增 `company`：`id`、`code`、`name`、`status`、`created_at`、`updated_at`。
- 在 `sys_user`、`bank_account` 增加 `company_id`，先回填现有演示数据到明确标记为开发/迁移的企业，再加非空、外键和企业内唯一/查询索引。
- 对角色采用全局角色定义、企业内用户角色关联的当前 MVP 方案；禁止通过修改全局角色权限让一个企业意外获得另一企业的资源。若后续需要企业自定义角色，再引入 `company_id` 作用域。
- 将银行账号改为受控密文列（如 `account_number_ciphertext`、`account_number_last4`、`encryption_key_version`），不再新增明文账号列；收款账号按同等敏感级别处理。迁移脚本不得新增真实或完整演示账号。
- 新增 `schema_version`/迁移检查和迁移前后校验脚本或测试：行数、企业归属、账户余额合计、唯一约束和敏感字段格式均可核对。V1 中已有演示数据只允许在 `dev` 测试数据路径使用，生产初始化必须为空数据或由受控导入完成。

**验收**：两个企业使用相同资源编号、账号和筛选条件时，列表、详情、分页、搜索、统计和写操作始终只返回当前企业数据；篡改 URL、请求体、Header、分页和查询参数不能跨企业；跨企业资源统一返回安全的 `403`/`404`，不泄露资源存在性。

### P0-2：真实认证边界与安全初始管理员

**目标**：移除公开固定凭据，建立注册激活、停用、改密/重置和旧会话失效的服务端闭环。

**代码落点**：改造 `AuthService`、`UserDetailsServiceImpl`、`JwtService`、`JwtAuthenticationFilter`、`BootstrapDataInitializer`、`SecurityConfig`；新增认证令牌/会话版本、激活令牌、密码重置令牌、请求编号和必要的限流组件。

**方案**：

- 自助注册只创建 `PENDING` 用户，不能绑定企业、角色或访问业务接口；管理员邀请/创建成员后，使用一次性、限时、哈希存储的激活凭证完成激活。
- 初始管理员只允许显式的本地 `dev` profile 创建，开发凭据来自本地配置或启动输出的一次性随机凭证；`prod` 缺少已配置管理员/引导令牌时快速失败，不创建默认账号。首次成功激活或改密后令牌立即失效。
- 通过 `session_version` 或等价的服务端撤销字段使停用、密码重置、登出和安全事件处置能够立即使旧 JWT 失效。请求过滤器必须重新加载用户状态和当前权限。
- 登录失败、停用、未激活和不存在账号统一返回相同外部错误；密码只保存 BCrypt/同等强度哈希，不能进入日志、审计、响应或异常堆栈。
- 为登录、激活、重置申请和重置验证增加限流；补充安全响应头、生产 HTTPS/来源配置和文档端点 profile 控制。

**验收**：错误凭据不可枚举账号状态；待激活/停用用户不能登录；管理员停用或降权后旧令牌下一次请求立即失效/降权；重置密码后所有旧会话失效；企业内最后一个启用系统管理员不可停用；生产启动不接受源码或 README 中的固定管理员凭据。

### P0-3：转账申请状态机、职责分离与领域校验

**目标**：把当前直接调用银行适配器的接口改为持久化申请流程。

**状态机**：

| 当前状态 | 允许动作 | 下一状态 | 操作者约束 |
| --- | --- | --- | --- |
| `DRAFT` | 编辑、提交、取消 | `PENDING_APPROVAL`、`CANCELLED` | 创建人；管理员/专员可创建，草稿仅创建人编辑 |
| `PENDING_APPROVAL` | 审批通过、驳回、取消 | `APPROVED`、`REJECTED`、`CANCELLED` | 财务经理；创建人不得审批自己 |
| `REJECTED` | 编辑后重新提交、取消 | `PENDING_APPROVAL`、`CANCELLED` | 创建人；保留原申请与驳回原因 |
| `APPROVED` | 执行、取消 | `EXECUTING`、`CANCELLED` | 管理员/财务专员；执行人不得为审批人 |
| `EXECUTING` | 成功、可恢复失败/未知结果 | `EXECUTED`、`EXECUTION_FAILED` 或 `PENDING_RECONCILIATION` | 由执行服务和回执处理驱动 |
| `EXECUTED`、`CANCELLED` | 无业务修改 | 无 | 只读，错误通过冲正交易处理 |

`EXECUTION_FAILED` 和 `PENDING_RECONCILIATION` 是对产品展示状态的后端细分；API 必须明确其是否可重试以及不得重复扣款。若当前版本只支持本地模拟器，可将确定性失败直接留在 `APPROVED` 并记录失败原因，但不能伪造 `EXECUTED`。

**代码落点**：新增 `TransferApplication`、状态枚举、Mapper、请求/响应 DTO、`TransferApplicationService` 和 Controller；将现有 `BankAccountService.submitTransfer` 降级为适配器边界或删除直接暴露路径。新增统一 `MoneyValidator`、账号格式/脱敏服务和状态转换校验。

**校验规则**：付款账户属于当前企业且启用；金额大于 0、最多两位小数且不超过账户可用余额；账号、银行、用途和计划付款日期满足长度/字符白名单；创建、提交、执行都重新校验账户状态和余额。

**验收**：每个非法状态转换无副作用；创建人不能审批，审批人不能执行自己审批的申请；驳回原因必填；已执行/已取消不可编辑、删除或恢复；余额不足、账户停用和并发状态变化不会生成错误交易。

### P0-4：幂等、并发、事务和银行出站一致性

**目标**：确保重复请求最多产生一个业务结果，余额、状态、交易和外部调用状态可追踪、可恢复。

**实现要求**：

- 提交接口要求 `Idempotency-Key`，按 `company_id + actor_id + operation + key` 唯一；保存请求摘要、首次响应或资源 ID、状态和时间。相同键不同请求体返回冲突，不同键允许不同申请。
- 审批/取消使用“当前状态 + 版本号”条件更新或数据库行锁，只有一个并发请求能成功转换；失败请求返回稳定的状态变化错误。
- 执行前锁定付款账户和申请，使用数据库内余额作为本地账本；禁止以银行查询结果直接覆盖本地余额。余额扣减、交易写入、申请状态和执行幂等记录在一个本地事务中完成。
- 对真实银行调用采用 `payment_attempt`/outbox：保存不可变外部请求号、请求摘要、发送次数、回执状态、错误分类和下一次重试时间。网络超时/未知结果不得自动再次发起一个新外部请求，必须使用同一外部幂等号查询或进入对账队列。
- 模拟适配器必须支持确定性成功、业务失败、超时和重复请求注入，不能每次无条件随机返回“accepted”。
- 所有关键写操作带 `@Transactional`，同时用集成测试验证唯一冲突、数据库异常、适配器异常和事务回滚。

**验收**：相同幂等键并发提交只产生一个申请编号；并发审批/执行只有一个成功；重复执行最多一笔交易、一次余额扣减和一个银行外部请求号；任何阶段故障都能回滚或进入明确可恢复的对账状态，不能出现“扣款无交易”或“已执行无余额变化”。

### P0-5：交易、冲正与审计持久化

**目标**：建立不可覆盖的资金流水和完整的安全操作证据。

**数据表**：

- `transaction_record`：企业、交易编号、账户、类型、金额、状态、交易日期、摘要、对方脱敏信息、关联转账编号、冲正源交易编号、创建人和时间；交易编号与企业内关联号唯一，已入账记录不可更新/删除。
- `audit_event`：企业、操作者、事件时间、操作类型、目标类型/ID、结果、请求编号、变更前后脱敏摘要、失败分类、来源 IP/用户代理摘要（按隐私要求最小化）。只提供追加写入服务和受控检索，不提供业务修改/删除 API。
- `idempotency_record`、`payment_attempt` 按 P0-4 设计，保留必要索引和清理/保留策略；审计保留不少于 365 天。

**代码落点**：新增交易和审计实体、Mapper、领域服务；在认证、用户/角色、账户、转账、冲正和异常处理边界统一写审计；全局异常响应增加请求编号，但不返回 SQL、堆栈、令牌或敏感原值。

**验收**：登录成功/失败、登出、权限拒绝、用户角色变更、账户变更、转账全生命周期、交易创建/冲正和系统异常都有企业、操作者、目标、结果和请求编号；日志、审计、响应和列表最多暴露银行账号末四位；直接业务请求不能修改或删除审计和已入账交易；冲正金额相反且原记录保持不变。

### P0-6：生产配置与发布闸门

**目标**：让错误配置快速失败，避免开发默认值、模拟成功或文档暴露进入生产。

**代码/配置落点**：新增生产配置校验器和健康检查；收紧 `application.yml`、`application-dev.yml`、`application-prod.yml`；按 profile 限制 H2 console、OpenAPI/Knife4j、CORS、错误详情和日志级别。

**必需校验**：生产必须显式指定 profile、数据库 URL/账号/密码、长度和熵足够的 JWT/加密密钥、密钥版本、允许来源、HTTPS 相关设置和银行模式；`CITIC_MOCK_MODE=true` 在生产直接拒绝启动；真实 SDK 未安装或证书/配置不完整时快速失败。生产 JDBC URL 不提供 `useSSL=false`、`allowPublicKeyRetrieval=true` 等不安全默认值。

**验收**：逐项注入缺失、空值、错误格式和开发值，应用在启动阶段失败且不打印密钥；生产构建不含演示凭据、完整账号、模拟成功路径或未授权文档端点；预发布完成备份恢复、迁移、部署和回滚演练。

### P1：查询能力、可观测性和运营控制

在全部 P0 通过后实施：

- 交易列表、转账列表、审计检索、仪表盘汇总和稳定分页；所有查询带企业过滤和固定排序，汇总与流水口径一致。
- 对余额/交易/转账状态不一致、审计写入失败、权限拒绝突增、重复执行冲突、银行超时和重试积压提供指标、结构化日志和告警。
- 补充账户停用前的未完成转账检查、唯一管理员风险提示、密码/密钥轮换和审计归档策略。
- 增加数据库索引、连接池、锁等待和关键接口延迟基线；按代表性数据量验证迁移与分页性能。

### P2：真实银行沙箱与后续扩展

仅在 P0/P1 通过且获得银行授权后实施：

- 替换 `ExternalCiticBankSdkAdapter` 的占位实现，完成签名、证书、请求时间戳、防重放、限额、回执验签、查询和对账。
- 使用银行提供的沙箱故障矩阵验证成功、明确失败、超时、重复回执、回执乱序和人工补单；保留外部请求号与内部转账号双向追踪。
- 真实资金生产放行需要独立的财务、安全、QA 和发布批准；本计划不把“SDK 调用成功”本身视为放行条件。

## 4. 数据模型与迁移版本建议

建议将迁移拆成可审查、可回滚或可前向修复的版本，不在一个脚本中混合业务重构：

| 版本 | 内容 | 关键校验 |
| --- | --- | --- |
| `V2` | `company`、用户/账户企业归属、企业索引和约束 | 旧数据归属明确，跨企业外键不可写入 |
| `V3` | 账号密文/末四位/密钥版本，移除新代码对明文列的依赖 | 迁移前后账户标识和余额可核对，日志无明文 |
| `V4` | `transfer_application`、状态、版本号、企业内转账编号 | 状态枚举、金额精度、外键和唯一约束有效 |
| `V5` | `transaction_record`、冲正关系、交易索引 | 转账执行只能关联一条交易 |
| `V6` | `idempotency_record`、`payment_attempt`/outbox | 相同作用域和幂等键不可重复 |
| `V7` | `audit_event`、审计索引和保留字段 | 追加写入路径存在，业务账号不能更新/删除 |
| `V8` | 删除或隔离演示数据、收紧非空约束和生产初始化检查 | 干净生产库无测试企业、凭据和完整账号 |

若实际迁移需要调整版本号，必须保持单向、可追踪，并在迁移测试中覆盖“干净库”和“已有 V1 数据库”两条路径。生产数据库不使用 H2 迁移结果作为 MySQL 兼容性的唯一证据。

## 5. API 变更契约

所有接口继续使用统一响应结构，但错误响应应包含稳定的 `requestId`、业务错误码和字段错误；不得返回内部异常细节。认证后的资源响应只包含当前企业可见字段。

| 方法 | 路径 | 权限/用途 | 关键请求字段与规则 |
| --- | --- | --- | --- |
| `POST` | `/api/auth/login` | 公开登录 | 用户名/邮箱、密码；统一错误信息；成功返回短生命周期令牌和当前用户 |
| `GET` | `/api/auth/me` | 已认证 | 从服务端当前状态返回企业、角色、权限和激活状态 |
| `POST` | `/api/auth/register` | 公开注册 | 仅创建 `PENDING` 用户，不返回可用会话 |
| `POST` | `/api/auth/activate` | 一次性激活 | 凭证只传输一次，服务端只保存摘要；成功后凭证失效 |
| `POST` | `/api/auth/password-reset/request` / `confirm` | 公开/凭证 | 限时一次性；成功使所有旧会话失效 |
| `GET` | `/api/bank-accounts` | `bank:view` | 只返回当前企业，账号仅末四位 |
| `POST`/`PUT` | `/api/bank-accounts` | `bank:manage` | 企业由会话决定；禁止停用存在未完成申请的账户 |
| `POST` | `/api/transfers` | `transfer:create` | 创建草稿；`Idempotency-Key` 必填；付款账户不能跨企业 |
| `PUT` | `/api/transfers/{id}` | 创建人 | 仅 `DRAFT`/`REJECTED` 可编辑，使用版本号防覆盖 |
| `POST` | `/api/transfers/{id}/submit` | 创建人 | 重验字段、账户状态和余额，进入 `PENDING_APPROVAL` |
| `POST` | `/api/transfers/{id}/approve` | `transfer:approve` | 创建人返回 `403`；通过/意见或驳回原因按规则校验 |
| `POST` | `/api/transfers/{id}/cancel` | 创建人/明确授权角色 | 只允许可取消状态，记录审计 |
| `POST` | `/api/transfers/{id}/execute` | `transfer:execute` | 执行人不能是审批人；返回内部状态和请求编号，不伪造银行最终成功 |
| `GET` | `/api/transfers` / `/{id}` | 业务读取权限 | 企业过滤、状态/日期/关键字筛选、稳定分页 |
| `GET` | `/api/transactions` / `/{id}` | `transaction:view` | 已入账只读，关联转账和冲正关系可追溯 |
| `POST` | `/api/transactions/{id}/reversal` | 规定角色 | 原交易不可改；金额相反、幂等且企业内关联 |
| `GET` | `/api/audit-events` | 管理员/财务经理 | 只读、企业过滤、按时间/操作者/资源检索，最少保留 365 天 |

旧的 `POST /api/transfers` 直接返回银行 `ACCEPTED` 的语义必须移除或改为创建申请；不保留一个绕过审批和持久化的兼容入口。状态枚举、错误码、幂等冲突语义和字段精度应在 OpenAPI 与后端契约测试中固定。

## 6. 测试与验收标准

### P0 自动化测试集

- **认证**：成功/失败登录统一错误、注册待激活、激活令牌过期/重复/篡改、停用账号、角色降权、密码重置后旧 JWT 失效、限流和生产配置快速失败。
- **企业隔离**：四角色矩阵、未认证、跨企业同 ID、跨企业列表/搜索/统计/分页、伪造企业 Header/请求体；断言状态码、响应字段和无副作用。
- **状态机**：创建、编辑、提交、审批、驳回、重新提交、取消、执行、失败、未知结果和冲正；覆盖所有非法跃迁、重复操作和职责分离。
- **幂等与并发**：相同键并发提交、相同键不同请求体、并发审批、并发执行、网络重试、适配器超时和重复回执；断言一个申请编号、一笔交易、一次扣款和一个外部幂等号。
- **事务回滚**：在余额更新、交易插入、申请状态更新、审计写入和唯一约束处注入异常；验证回滚或进入明确对账状态，不允许半成功。
- **数据安全**：金额精度、账号白名单、敏感字段脱敏、错误响应、审计追加不可改、已入账交易不可删改、365 天留存字段和企业索引。
- **迁移**：MySQL 干净库、含 V1 演示数据的升级库、重复启动、迁移失败/前向修复、备份恢复和关键金额/行数校验。

### 验收门槛

1. 所有产品需求和 `docs/quality-security-checklist.md` 中的 P0 用例通过；无未批准的越权、敏感数据泄露、重复扣款、金额不一致和迁移损坏。
2. `mvn test` 在干净环境通过，并产出可追溯测试报告；至少包含 Spring Security/API 集成测试、Flyway 集成测试、事务测试和并发测试。
3. 预发布使用 MySQL 等价配置完成迁移、备份恢复、部署和回滚演练；记录制品校验值、数据库版本和配置校验结果。
4. 生产 profile 缺少任一必需密钥、数据库配置、加密配置或真实银行配置时快速失败；不存在公开固定管理员、默认开发密钥、默认模拟成功或开放文档端点。
5. 认证、用户、银行账户、转账、交易、审计和错误响应的 OpenAPI 契约经过后端/前端/QA 评审；本计划不直接修改 `frontend/`，前端联调由后续任务按契约实施。

## 8. v0.2 银行数据接入底座

### 8.1 架构约束

银行 SDK/API 只能由后端 `bank-adapter` 反腐层调用。适配器负责银行协议、鉴权、签名、分页、回执和错误映射；其输出先写原始结果与同步日志，再转换为 FINFLOW 统一数据模型，最后经校验、去重与领域服务写入业务表。前端只能通过 FINFLOW API 查询业务表和只读投影，禁止读取 SDK 返回、同步日志或原始报文。

外部调用与本地事务采用可恢复任务模型，不能把 SDK 调用包进长事务：先创建同步任务和不可变请求摘要，再调用银行，随后持久化原始结果、标准化结果和状态变化。每个阶段以 `request_id`、企业 ID、任务编号、银行侧请求号和外部幂等号关联。

### 8.2 数据对象和保留策略

| 对象 | 最小字段与约束 |
| --- | --- |
| `bank_connection_profile` | `company_id`、银行、环境、适配器版本、签约状态、启用状态、凭据引用；不保存明文密钥 |
| `bank_sync_job` | `company_id`、任务类型（拉取/提交/回执）、触发方式（定时/手动）、状态、时间窗口、幂等键、请求编号、重试与调度信息 |
| `bank_sync_log` | 任务、请求编号、银行侧请求号、调用阶段、响应码、耗时、结果、安全摘要；仅追加 |
| `bank_raw_message` | 企业、任务、方向、接收时间、加密原始请求/响应、内容摘要、保留截止时间；业务写入不可修改原始消息 |
| `bank_canonical_record` | 企业、来源、银行流水号、账户、交易时间、金额、币种、方向、映射版本、校验状态、原始消息引用 |
| `payment_attempt` | 企业、转账申请、外部幂等号、银行侧请求号、出站摘要、回执状态、下一次查询时间 |

原始银行请求/响应及同步日志在数据库中保留 30 天，按接收时间计算。到期后清理或归档必须有可配置策略、清理审计和争议/审计保留豁免能力；具体处置方式尚未确定。真实凭据、私钥和访问令牌无论环境均不得写入原始报文、同步日志、审计、导出或客户端。

### 8.3 标准化、去重与业务写入

标准化层为每类银行数据定义稳定的内部模型：账户快照、资金流水、回单、对账单、支付回执和代发结果。模型必须带 `company_id`、`source_system`、`source_record_id`、`mapping_version`、原始消息引用和来源时间；银行专有字段保留在受控原始层，不进入通用业务表。

流水去重同时使用银行流水号以及“企业 + 银行账户 + 交易时间 + 金额”的组合。服务端先查组合命中，再由数据库以企业范围内的唯一索引兜底；处理重复回执、定时与手动同步重叠、网络重试时必须返回已有标准化/业务记录而非重写或创建第二条业务事实。若银行缺少稳定流水号，必须记录降级判定和人工复核原因。

标准化成功不等于业务成功：流水写入自动入账域后仍按校验、复核、制证流程处理；支付回执更新 `payment_attempt` 和转账申请状态，但只有明确最终回执才能进入 `EXECUTED`。`ACCEPTED`、超时和未知结果进入等待异步回执或待对账状态，禁止直接产生已付款交易或覆盖本地余额。

### 8.4 实施顺序与接口边界

1. 先完成 `company_id` 在连接、任务、原始报文、标准化记录、业务表和查询接口的强制服务端范围过滤。
2. 新增适配器 SPI、模拟适配器、`bank_sync_job` 状态机和定时/手动触发接口；真实 SDK 仍不接入。
3. 新增原始消息/同步日志持久化、30 天保留任务、标准化映射器、组合去重约束与追溯 API。
4. 将标准化流水接入自动入账域，将支付回执接入既有转账状态机；不得让任一链路绕过领域服务。
5. 银行交付 SDK、示例和 API 后，为每家银行单独实现 Adapter，并在沙箱验证签名、分页、超时、重复/乱序回执和补单。

建议 API 只暴露内部任务、业务投影和受控追溯：`POST /api/bank-sync-jobs`（授权手动触发）、`GET /api/bank-sync-jobs`、`GET /api/bank-sync-jobs/{id}`、`GET /api/bank-data/*` 以及按权限控制的追溯接口。原始报文不作为普通前端资源暴露；需要查看时通过受控审计 API 提供最小化、环境策略限定的内容。

### 8.5 暂定风险接受与待决策

当前接受“测试与非生产环境可临时使用真实银行业务数据”的风险，以支持集成测试；该决定不扩展到真实凭据、私钥或访问令牌。是否允许原始业务数据出现在日志、导出和哪些非生产环境，及其访问权限、脱敏、审计与退出条件，必须在银行沙箱联调和生产放行前完成专项决策。

仍待产品、财务、运维和安全共同确认：30 天到期后的清理/归档方式；定时任务责任人与告警升级策略；网络超时但银行可能已受理时的补单、对账和最终人工确认流程。
