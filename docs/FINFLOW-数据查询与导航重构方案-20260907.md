## 1. 现状盘点

### 1.1 导航结构（6 组 17 页）

| 顶层组 | 页面 | 权限 | 价值评估 |
|---|---|---|---|
| 工作台 | /dashboard | dashboard:view | 首页，保留 |
| 银行接入 | 银行账户 /bank-access/accounts | bank:view | 出纳配置，保留 |
| 银行接入 | 采集任务 /bank-access/tasks | operation:monitor 或 bankdata:view | 保留（建议改名「同步任务」） |
| 银行接入 | 采集失败日志 /bank-access/logs | operation:log:view | 低频运维，建议收纳 |
| 银行接入 | **数据查询（第 3 层）**：余额查询 / 流水查询 / 对账核对 | bankdata:balance/statement/reconciliation:view | **上移顶层** |
| 银行接入 | 原始报文 /bank-access/raw-messages | bankdata:raw:view | 银行原文铁证，保留但收纳 |
| 流水中心 | 导入流水 / 标准流水 / 人工复核 | statement:* | 1.0 主流程，保留 |
| 金蝶入账 | 科目与往来规则 / 凭证草稿与制证 | validation:* / voucher:push | 9/18 联调核心，保留 |
| 对账结账 | 三方对账 / 账期结账 | reconciliation:view / closing:* | 低频，候选收纳 |
| 系统管理 | 用户与角色 / 飞书配置 / 审计中心 | user:manage / feishu:* / audit:view | 保留 |

问题：核心的「数据查询」埋在第 3 层（银行接入 > 数据查询 > 余额查询）；6 个顶层组中「对账结账」只有 2 个低频页。

### 1.2 手动触发表单（采集任务页右上角）

现状 6 个字段全部手填，对业务用户不可用（实为开发者调试面板）：

| 字段 | 现状 | 问题 |
|---|---|---|
| 任务类型 | 手输文本，提示「例如：STATEMENT_PULL」 | 业务用户不可能知道枚举 |
| 账户标识 | 手输数字 ID | 不知道 ID 是什么 |
| 连接标识 | 手输可选 | 无意义（生产 profile 表为空） |
| 适配器代码 | 手输，提示「真实直联填 CMB」 | 9/7 已实现 bankCode 兜底，此字段多余 |
| 开始/结束时间 | 手打 ISO-8601 字符串 | 业务用户不会写 `2026-09-05T00:00:00` |

事实：系统实际只有 `STATEMENT_PULL` 一种作业类型（自动附带余额快照）；调度器 9/7 已上线自动拉 T-1，手动触发的真实场景只剩**补拉历史窗口**。

### 1.3 英文暴露点

- 采集任务列表/详情：任务类型（STATEMENT_PULL）、触发方式（MANUAL/SCHEDULED）、连接标识、状态（StatusTag 英文）
- 采集失败日志：级别/结果列英文
- 数据查询页：状态筛选手输英文（SUCCEEDED 等）
- 银行原生返回代码（bankStatusCode 等）**保持原文直出**（「收到什么就是什么」原则），不属于本次中文化范围

### 1.4 跨公司现状

- 查询链路按登录用户 companyId 强制过滤（单公司=单租户隔离）
- 公司有多家分公司/子公司，各自银行账号录入的流水分散在各公司视图下，集团视角看不到全局

## 2. 工作包设计

### WP1 跨公司主体查询

**备选：**
- **A1 跨公司查看权限（推荐）**：新增权限 `bankdata:cross-company:view`（V24 迁移，授权 ADMIN + FINANCE_MANAGER）。持有者在余额/流水查询页可看到「公司主体」下拉（数据源新端点 `GET /bank-data/company-options`，仅返回 ACTIVE 公司的 id+name），可选单个或不选=全部；查询结果每行加「公司主体」列。无该权限的用户行为完全不变（防越权回归）。
- A2 集团树（company 加 parent_id，按树授权）：更正规但要迁移+授权模型改造，9/18 前不必要。
- A3 登录后公司切换器：不符合「一个用户看全部」诉求。

**A1 实施要点：**
- 后端：`BankDataQueryService` 查询参数加可选 companyId；跨公司权限校验不过 → 403；行 DTO 加 companyName（**加字段必须 grep 全部构造点**，防聚合层静默吞字段教训）
- 迁移：`V24__bankdata_cross_company_permission.sql`（CI 断言 applied=文件数+1 需同步）
- 前端：筛选区加公司下拉（有权限才渲染），表格加公司列
- permission-catalog.md 同步 32→33 项

### WP2 手动触发 →「补拉历史数据」

表单 6 字段砍到 2 个：

| 字段 | 形态 | 默认值 |
|---|---|---|
| 银行账户 | 下拉（复用 /bank-accounts，中文户名+脱敏号） | 唯一账户自动选中 |
| 补拉日期区间 | RangePicker（业务日期） | 昨天 ~ 昨天，最长 90 天 |

- 固定文案说明：「作业类型：流水拉取（自动附带当日余额快照）；日常数据每晚自动同步，本功能用于银行补发历史数据或需要立即重拉指定日期」
- 连接标识/适配器代码/requestId 全部移除（服务端 bankCode 兜底 + 自动 requestId 已上线）
- 按钮改名「补拉历史数据」；确认弹窗用业务语言
- 权限不变（bankdata:sync:trigger）；后端零改动

### WP3 枚举中文化

- 新建 `frontend/src/modules/shared/dict.ts`：jobType / triggerType / status / connectionStatus 统一映射，一处定义全站复用
- 映射（初稿）：
  - 任务类型：STATEMENT_PULL → 流水拉取（含余额）
  - 触发方式：MANUAL → 手动 / SCHEDULED → 自动调度
  - 任务状态：SUCCEEDED → 成功 / FAILED → 失败 / PENDING → 进行中 / PARTIAL_SUCCESS → 部分成功 / UNKNOWN → 待核实 / DUPLICATE → 重复跳过 / EMPTY → 无新数据
  - 投影页：REAL → 已连接直联 / NOT_CONFIGURED → 未连接直联
- 采集任务筛选区改为 Select 选项化（不再手输英文）；失败日志级别/结果同步映射
- 未收录的枚举值兜底显示原文（防银行新增状态被吞）

### WP4 导航 IA 重构

**备选：**
- **B1 归并 4 组（推荐）**：顶组 6→4，页数不变只收纳：
  1. 工作台
  2. **银行数据（升顶层）**：余额查询 / 流水查询 / 对账核对 / 同步任务（原采集任务）/ 运行日志（原采集失败日志）/ 原始报文
  3. 流水与入账：导入流水 / 标准流水 / 人工复核 / 科目与往来规则 / 凭证草稿与制证
  4. 系统管理：用户与角色 / 审计中心 / 账期结账 / 三方对账 / 飞书配置
- B2 最小上移：仅把「数据查询」上移为顶层组「银行数据」（余额/流水/对账核对），其余全不动。改动最小，但「太多组」的抱怨不解决。
- B3 极简 3 组（数据 / 作业 / 管理）：最干净，但组内单页过多，权限差异大，暂不推荐。

**候选收纳/下线清单（收纳=菜单换位置，不删代码不动权限）：**
| 页面 | 建议 | 理由 |
|---|---|---|
| 账期结账 | 收纳进系统管理 | 低频，9 月演练未见使用 |
| 三方对账 | 收纳进系统管理 | 与「对账核对」（银行 Z1）名字易混，可考虑改名「对账核对(平台)」或暂藏 |
| 采集失败日志 | 收纳 + 改名「运行日志」 | 30 条全 INFO，无真失败 |
| 飞书配置 | 收纳 | 低频 |

**路由兼容**：旧路径 `/bank-access/data/*` 等保留 301 重定向（沿用既有 Navigate 惯例）；书签不失效。
