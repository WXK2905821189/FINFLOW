## 一、结论先说

**19 条规则已全部结构化，但目前不能直接'录进规则中心'**——不是格式问题，而是其中
**12 条依赖 3 类现有引擎不具备的能力**（供应商/员工/货币资金维度、多维度注入、查找表）。
硬录进去会有个坏结果：界面上看着配好了，一推就失败，或者更糟——**维度缺失被金蝶按空维度记账**。

建议：**规则先入库（追加，scope 隔离）→ 同时补 3 项能力 → 再启用**。分期方案见第五节。

## 五、必须补的 4 项能力（缺一项就有规则推不通）

### 缺口 1：5 个新维度类型（影响 12 条规则）

| 维度 | 用在哪 | 现状 |
|---|---|---|
| `SUPPLIER_CODE` | R24~R28、R32、R37（10 处） | ❌ 现有 `SUPPLIER` 取的是**对手方名称**，而金蝶要的是 `VEN00511` 这类**档案编码** |
| `SUPPLIER_CODE_DEPT_LINE` | R26（2 处） | ❌ 多维度组合（供应商+部门+业务线） |
| `EMPLOYEE_CODE` | R29、R30（2 处） | ❌ 同上：要员工编码，不是姓名 |
| `MONEY_FUND` | R34（1 处） | ❌ 货币资金类维度（1012 / 薪福通账号） |
| `FIXED` 多值 | R27、R31、R38~R40（7 处） | ✅ 已支持单值；多值形如 `VEN00511/RZ008/BM000009` 需按槽位拆 |

### 缺口 2：3 个新匹配算子

| 算子 | 用在哪 | 说明 |
|---|---|---|

| `IN_EMPLOYEE_LIST` | R30 | 对手方必须匹配到附件2 的员工 |

现有算子：`SUMMARY CONTAINS` ✅、`IN_ORG_LIST` ✅。

### 缺口 3：凭证分录的**多核算维度注入** —— ✅ 已补齐（2026-09-21）

原状：payload builder 只会注入**一个**槽位（`FDETAILID__FF100002` = 银行账号）。
图虫侧要求同一分录同时带「供应商 + 部门 + 业务线」。

**已实施**：

1. `KingdeeVoucherEntryDraft` 新增 `extraDimensions`（1..n 个维度），payload builder 支持同一
   分录注入多个槽位（多个键共用一个 `FDetailID` 对象）；未就绪的维度在推送前**拒绝并给出补齐
   指引**（fail-closed，不静默按空维度记账）；
2. **槽位归属已破解并实证**——不必再让金蝶给清单，也不必逐个盲试：
   读 `QueryBusinessInfo(GL_VOUCHER)` 元数据，每个 `FDETAILID__FFxxxx` 字段自带
   `Name = 维度名`；再用真实凭证交叉实证（16059 / 16060 保存成功后即时回滚）。
   完整台账见 **`kingdee-dimension-slot-ledger-20260921.md`**（含 14 个维度 ↔ 槽位 ↔ 值来源）；
3. 槽位与值映射均由 V42 两张表承载（`kingdee_dimension_slot` / `kingdee_dimension_mapping`），
   可在「规则中心 › 核算维度配置」界面直接维护。

⚠️ 唯一未解：**「业务线」维度在账套里不存在**（`BD_FLEXITEMPROPERTY` 14 个维度类型中无此项）
→ 见台账第四节三选一决策。

### 缺口 4：`KingdeeOrgResolver` 扩展 —— ✅ 已实施（2026-09-21）

已追加 **映脉 411 / 浙江北分 421 / 浙江 420 / 图虫 410** 四个主体，顺序按「具体者在前」排：

映脉(411) → 浙江北分(421) → 浙江(420) → 图虫(410) → 长沙(710) → 广州(720) → 海南(900) → 即设(300) → 雪云(400)

### 附：附件数据的落点（412 + 354 行，**不属于规则表**）

规则表 `kingdee_voucher_rule` 装的是"怎么判断+怎么记账"，附件是"某个名字对应哪个金蝶编码"——
两类数据。建议新建 **`kingdee_dimension_mapping`**（类型/名称/金蝶编码/业务线/部门/有效期），
提供「按对手方名→编码」解析服务，规则里只引用 `SUPPLIER_CODE` 这类**逻辑维度名**。
这样附件月更（客户 mapping 明说是月更）不必动规则表。
