**维度类型是「基础资料」**（不是辅助资料），数据状态已审核、系统预置。因此：
- 我上一轮「账套未维护维度值」的推断**不成立**（辅助资料里查不到很正常，因为值引用的是基础资料）；

**✅ 已解开（2026-09-21 11:52，实测保存成功并回滚）**：

正确形态是**两层**——外层 `FDetailID`（对象 / Dictionary），内层键是**带前缀的完整字段名**：

```json
"FDetailID": { "FDETAILID__FF100002": { "FNumber": "11050160520009100036" } }
```

- 实测凭证号 **16043（内码 116182）保存成功**，随后立即删除回滚（`ExcuteOperation Delete`）。
- 关键线索来自形态试错的反证：把 `FDetailID` 传成数组时报
  `无法将类型为"Kingdee.BOS.JSON.JSONArray"的对象强制转换为类型"Dictionary"` →
  证明 **`FDetailID` 必须是对象**，且内层键要用 `FDETAILID__FFxxxx` 全名（不是裸槽位名 `FF100002`）。
- 维度可选值由用户截图确认 = `CN_BANKACNT` 账号档案（含 `11050160520009100036`，属 org 400）。
- **槽位归属实测**：`FF100002` = 银行账号（ZDY0001）。

**结论**：银行类科目（1002）推 GL 凭证时，按上述形态注入维度即可，**无需金蝶侧再配置**。

## 四、维度取值改为账户级映射（2026-09-21 当日实施完成）

前置 ①② 都解开后暴露出一个新的产品问题：**维度值取什么？** 原先取全局
`KINGDEE_DEFAULT_BANK_ACCOUNT_NUMBER`（一个值打天下）是联调期占位——用户明确反馈：
「我有很多公司，每个公司都有几个银行账号」，要求与「银行账号」模块联动。

**结论：维度值应跟随该笔流水所属的我方账户**（凭证里银行存款分录记的只是某一个账户），
可全自动解析，不需要财务逐笔填写。

| 层 | 实现 |
|---|---|
| 数据 | V41 给 `bank_account` 加 `kingdee_account_number`（= CN_BANKACNT 的 FNumber） |
| 取档案 | `KingdeeVoucherGateway.queryBankAccountCatalog()` 只读拉 CN_BANKACNT（编码/名称/组织） |
| 匹配 | `KingdeeAccountMappingService`：账号规范化精确匹配 → 多命中用「公司→金蝶组织」消歧 → **唯一命中才自动写回**；多义/零命中列候选交人工 |
| 取值 | `BankAccountDimensionResolver` 按流水所属账户取；**未映射即阻断**（400 + 指明去「银行账户」页补映射） |
| 界面 | 银行账户页「金蝶账户」列 + 「金蝶账户映射」抽屉（一键自动匹配 / 候选点选 / 手工输入） |

**真实账套档案特征（只读实测，决定匹配策略）**：

- 142 个档案分属 **23 个组织**；**102 个 FNumber 就是账号本体**（可直接匹配），
  其余 40 个是虚拟账户编码（支付宝邮箱 `admin@xiaopiu.com`、`分贝通平台`、`shym001`、
  `11111111`、`222`、`333` 等）→ 无账号可匹配，须人工指定一次；
- **同一账号可在不同组织各有一个档案**（如网商银行账号在 300/400 都有）⇒ 必须用
  「公司 → 金蝶组织」消歧，否则多义；
- 零命中时把**该公司所属组织下的全部档案**作为候选给出，人工挑一个即可（覆盖虚拟账户场景）。
